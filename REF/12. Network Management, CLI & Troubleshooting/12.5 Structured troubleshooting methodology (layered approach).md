# 1. Overview

Structured troubleshooting is a systematic approach used by network engineers to identify, isolate, and resolve network problems. Instead of randomly changing configurations, engineers follow a logical process based on the OSI model, TCP/IP model, and documented troubleshooting methods.

The layered troubleshooting approach helps determine whether the problem exists at the physical layer, data link layer, network layer, transport layer, or application layer.

---

# 2. Why Use a Structured Approach?

Without methodology:

```
Problem

↓

Random configuration changes

↓

More problems
```

---

With structured troubleshooting:

```
Problem

↓

Collect information

↓

Identify layer

↓

Test hypothesis

↓

Fix issue

↓

Verify solution
```

---

# 3. Troubleshooting Process

Cisco commonly follows these steps:

```
1. Identify the problem

2. Establish a theory of probable cause

3. Test the theory

4. Establish a plan of action

5. Implement the solution

6. Verify full functionality

7. Document findings
```

---

# 4. Step 1: Identify the Problem

## Goal

Understand:

- What is failing?
- Who is affected?
- When did it start?
- What changed?

---

# Information Gathering

Sources:

| Source | Example |
|---|---|
| User reports | Cannot access website |
| Monitoring tools | Interface errors |
| Logs | Syslog messages |
| Alerts | Device down |
| Documentation | Network diagrams |

---

# Questions to Ask

| Question | Purpose |
|---|---|
| What is not working? | Define scope |
| Who is affected? | Determine impact |
| When started? | Find timeline |
| Was there a change? | Identify cause |
| Is it intermittent? | Determine pattern |

---

# Example

Problem:

```
User cannot access server
```

Need to determine:

- One user?
- Entire department?
- Local network?
- Remote network?

# 5. Step 2: Establish Theory of Probable Cause

Create possible causes.

Example:

Problem:

```
Cannot reach server
```

Possible causes:

| Layer | Possible Cause |
|---|---|
| Physical | Cable disconnected |
| Data Link | VLAN mismatch |
| Network | Missing route |
| Transport | Firewall blocking port |
| Application | Server service down |

---

# Common Approach

Start with simple causes:

```
Physical issue

↓

Configuration issue

↓

Protocol issue

↓

Application issue
```

---

# 6. Step 3: Test the Theory

Use commands and tools.

---

# Testing Tools

| Tool | Purpose |
|---|---|
| ping | Connectivity test |
| traceroute | Path discovery |
| show commands | Device status |
| debug | Real-time events |
| logs | Historical events |
| packet capture | Traffic analysis |

---

# Example

Theory:

```
Interface is down
```

Test:

```bash
show ip interface brief
```

Result:

```
Gi0/1 administratively down
```

Cause confirmed.

# 7. Step 4: Establish a Plan of Action

Before making changes:

Consider:

- Impact
- Risk
- Rollback plan
- Maintenance window

---

Example:

Problem:

Wrong VLAN assignment.

Plan:

```
Move port to correct VLAN

↓

Verify connectivity

↓

Document change
```

---

# 8. Step 5: Implement Solution

Apply the fix carefully.

Example:

Interface shutdown:

Check:

```bash
show interfaces status
```

Fix:

```bash
interface g0/1
no shutdown
```

---

# 9. Step 6: Verify Full Functionality

Verify:

## Connectivity

```bash

```

## Interfaces

```bash

```

---

## Routing

```bash

```

---

## Applications

Test:

- Website access

# 10. Step 7: Document Findings

# 11. OSI Layer Troubleshooting Approach

A network can be tested layer by layer.

---

# Layer 1: Physical Layer

## Checks

- Cable
- Power
- Interface status
- Transceiver
- Signal

---

Commands:

```bash
show interfaces
```

```bash
show controllers
```

---

Common Problems:

| Problem | Symptom |
|---|---|
| Cable failure | Link down |
| Bad optic | No signal |
| Power issue | Device offline |

---

# Layer 2: Data Link Layer

## Checks

- MAC addresses
- VLANs
- Trunks
- STP

---

Commands:

```bash
show vlan brief
```

```bash
show mac address-table
```

```bash
show interfaces trunk
```

---

Common Problems:

| Problem | Symptom |
|---|---|
| VLAN mismatch | No communication |
| STP blocking | Port unavailable |
| Duplex mismatch | Errors |

---

# Layer 3: Network Layer

## Checks

- IP addressing
- Routing
- ACLs

---

Commands:

```bash
show ip route
```

```bash
show ip interface brief
```

---

Common Problems:

| Problem | Symptom |
|---|---|
| Wrong subnet | Cannot communicate |
| Missing route | Destination unreachable |
| ACL block | Traffic denied |

---

# Layer 4: Transport Layer

## Checks

- TCP/UDP ports
- Firewall rules
- Sessions

---

Examples:

HTTP:

```
TCP 80
```

HTTPS:

```
TCP 443
```

SSH:

```
TCP 22
```

---

Common Problems:

| Problem | Symptom |
|---|---|
| Port blocked | Application unavailable |
| Firewall rule | Connection refused |

---

# Layer 5-7: Application Layers

## Checks

- Application services
- DNS
- Authentication
- Server status

---

Common Problems:

| Problem | Symptom |
|---|---|
| DNS failure | Name does not resolve |
| Service down | Application unavailable |

# 12. Bottom-Up Troubleshooting

## Start at Layer 1

Method:

```
Physical

↓

Data Link

↓

Network

↓

Transport

↓

Application
```

---

Advantages:

- Good for unknown problems
- Finds basic failures quickly

---

Example:

Cannot access website:

Check:

```
Cable

↓

IP address

↓

Routing

↓

DNS

↓

Browser
```

---

# 13. Top-Down Troubleshooting

## Start at Application Layer

Method:

```
Application

↓

Transport

↓

Network

↓

Data Link

↓

Physical
```

---

Advantages:

- Faster for application problems

---

Example:

Website fails:

Check:

```
Browser

↓

HTTP

↓

TCP 443

↓

IP routing
```

---

# 14. Divide-and-Conquer Troubleshooting

Start in middle layers.

Example:

Check Layer 3 first:

```
Can ping gateway?

```

If yes:

```
Routing works

```

If no:

```
Investigate Layer 1-3
```

---

Advantages:

- Faster isolation

# 19. Troubleshooting Best Practices

| Practice | Reason |
|---|---|
| Change one thing at a time | Identify cause |
| Document changes | Tracking |
| Backup configuration | Recovery |
| Avoid unnecessary reboot | Reduce impact |
| Use show before debug | Safer |
| Verify after changes | Confirm fix |

---

# CCNA Exam Traps

- Troubleshooting should follow a structured process.
- Always identify the problem before changing configuration.
- Start with simple causes first.
- Use `show` commands before `debug`.
- Physical layer problems must be checked first in bottom-up troubleshooting.
- Document the solution after fixing the issue.
- Debug commands can impact device performance.
