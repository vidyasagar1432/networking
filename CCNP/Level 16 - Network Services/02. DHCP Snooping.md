# DHCP Snooping

> **Level 16 · Network Services** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

**DHCP Snooping** is a **Layer 2 security feature** that protects switched networks from  
unauthorized DHCP servers and DHCP-based attacks.

It establishes a **trusted/untrusted interface model**:

- **Trusted ports** — allowed to receive DHCP server messages.
    
- **Untrusted ports** — normally client-facing; DHCP server messages received here are  
    blocked.
    

DHCP snooping also builds a **DHCP binding database** containing information such as:

- Client MAC address
    
- Assigned IP address
    
- VLAN
    
- Switch interface
    
- Lease information
    

The binding database can be used by other security features, especially:

- **Dynamic ARP Inspection (DAI)**
    
- **IP Source Guard**
    

### Main protections

|Threat|DHCP Snooping Mechanism|
|---|---|
|Rogue DHCP server|Blocks server messages on untrusted ports|
|DHCP starvation|Rate-limits DHCP traffic|
|Invalid IP/MAC relationships|Provides bindings for DAI/IP Source Guard|
|Unauthorized DHCP information|Enforces trusted/untrusted boundary|

> **Core idea:** DHCP snooping controls **where DHCP server messages are allowed to  
> originate** and learns legitimate DHCP client bindings.

---

# 2. Why DHCP Snooping Is Needed

Without DHCP snooping, a malicious device could connect to a normal access port and  
operate as a rogue DHCP server.

Example:

```text
                         Legitimate DHCP Server
                                  |
                                  |
                            Trusted Port
                                  |
                           +-------------+
                           |   Switch    |
                           +-------------+
                            |           |
                      Untrusted     Untrusted
                           |           |
                        Client      Rogue DHCP
                                    Server
```

The rogue server could send:

```text
DHCPOFFER
DHCPACK
```

and provide clients with malicious or incorrect:

- IP address
    
- Default gateway
    
- DNS server
    
- Other DHCP options
    

This could redirect client traffic or disrupt network connectivity.

DHCP snooping prevents this by treating client-facing interfaces as **untrusted** and  
blocking unauthorized DHCP server messages received there.

---

# 3. Trusted vs Untrusted Ports

## 3.1 Trusted Ports

A trusted port is normally connected toward:

- Legitimate DHCP server
    
- DHCP relay
    
- Network infrastructure/uplink carrying legitimate DHCP server responses
    

Example:

```cisco
interface GigabitEthernet0/1
 ip dhcp snooping trust
```

Server-originated messages such as:

```text
DHCPOFFER
DHCPACK
DHCPNAK
```

are allowed from trusted interfaces.

---

## 3.2 Untrusted Ports

Interfaces are **untrusted by default** for DHCP snooping.

Client-facing access ports normally remain untrusted.

Example:

```text
Switch
 |
 +-- Gi0/1  --> DHCP Server / Relay
 |             TRUSTED
 |
 +-- Gi0/10 --> Client
 |             UNTRUSTED
 |
 +-- Gi0/11 --> Client
               UNTRUSTED
```

DHCP server messages received on an untrusted interface can be dropped.

> **Exam trap:** Trust the **server/relay/uplink-facing interface**, not normal  
> client-facing ports.

---

# 4. What DHCP Snooping Checks

DHCP snooping inspects DHCP traffic entering switch interfaces.

The most important trust check is:

```text
DHCP Server Message
        |
        v
Which interface received it?
        |
   +----+----+
   |         |
Trusted   Untrusted
   |         |
 Allow      Drop
```

Typical server-originated messages include:

- DHCPOFFER
    
- DHCPACK
    
- DHCPNAK
    

Client-originated DHCP messages such as:

- DHCPDISCOVER
    
- DHCPREQUEST
    
- DHCPDECLINE
    
- DHCPRELEASE
    
- DHCPINFORM
    

are normally received on untrusted client-facing interfaces.

DHCP snooping observes these transactions and can use successful DHCP activity to build  
the binding database.

---

# 5. DHCP Snooping Configuration

Enable DHCP snooping globally:

```cisco
ip dhcp snooping
```

Enable it for VLAN 10:

```cisco
ip dhcp snooping vlan 10
```

Trust the interface toward the legitimate DHCP server or relay:

```cisco
interface GigabitEthernet0/1
 ip dhcp snooping trust
```

Rate-limit DHCP traffic on a client-facing interface:

```cisco
interface GigabitEthernet0/10
 ip dhcp snooping limit rate 10
```

Complete example:

```cisco
ip dhcp snooping
ip dhcp snooping vlan 10

interface GigabitEthernet0/1
 description Uplink-to-DHCP-Server-or-Relay
 ip dhcp snooping trust

interface GigabitEthernet0/10
 description Client-Port
 ip dhcp snooping limit rate 10
```

---

# 6. DHCP Snooping and VLANs

DHCP snooping is enabled globally and then enabled for the required VLANs.

```cisco
ip dhcp snooping
ip dhcp snooping vlan 10
```

Multiple VLANs:

```cisco
ip dhcp snooping vlan 10,20,30
```

Depending on IOS/IOS XE syntax, a VLAN range can also be configured:

```cisco
ip dhcp snooping vlan 10-20
```

> **Exam trap:** `ip dhcp snooping` alone does not mean every VLAN is protected.  
> The relevant VLANs must also be enabled.

---

# 7. DHCP Snooping Rate Limiting

DHCP snooping can limit the number of DHCP packets accepted on an interface.

Example:

```cisco
interface GigabitEthernet0/10
 ip dhcp snooping limit rate 10
```

This limits DHCP packet reception to approximately **10 packets per second** on that  
interface.

Rate limiting helps mitigate:

- Excessive DHCP traffic
    
- DHCP starvation attacks
    
- Abnormally high DHCP request rates
    

> **Important:** Rate limiting is a mitigation mechanism. It does not independently  
> identify an attack as a starvation attack.

---

# 8. DHCP Starvation Attack

A **DHCP starvation attack** attempts to consume all available addresses in a DHCP  
pool.

An attacker may generate many DHCP requests using different client identities.

```text
Attacker
   |
   | Many DHCP requests
   v
Switch
   |
   v
DHCP Server
   |
   +--> Address 1
   +--> Address 2
   +--> Address 3
   +--> Address 4
   +--> ...
   +--> Pool exhausted
```

### Impact

Legitimate clients may be unable to obtain an IP address.

### Mitigations

- DHCP snooping
    
- DHCP snooping rate limiting
    
- Port security
    
- Other Layer 2 security controls
    

> **Exam trap:** DHCP snooping rate limiting helps mitigate starvation; it does not  
> magically detect and identify every starvation attack.

---

# 9. DHCP Snooping Binding Database

DHCP snooping builds a **binding database** from DHCP transactions.

Typical fields include:

|Field|Information|
|---|---|
|MAC Address|Client MAC address|
|IP Address|DHCP-assigned IPv4 address|
|VLAN|Client VLAN|
|Interface|Client-facing switch port|
|Lease|Lease-related information|

Example:

```text
MAC Address       IP Address       VLAN       Interface
--------------------------------------------------------
AAAA.BBBB.CCCC    10.10.10.101    10         Gi0/10
DDDD.EEEE.FFFF    10.10.10.102    10         Gi0/11
```

The binding identifies the relationship:

```text
MAC + IP + VLAN + Interface + Lease
```

---

# 10. How Bindings Are Learned

A simplified successful DHCP transaction looks like:

```text
Client
  |
  | DHCPDISCOVER
  v
Switch
  |
  | DHCPREQUEST
  v
DHCP Server
  |
  | DHCPACK
  v
Switch
  |
  | Learns DHCP binding
  v
Binding Database
```

The switch observes the DHCP exchange and records the resulting client binding.

Bindings are generally associated with **dynamically learned DHCP clients**.

> **Important:** A host using a manually configured static IP does not automatically  
> produce a normal DHCP snooping binding through a DHCP transaction.

---

# 11. Static DHCP Snooping Bindings

Static IP devices may need special handling when security features such as IP Source  
Guard or DAI depend on the DHCP snooping database.

Some Cisco platforms support **static DHCP snooping bindings**.

A common Cisco IOS/IOS XE form is:

```cisco
ip dhcp snooping binding <MAC> vlan <VLAN> <IP> interface <INTERFACE>
```

Example syntax:

```cisco
ip dhcp snooping binding 0011.2233.4455 vlan 10 10.10.10.50 interface GigabitEthernet0/10
```

> **Platform note:** Static binding syntax and support can vary by Cisco IOS/IOS XE  
> release and platform. Always verify the exact syntax for the target device.

---

# 12. DHCP Snooping Binding Database Persistence

A DHCP snooping binding database can be stored externally so that bindings can survive  
a switch reload.

Cisco platforms can support a DHCP snooping database agent using a configured database  
location.

Example syntax:

```cisco
ip dhcp snooping database flash:dhcp-snooping.db
```

The exact supported storage options vary by platform and IOS/IOS XE release.

### Why persistence matters

Without persistent binding information, a switch reload can result in loss of learned  
dynamic bindings.

That can affect security features that depend on the bindings, such as:

- Dynamic ARP Inspection
    
- IP Source Guard
    

Conceptually:

```text
DHCP Snooping
      |
      v
Binding Database
      |
      +----> Persistent Storage
      |
      +----> Survives Reload
```

> **Exam concept:** Binding persistence is important when other security features depend  
> on the DHCP snooping database after a reload.

---

# 13. DHCP Snooping + DAI + IP Source Guard

The DHCP snooping binding database can provide information to other security features.

```text
                 DHCP Snooping
                       |
                       v
              Binding Database
                 /          \
                /            \
               v              v
              DAI       IP Source Guard
```

## Dynamic ARP Inspection

**DAI** uses DHCP snooping bindings to validate ARP information.

It helps prevent attacks involving forged ARP information.

## IP Source Guard

**IP Source Guard** uses binding information to restrict IP traffic based on the  
expected IP/MAC/interface relationship.

> **Exam trap:** DHCP snooping is often the foundation for **DAI and IP Source Guard**.

---

# 14. DHCP Snooping and Option 82

**DHCP Option 82 = Relay Agent Information.**

It can contain information such as:

- **Circuit ID**
    
- **Remote ID**
    

Conceptually:

```text
Client
  |
  | DHCPDISCOVER
  v
Switch / Relay
  |
  | Option 82
  | +----------------+
  | | Circuit ID     |
  | | Remote ID      |
  | +----------------+
  v
DHCP Server
```

Option 82 can be used for:

- Client identification
    
- Location-based addressing
    
- DHCP policy
    
- Subscriber identification
    
- Security controls
    

---

## 14.1 Option 82 Configuration

Cisco platforms can support:

```cisco
ip dhcp snooping information option
```

This enables DHCP Option 82 insertion/handling where supported.

Some platforms also support:

```cisco
ip dhcp snooping information option allow-untrusted
```

This can allow DHCP packets containing Option 82 from untrusted sources, depending on  
platform and configuration.

> **Important:** Option 82 is **Relay Agent Information**. It is not itself a general  
> mechanism for detecting every spoofing attack.

> **Platform note:** Exact Option 82 behavior and commands can vary by Cisco IOS/IOS XE  
> release and platform.

---

# 15. DHCP Snooping with DHCP Relay

A common enterprise topology is:

```text
Client
  |
  v
Access Switch
DHCP Snooping
  |
  | Trusted Uplink
  v
L3 Switch / Router
DHCP Relay
  |
  | ip helper-address
  v
DHCP Server
```

The access switch provides Layer 2 DHCP security.

The Layer 3 device provides DHCP relay.

These are **different functions**.

|Feature|Purpose|
|---|---|
|DHCP Snooping|DHCP security|
|DHCP Relay|Forward DHCP between subnets|
|`ip helper-address`|Configures DHCP relay|
|Option 82|Relay Agent Information|
|Binding Database|DHCP client security information|

---

# 16. DHCP Snooping and `giaddr`

When a Layer 3 device acts as a DHCP relay, it can populate the **`giaddr` (Gateway IP  
Address)** field.

The DHCP server can use `giaddr` to determine the client's subnet and select the  
appropriate DHCP scope.

```text
Client
10.10.10.0/24
    |
    v
Relay
10.10.10.1
    |
    | giaddr = 10.10.10.1
    v
DHCP Server
    |
    +--> Select 10.10.10.0/24 DHCP pool
```

> DHCP snooping and `giaddr` are related through DHCP relay operation, but they are not  
> the same feature.

---

# 17. DHCP Snooping on Trunk Ports

Trunk links commonly carry multiple VLANs.

Example:

```text
                 DHCP Server
                      |
                L3 Switch / Relay
                      |
                 Trunk / Uplink
                      |
                Access Switch
                 /          \
              VLAN 10      VLAN 20
             Clients      Clients
```

If the trunk carries legitimate DHCP server/relay traffic, the appropriate interface  
may need to be trusted:

```cisco
interface GigabitEthernet0/1
 switchport mode trunk
 ip dhcp snooping trust
```

The relevant VLANs must also have DHCP snooping enabled:

```cisco
ip dhcp snooping
ip dhcp snooping vlan 10,20
```

> **Exam trap:** Trusting a trunk is a security decision. Only trust it when legitimate  
> DHCP server/relay traffic is expected through that path.

---

# 18. DHCP Snooping with EtherChannel

When DHCP traffic crosses an EtherChannel toward a trusted network device, DHCP snooping  
trust must be configured appropriately for the EtherChannel design and platform.

Example:

```cisco
interface Port-channel1
 ip dhcp snooping trust
```

Verify the actual platform behavior and supported configuration.

Conceptually:

```text
DHCP Server
    |
    +---- Gi0/1 \
    |            \
    +---- Gi0/2 ---- Port-Channel1
                      |
                   Switch
```

> **Important:** EtherChannel behavior and whether configuration is applied to the  
> logical port-channel or member interfaces can vary by feature/platform. Follow the  
> platform-specific Cisco implementation.

# 22. DHCP Snooping Troubleshooting

Use a structured workflow:

```text
Client
  |
  v
Access Port
  |
  v
DHCP Snooping
  |
  v
Trusted Uplink
  |
  v
DHCP Relay
  |
  v
DHCP Server
```

---

## 22.1 Hosts Get No IP Address

Check:

```cisco
show ip dhcp snooping
show ip dhcp snooping statistics
```

Possible causes:

- DHCP snooping not enabled on the client VLAN
    
- DHCP server/relay-facing port is untrusted
    
- Rate limit is too low
    
- DHCP relay problem
    
- DHCP server/pool problem
    
- Incorrect VLAN assignment
    

---

## 22.2 Legitimate DHCP Server Is Blocked

Likely cause:

```text
Server/relay-facing interface is untrusted.
```

Correct:

```cisco
interface GigabitEthernet0/1
 ip dhcp snooping trust
```

---

## 22.3 Legitimate Clients Are Rate-Limited

Check:

```cisco
show running-config interface GigabitEthernet0/10
```

Look for:

```cisco
ip dhcp snooping limit rate 10
```

If the configured rate is too low, legitimate DHCP traffic can be affected.

---

## 22.4 Binding Table Is Empty

Check:

```cisco
show ip dhcp snooping binding
```

Verify:

- DHCP snooping is globally enabled.
    
- Client VLAN is enabled.
    
- Client is actually using DHCP.
    
- DHCP transaction is completing.
    
- Binding database has not been cleared.
    
- Correct interfaces are configured.
    

---

## 22.5 DAI Starts Dropping ARP

Check:

```cisco
show ip dhcp snooping binding
```

Possible causes:

- Missing binding
    
- Incorrect binding
    
- Client uses static IP
    
- DHCP lease expired
    
- DHCP snooping was recently enabled
    
- Binding database was lost after reload
    

For static clients, appropriate static bindings or other DAI configuration may be  
required.

---

# 23. DHCP Snooping Database Recovery

A switch reload can affect dynamically learned DHCP snooping bindings.

If persistent storage is configured, the switch can recover the binding database after  
reload.

Concept:

```text
Before Reload
     |
     v
DHCP Snooping Bindings
     |
     v
Persistent Database
     |
     v
Switch Reload
     |
     v
Binding Recovery
```

This is especially important when:

- DAI depends on the bindings.
    
- IP Source Guard depends on the bindings.
    
- Clients have long DHCP leases.
    
- The switch may reload while leases remain active.

|DHCP through EtherChannel fails|Incorrect trust configuration|Port-channel configuration|

# 26. Exam Traps

- DHCP snooping is primarily a **Layer 2 switch security feature**.
    
- DHCP snooping primarily protects against **rogue DHCP servers**.
    
- Interfaces are **untrusted by default**.
    
- Trust the interface toward the **legitimate DHCP server/relay**.
    
- Do not blindly trust client-facing ports.
    
- DHCP server messages received on untrusted interfaces can be dropped.
    
- **DHCPOFFER, DHCPACK, and DHCPNAK** are server-originated DHCP messages.
    
- Enable DHCP snooping globally with:  
    `ip dhcp snooping`
    
- Enable it on the required VLANs with:  
    `ip dhcp snooping vlan <vlan-id>`
    
- Rate limiting helps mitigate **DHCP starvation**.
    
- Rate limiting is not the same as starvation detection.
    
- DHCP snooping creates a **binding database**.
    
- The binding contains information such as **MAC, IP, VLAN, interface, and lease**.
    
- DAI can use the DHCP snooping binding database.
    
- IP Source Guard can use the DHCP snooping binding database.
    
- **Option 82 = Relay Agent Information**.
    
- Option 82 commonly contains **Circuit ID and Remote ID**.
    
- DHCP snooping and DHCP relay are **different functions**.
    
- `ip helper-address` configures DHCP relay, not DHCP snooping.
    
- `giaddr` is associated with DHCP relay operation.
    
- Static IP clients do not automatically create normal DHCP snooping bindings.
    
- Static bindings may be required for some DAI/IP Source Guard designs.
    
- Binding persistence matters when security features depend on bindings after reload.
    
- Trusting an uplink/trunk is a **security decision**.
    
- Exact Option 82, database persistence, static-binding, trunk, and EtherChannel behavior  
    can vary by Cisco platform and IOS/IOS XE version.

# 30. Final Exam Summary

The complete DHCP snooping model is:

```text
                  DHCP Snooping
                        |
          +-------------+-------------+
          |                           |
       TRUSTED                    UNTRUSTED
          |                           |
 Server / Relay                   Clients
          |                           |
 Allow DHCP                     Inspect DHCP
 server messages                     |
          |                           |
          |                    Block rogue
          |                    server messages
          |                           |
          +-------------+-------------+
                        |
                        v
                Binding Database
                        |
              +---------+---------+
              |                   |
              v                   v
             DAI          IP Source Guard
```

### Remember these five points

1. **DHCP Snooping = Layer 2 DHCP security.**
    
2. **All ports are untrusted by default; trust the legitimate server/relay path.**
    
3. **Untrusted ports cannot legitimately provide DHCP server messages.**
    
4. **The snooping binding database provides MAC/IP/VLAN/interface information for  
    security features such as DAI and IP Source Guard.**
    
5. **Rate limiting helps mitigate DHCP starvation; Option 82 provides Relay Agent  
    Information.**
    

**Core idea:** DHCP snooping establishes a **trust boundary for DHCP traffic**, blocks  
unauthorized DHCP server messages, learns legitimate DHCP bindings, and provides the  
foundation for additional Layer 2 security mechanisms.
