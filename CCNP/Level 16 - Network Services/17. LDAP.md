# LDAP

> **Level 16 · Network Services** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

**LDAP (Lightweight Directory Access Protocol)** is a protocol used to access and  
manage **directory services** containing identities and attributes such as users,  
groups, computers, and organizational information.

LDAP organizes information in a hierarchical **Directory Information Tree (DIT)**.  
**Active Directory Domain Services (AD DS)** and **OpenLDAP** are examples of directory  
services that support LDAP.

LDAP commonly uses **TCP 389**. LDAP can also be protected with **StartTLS on 389**,  
while **LDAPS** conventionally uses **TCP 636** with TLS established when the connection  
starts.

> **Exam focus:** LDAP is a directory-access protocol; Active Directory is a directory  
> service/product that supports LDAP.

---

## 2. Core Concepts

### 2.1 Directory Information Tree (DIT)

LDAP entries are organized hierarchically in a **Directory Information Tree (DIT)**.

Example:

```text
dc=corp,dc=example
 └── ou=Users
      └── cn=Bob
```

Example Distinguished Name (DN):

```text
cn=Bob,ou=Users,dc=corp,dc=example
```

|Component|Meaning|Example|
|---|---|---|
|`dc`|Domain Component|`dc=corp`|
|`ou`|Organizational Unit|`ou=Users`|
|`cn`|Common Name|`cn=Bob`|
|DN|Distinguished Name; uniquely identifies an entry|`cn=Bob,ou=Users,dc=corp,dc=example`|

**DN = the unique name/path used to identify an LDAP entry.**

---

## 3. LDAP vs Relational Database

LDAP is designed as a **directory service**, optimized for efficient  
identity and attribute lookups.

|LDAP Directory|Relational Database|
|---|---|
|Hierarchical DIT|Tables and relationships|
|Entries + attributes|Rows + columns|
|Distinguished Names (DNs)|Primary/foreign keys|
|Directory-oriented queries|SQL queries|
|Commonly used for identity data|General-purpose structured data|
|Optimized for directory lookups|Broad transactional/data workloads|

> Do not reduce LDAP to simply “a tree database.” LDAP is a **protocol for accessing  
directory services**.

---

## 4. LDAP Entries and Attributes

An LDAP **entry** represents an object such as a user, group, computer, or device.

Entries contain **attributes**.

Example:

```text
dn: cn=Bob,ou=Users,dc=corp,dc=example
objectClass: person
cn: Bob
sn: Smith
mail: bob@example.com
```

- **Entry** = directory object
    
- **Attribute** = property of that object
    
- **DN** = unique identifier for the entry
    
- **objectClass** = defines the types/schema rules applicable to an entry
    

---

## 5. LDAP Operations

LDAP clients communicate with a directory server using operations such as:

|Operation|Purpose|
|---|---|
|**BIND**|Establish/authenticate an LDAP session|
|**SEARCH**|Find entries matching criteria|
|**ADD**|Create an entry|
|**MODIFY**|Change attributes|
|**DELETE**|Remove an entry|
|**MODIFY DN**|Rename/move an entry|
|**UNBIND**|End the LDAP session|

### BIND

**BIND** establishes the LDAP authentication/session context.

Common forms include:

- **Simple Bind** — typically uses a DN and password
    
- **SASL Bind** — uses SASL authentication mechanisms
    
- **Anonymous Bind** — no user credentials
    

> **Exam trap:** BIND does not always mean “password authentication.” LDAP supports  multiple authentication mechanisms, including anonymous and SASL authentication.

---

## 6. LDAP Search Filters

LDAP uses filters to locate directory entries.

Example:

```text
(&(objectClass=user)(sAMAccountName=bob))
```

This means:

> Find an entry that is a `user` AND whose `sAMAccountName` is `bob`.

### Common filter operators

|Syntax|Meaning|
|---|---|
|`(&...)`|AND|
|`(|...)`|
|`(!...)`|NOT|
|`(attribute=value)`|Equality match|
|`(attribute=*)`|Attribute exists|
|`(attribute=value*)`|Wildcard/prefix matching|

Example OR:

```text
(|(uid=bob)(uid=alice))
```

Example NOT:

```text
(!(objectClass=computer))
```

> **Exam trap:** `&`, `|`, and `!` are LDAP filter operators — not regular SQL operators.

## 7. LDAP Ports and Security

|Port|Service|Security|
|--:|---|---|
|**TCP 389**|LDAP|Plain LDAP unless protected with StartTLS|
|**TCP 636**|LDAPS|TLS from the beginning of the connection|
|**TCP 3268**|Active Directory Global Catalog|Non-TLS|
|**TCP 3269**|Active Directory Global Catalog over SSL/TLS|TLS|

### LDAP on TCP 389

LDAP on 389 can operate without encryption.

For example:

```text
Client ─── TCP 389 ───> LDAP Server
```

Credentials and directory data should **not** be assumed protected merely because  
TCP 389 is being used.

### StartTLS

LDAP can upgrade an existing TCP 389 connection to TLS using **StartTLS**:

```text
TCP 389
   ↓
LDAP connection
   ↓
StartTLS
   ↓
TLS-protected LDAP
```

### LDAPS

LDAPS conventionally uses TCP 636 and establishes TLS when the connection begins:

```text
Client ─── TLS/TCP 636 ───> LDAP Server
```

> **Exam focus:**  
> **389 = LDAP**  
> **636 = LDAPS**  
> **StartTLS = TLS upgrade on an existing LDAP connection, typically TCP 389**

---

## 8. LDAP and Active Directory

**LDAP is a protocol. Active Directory is a directory service.**

Active Directory Domain Services (AD DS) supports LDAP for directory access.

Common AD-related ports include:

|Port|Purpose|
|--:|---|
|TCP 389|LDAP|
|TCP 636|LDAP over SSL/TLS|
|TCP 3268|Global Catalog|
|TCP 3269|Global Catalog over SSL/TLS|

Other AD protocols/services use additional ports, including:

- Kerberos
    
- DNS
    
- SMB
    
- RPC
    

> **Exam trap:** LDAP and Active Directory are **not interchangeable terms**.

## 9. LDAP in Network Authentication

LDAP is often used as an **identity directory/backend**, rather than as the  
network-device AAA protocol itself.

A common enterprise design is:

```text
Network Device
      │
      │ RADIUS / TACACS+
      ▼
 AAA Server
      │
      │ LDAP / AD lookup
      ▼
LDAP / Active Directory
```

For example:

- A switch uses **802.1X** for endpoint access control.
    
- The switch commonly communicates with a **RADIUS server**.
    
- The RADIUS server may use **LDAP/Active Directory** to verify identity or obtain  
    group/attribute information.
    

Similarly, an AAA platform may use LDAP/AD as its external identity source.

> **Important:** Do not assume that a Cisco network device directly performs ordinary  
> network AAA against LDAP. In many enterprise deployments, **RADIUS/TACACS+ is the  
> network AAA protocol**, while LDAP/AD provides the identity backend.

---

## 10. LDAP and AAA

LDAP can provide identity information to authentication systems.

Typical relationship:

```text
LDAP / AD
   │
   │ User / group information
   ▼
AAA Server
   │
   │ RADIUS / TACACS+
   ▼
Network Device
```

### Typical roles

|Technology|Primary role|
|---|---|
|LDAP|Directory access|
|Active Directory|Directory/identity service|
|RADIUS|Network access AAA|
|TACACS+|Network-device AAA|
|802.1X|Port-based network access control|

> **Exam distinction:** LDAP is primarily a **directory protocol**, not a replacement  
> for RADIUS or TACACS+.

## 11. LDAP Schema

LDAP directories use a **schema** that defines:

- Object classes
    
- Attribute types
    
- Syntax
    
- Matching rules
    
- Required/allowed attributes
    

Example:

```text
objectClass: person
    ├── cn
    ├── sn
    └── mail
```

The schema controls what types of objects and attributes can exist in the directory.

---

## 12. Active Directory Global Catalog

The **Global Catalog (GC)** is an Active Directory service that provides information  
about objects across an AD forest.

|Port|Service|
|--:|---|
|**3268**|Global Catalog|
|**3269**|Global Catalog over SSL/TLS|

The Global Catalog contains a **partial replica of attributes** for objects in the  
forest, allowing forest-wide searches without querying every domain separately.

> **Exam trap:**  
> **389/636 = LDAP**  
> **3268/3269 = AD Global Catalog**

## 13. Troubleshooting

|Symptom|Possible Cause|What to Check|
|---|---|---|
|Authentication fails|Invalid credentials / bind failure|Username, password, bind DN|
|Connection timeout|Firewall/ACL/routing issue|TCP 389/636 connectivity|
|No entries returned|Incorrect search base/filter|Base DN and search filter|
|LDAP search fails|Invalid filter|LDAP filter syntax|
|TLS failure|Certificate/trust problem|Certificate, hostname, CA trust|
|LDAPS connection fails|TCP 636 blocked|Firewall/ACL/listener|
|StartTLS fails|TLS negotiation problem|Server support, certificates, TLS settings|
|Wrong group/attribute result|Search scope/filter problem|Base DN, scope, filter, attributes|
|Global Catalog unavailable|3268/3269 connectivity issue|AD GC service and firewall|

### Useful troubleshooting logic

```text
1. Can the client reach the LDAP server?
           ↓
2. Is TCP 389/636 reachable?
           ↓
3. Does TLS/StartTLS succeed?
           ↓
4. Does BIND succeed?
           ↓
5. Is the search base correct?
           ↓
6. Is the LDAP filter correct?
           ↓
7. Are the expected attributes/groups returned?
```

## 14. Security Considerations

### Plain LDAP

Unprotected LDAP traffic should not be treated as confidential.

```text
Client ─── LDAP/389 ───> Server
             ⚠
        No encryption
```

### TLS-protected LDAP

Use StartTLS or LDAPS when encryption is required:

```text
Client ─── TLS ───> LDAP Server
```

TLS provides protection for data in transit and can provide server authentication  
through certificates.

### Important security points

- Protect LDAP authentication traffic with TLS.
    
- Validate server certificates.
    
- Use strong authentication mechanisms where appropriate.
    
- Restrict anonymous access when not required.
    
- Apply least privilege to directory accounts.
    
- Monitor authentication and directory access.
    
- Protect LDAP servers with network access controls.

## 15. LDAP vs RADIUS vs TACACS+

|Feature|LDAP|RADIUS|TACACS+|
|---|---|---|---|
|Primary purpose|Directory access|Network AAA|Network-device AAA|
|Common port|TCP 389|UDP 1812/1813|TCP 49|
|Directory service|Yes|No|No|
|Authentication|Yes, via BIND|Yes|Yes|
|Authorization|Directory attributes/groups|Yes|Yes|
|Accounting|Not its primary role|Yes|Yes|
|Common enterprise use|Identity backend|Network access AAA|Device administration AAA|

> LDAP can be used **behind** RADIUS/TACACS+ as an identity source.

## 16. Exam Traps

- **LDAP = protocol**, not a directory product.
    
- **Active Directory = directory service** that supports LDAP.
    
- **TCP 389 = LDAP**.
    
- **TCP 636 = LDAPS**.
    
- **StartTLS can protect LDAP on TCP 389**.
    
- **TCP 3268 = AD Global Catalog**.
    
- **TCP 3269 = AD Global Catalog over SSL/TLS**.
    
- **DIT = Directory Information Tree**.
    
- **DN = Distinguished Name**.
    
- **BIND = establishes/authenticates an LDAP session**, but does not necessarily mean password authentication.
    
- **SEARCH = directory lookup**.
    
- `&` = AND.
    
- `|` = OR.
    
- `!` = NOT.
    
- LDAP is a **directory protocol**, not a replacement for RADIUS/TACACS+.
    
- RADIUS/TACACS+ servers can use **LDAP/Active Directory as an identity backend**.
    
- **802.1X commonly uses RADIUS** for the authentication exchange; LDAP/AD may sit behind the RADIUS server.
    
- Do not assume **TCP 389 is always encrypted**.
    
- Do not confuse **LDAP 389/636** with **AD Global Catalog 3268/3269**.
