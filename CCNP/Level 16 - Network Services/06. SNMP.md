# SNMP (Simple Network Management Protocol)

> **Level 16 · Network Services** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

**SNMP (Simple Network Management Protocol)** is used to monitor and manage  
network devices.

It allows a management system to:

- Read device information
    
- Monitor interfaces and resources
    
- Collect performance statistics
    
- Modify certain configuration values when permitted
    
- Receive asynchronous notifications about events
    

Common transport ports:

- **UDP 161** — SNMP requests/responses
    
- **UDP 162** — SNMP notifications such as traps and informs
    

The major SNMP versions are:

```text
SNMPv1
SNMPv2c
SNMPv3
```

For modern secure deployments, **SNMPv3 is preferred** because it supports  
authentication and optional encryption/privacy.

---

# 2. SNMP Architecture

A typical SNMP deployment looks like:

```text
                    SNMP Manager
                         |
                  UDP 161 / 162
                         |
        +----------------+----------------+
        |                                 |
        v                                 v
   SNMP Agent                         SNMP Agent
      R1                                  SW1
        |                                 |
        v                                 v
      MIB/OIDs                          MIB/OIDs
```

### Manager

The **SNMP manager** is the network-management system that:

- Polls devices
    
- Collects statistics
    
- Displays information
    
- Sends SNMP SET operations when authorized
    

Examples include network-management/monitoring platforms.

### Agent

The **SNMP agent** runs on the managed device.

It:

- Maintains managed information
    
- Responds to SNMP requests
    
- Generates notifications
    

Cisco IOS/IOS XE devices can act as SNMP agents.

# 3. MIB and OIDs

## MIB

**MIB (Management Information Base)** defines the managed objects that can  
be monitored or managed through SNMP.

The MIB is organized hierarchically.

## OID

An **OID (Object Identifier)** identifies a particular object in the SNMP  
object hierarchy.

Example:

```text
1.3.6.1.2.1.1
```

This is part of the standard `system` MIB branch.

Common branches:

|OID|General area|
|---|---|
|`1.3.6.1.2.1.1`|System|
|`1.3.6.1.2.1.2`|Interfaces|
|`1.3.6.1.2.1.4`|IP|
|`1.3.6.1.4.1`|Private enterprise|
|`1.3.6.1.4.1.9`|Cisco enterprise branch|

### Important distinction

```text
MIB
 |
 +-- Defines managed objects
 |
 +-- OID
      |
      +-- Identifies a specific object/instance
```

The Cisco enterprise branch is:

```text
1.3.6.1.4.1.9
```

# 4. SNMP Operations

|Operation|Purpose|
|---|---|
|**GET**|Read a specific object|
|**GETNEXT**|Retrieve the next object in the MIB tree|
|**GETBULK**|Efficiently retrieve multiple objects|
|**SET**|Modify an object|
|**TRAP**|Unsolicited notification|
|**INFORM**|Notification requiring acknowledgment|

### GET

The manager requests information:

```text
Manager → GET → Agent
Manager ← Response ← Agent
```

### SET

The manager attempts to modify a value:

```text
Manager → SET → Agent
Manager ← Response ← Agent
```

The operation must be authorized by the SNMP configuration/access policy.

### GETBULK

`GETBULK` allows a manager to retrieve larger amounts of information  
efficiently.

Important:

> **GETBULK was introduced with SNMPv2 and is not an SNMPv1 operation.**

# 5. TRAP vs INFORM

This is a common exam topic.

## TRAP

A trap is an **unsolicited notification** sent by the SNMP agent.

```text
Agent
  |
  | TRAP
  v
Manager
```

The sender does not receive an SNMP acknowledgment for the trap.

## INFORM

An inform is also an unsolicited notification, but the receiving SNMP  
manager sends an acknowledgment.

```text
Agent
  |
  | INFORM
  v
Manager
  |
  | Response / acknowledgment
  v
Agent
```

Therefore:

|Feature|TRAP|INFORM|
|---|---|---|
|Agent initiated|Yes|Yes|
|Unsolicited|Yes|Yes|
|Acknowledgment|No|Yes|
|Reliability|Lower|Higher|
|Transport|Usually UDP|Usually UDP|

### Exam memory

> **TRAP = no acknowledgment**  
> **INFORM = acknowledgment**

INFORM improves reliability, but it does **not** mean SNMP stops using UDP.

# 6. SNMP Versions

## SNMPv1

The original widely deployed SNMP version.

Security:

- Community strings
    
- No encryption
    
- Weak security model
    

Example:

```text
community = public
```

---

## SNMPv2c

SNMPv2c improves the protocol operations over v1.

Important additions include:

- `GETBULK`
    
- `INFORM`
    

However, the **"c" means community-based security**.

It still uses:

- Community strings
    
- No encryption
    
- No strong cryptographic authentication
    

Therefore:

> SNMPv2c provides better protocol functionality than v1, but not modern  
> cryptographic security.

---

## SNMPv3

SNMPv3 provides a significantly stronger security model.

It supports three security levels:

|Security level|Authentication|Privacy/encryption|
|---|---|---|
|`noAuthNoPriv`|No|No|
|`authNoPriv`|Yes|No|
|`authPriv`|Yes|Yes|

### noAuthNoPriv

No authentication and no encryption.

### authNoPriv

Authentication is provided, but the SNMP payload is not encrypted.

### authPriv

Authentication **and privacy/encryption** are provided.

This is generally the preferred SNMPv3 security level.

---

# 7. SNMPv3 Security

SNMPv3 commonly uses:

### Authentication

Provides message authentication and helps verify that messages originate  
from an authorized source.

Depending on platform/release, supported authentication algorithms can  
include:

- MD5
    
- SHA variants
    

### Privacy

Encrypts SNMP messages.

Common algorithms include:

- DES
    
- AES variants
    

For modern deployments, stronger algorithms should be preferred when  
supported.

---

# 8. SNMP Community Strings

SNMPv1 and SNMPv2c use **community strings**.

Conceptually:

```text
Manager
   |
   | community = cisco123
   v
Agent
```

Typical access:

```text
RO = Read Only
RW = Read Write
```

Example:

```cisco
snmp-server community cisco123 RO
snmp-server community netops RW
```

### Security warning

Community strings should not be treated as secure passwords.

SNMPv1/v2c do not provide cryptographic encryption.

A read-write community is especially dangerous because a compromised  
community string can potentially allow unauthorized modification of  
managed values.

For secure deployments:

> **Prefer SNMPv3.**

# 9. SNMPv2c Cisco Configuration

Basic read-only community:

```cisco
snmp-server community cisco123 RO
```

Read-write:

```cisco
snmp-server community netops RW
```

Configure an SNMP manager/notification destination:

```cisco
snmp-server host 10.0.0.5 version 2c cisco123
```

Configure device location:

```cisco
snmp-server location R1
```

Configure administrator contact:

```cisco
snmp-server contact netadmin@corp
```

# 10. SNMPv3 Configuration

A basic SNMPv3 configuration involves:

1. Group
    
2. User
    
3. Authentication/privacy
    
4. Manager/notification destination
    

Example:

```cisco
snmp-server group ADMIN v3 priv

snmp-server user cisco-user ADMIN v3 auth sha SecretAuth priv aes 128 SecretPriv

snmp-server host 10.0.0.5 version 3 priv cisco-user
```

### Group

```cisco
snmp-server group ADMIN v3 priv
```

The group defines the SNMPv3 security level and can also be associated with  
access controls/views.

### User

```cisco
snmp-server user cisco-user ADMIN v3 auth sha SecretAuth priv aes 128 SecretPriv
```

The user contains:

- Username
    
- Group
    
- Authentication method/key
    
- Privacy method/key
    

### Important

The exact syntax for supported algorithms and key lengths can vary by  
Cisco IOS/IOS XE release.

# 11. SNMP Views

SNMP views control which MIB objects an SNMP group is allowed to access.

Conceptually:

```text
SNMP Manager
      |
      v
SNMP Group
      |
      v
SNMP View
      |
      v
Allowed MIB objects
```

Example:

```cisco
snmp-server view NMSVIEW iso included
```

A group can then reference a view:

```cisco
snmp-server group ADMIN v3 priv read NMSVIEW
```

Views are important because they allow administrators to restrict SNMP  
access to only the required portions of the MIB.

---

# 12. SNMP Notifications

Cisco devices can send event notifications to an SNMP management system.

Configure a destination:

```cisco
snmp-server host 10.0.0.5 version 2c cisco123
```

Notifications can be generated for events such as:

- Interface state changes
    
- Routing events
    
- Device conditions
    
- Authentication/security events
    
- Other supported Cisco MIB events
    

The exact notifications generated depend on the configured SNMP traps,  
platform, and IOS/IOS XE features.

---

# 13. SNMP Traps

Trap generation can be configured with:

```cisco
snmp-server enable traps
```

Specific trap categories can also be enabled.

Examples may include:

```cisco
snmp-server enable traps snmp
snmp-server enable traps syslog
snmp-server enable traps config
```

Exact supported categories vary by IOS/IOS XE release and platform.

---

# 14. SNMP Access Control

SNMP should not normally be exposed to every host.

A common security approach is:

```text
              ACL
               |
               v
NMS --------> Router
               |
               X
          Unauthorized hosts
```

Restrict SNMP access to trusted management systems.

For example, an access list can limit which NMS systems can communicate  
with SNMP services.

# 16. SNMP Polling vs Notifications

### Polling

The manager periodically asks the device for information.

```text
Manager
   |
   | GET
   v
Agent
   |
   | Response
   v
Manager
```

Advantages:

- Predictable
    
- Manager controls frequency
    
- Good for statistics
    

### Notification

The device sends an event to the manager.

```text
Agent
   |
   | TRAP / INFORM
   v
Manager
```

Advantages:

- Immediate event notification
    
- No need for the manager to continuously poll for every event
    

Enterprise monitoring normally uses a combination of polling and  
notifications.

# 20. Troubleshooting

## No SNMP response

Possible causes:

```text
UDP 161 blocked
Incorrect community
Wrong SNMP version
ACL blocking NMS
SNMP agent/configuration problem
Incorrect SNMPv3 credentials
```

Check:

```cisco
show snmp
show snmp group
show snmp user
show snmp host
```

---

## No traps

Check:

```cisco
show snmp host
```

Then verify:

- Destination IP
    
- SNMP version
    
- Community/user
    
- Trap configuration
    
- UDP 162 reachability
    
- Required trap categories enabled
    

---

## SNMP SET fails

Possible causes:

- Read-only community
    
- SNMPv3 user lacks write access
    
- MIB object is read-only
    
- SNMP view blocks the object
    
- Authorization/access configuration
    

Remember:

> SNMP write capability depends on both the SNMP security/access  
> configuration and whether the particular MIB object supports writing.

---

## SNMPv3 authentication fails

Check:

- Username
    
- Group
    
- Authentication algorithm
    
- Authentication key
    
- Security level
    
- Privacy algorithm
    
- Privacy key
    
- SNMPv3 configuration on both sides
    

---

## SNMP works but values are missing

Possible causes:

- Wrong OID
    
- Unsupported MIB
    
- Incorrect MIB version
    
- SNMP view restricting the object
    
- Object not supported by the device/platform

# 23. Exam Traps

- **UDP 161** = SNMP requests/responses.
    
- **UDP 162** = traps/informs.
    
- **SNMPv1/v2c use community strings.**
    
- Community strings are **not encryption**.
    
- **SNMPv3** provides the modern security model.
    
- `authNoPriv` = authentication without encryption.
    
- `authPriv` = authentication + encryption/privacy.
    
- **TRAP** does not require an acknowledgment.
    
- **INFORM** requires an acknowledgment.
    
- INFORM still normally uses **UDP**.
    
- `GETBULK` is available in **SNMPv2 and later**, not v1.
    
- `GETNEXT` walks the MIB hierarchy.
    
- `SET` modifies a writable object when authorization permits.
    
- **MIB** defines/organizes managed objects.
    
- **OID** identifies objects in the MIB hierarchy.
    
- Cisco enterprise OID = **`1.3.6.1.4.1.9`**.
    
- `RO` = read-only.
    
- `RW` = read-write.
    
- SNMPv3 uses **users and groups**, not community strings.
    
- SNMP views can restrict which MIB objects a user/group can access.
    
- `show snmp` is a key troubleshooting command.
    
- Do not assume every `show snmp ...` subcommand exists identically on every  
    IOS/IOS XE release.
    
- SNMP monitoring normally combines **polling + notifications**.
