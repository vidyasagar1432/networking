# Syslog

> **Level 16 · Network Services** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

**Syslog** is a standardized mechanism for generating and transporting  
event/log messages.

Network devices use Syslog to record events such as:

- Interface state changes
    
- Routing events
    
- Authentication events
    
- Configuration changes
    
- System errors
    
- Hardware/software conditions
    
- Debugging information
    

Cisco devices can store messages locally and/or send them to a centralized  
Syslog server.

Typical Cisco Syslog transport:

- **UDP 514** — traditional/default Syslog transport
    

Other Syslog implementations can use TCP and TLS, but **UDP 514** is the  
important baseline for CCNP ENCOR.

---

# 2. Syslog Architecture

A typical enterprise deployment:

```text
Router R1 ───────┐
                |
Switch SW1 ─────+────> Central Syslog Server
                |
Router R2 ──────┘
```

Centralized logging provides:

- One location for event analysis
    
- Long-term log storage
    
- Correlation across multiple devices
    
- Easier troubleshooting
    
- Security monitoring
    
- Incident investigation
    

Without centralized logging, device logs may remain only on the local  
device and can be lost after a reload or buffer overflow.

# 3. Syslog Severity Levels

Cisco Syslog uses severity levels **0 through 7**.

|Level|Name|Meaning|
|--:|---|---|
|**0**|Emergency|System unusable|
|**1**|Alert|Immediate action required|
|**2**|Critical|Critical condition|
|**3**|Error|Error condition|
|**4**|Warning|Warning condition|
|**5**|Notice|Normal but significant condition|
|**6**|Informational|Informational message|
|**7**|Debugging|Debugging information|

### Critical exam rule

```text
0 = most severe
7 = least severe / most verbose
```

Think:

```text
Emergency
   0
   |
   v
Alert
   1
   |
   v
Critical
   2
   |
   v
Error
   3
   |
   v
Warning
   4
   |
   v
Notice
   5
   |
   v
Informational
   6
   |
   v
Debugging
   7
```

# 4. Severity Thresholds

This is one of the most important Syslog exam concepts.

If you configure:

```cisco
logging trap 4
```

the device sends:

```text
0 Emergency
1 Alert
2 Critical
3 Error
4 Warning
```

It does **not** send levels 5, 6, and 7.

### Rule

> **A severity threshold includes that level and all numerically lower  
> (more severe) levels.**

Examples:

|Threshold|Messages sent|
|--:|---|
|0|0|
|1|0–1|
|2|0–2|
|3|0–3|
|4|0–4|
|5|0–5|
|6|0–6|
|7|0–7|

Therefore:

```text
logging trap 4
```

means:

```text
0–4 → sent
5–7 → not sent
```

# 5. Syslog Message Format

Cisco Syslog messages commonly look like:

```text
%FACILITY-SEVERITY-MNEMONIC: description
```

Example:

```text
%LINEPROTO-5-UPDOWN: Line protocol on Interface GigabitEthernet0/1, changed state to up
```

Breakdown:

```text
%LINEPROTO
     |
     +-- Facility

-5
 |
 +-- Severity

-UPDOWN
 |
 +-- Mnemonic

: description
     |
     +-- Event details
```

# 6. Syslog Message Components

## Facility

Identifies the subsystem or component generating the message.

Examples can include:

```text
LINK
LINEPROTO
OSPF
SYS
BGP
```

The exact facilities available depend on the Cisco platform and software.

## Severity

The numeric severity from:

```text
0–7
```

## Mnemonic

A short identifier describing the event.

Example:

```text
UPDOWN
```

## Description

Provides additional information about what happened.

# 7. Local Syslog Logging

Cisco devices can maintain a local logging buffer.

Example:

```cisco
logging buffered 4096
```

This stores log messages in RAM.

Verify:

```cisco
show logging
```

### Important

The local buffer is **volatile**.

If the device reloads, the buffered messages are normally lost.

For persistent centralized logging, send messages to an external Syslog  
server.

---

# 8. Remote Syslog Server

Configure a remote Syslog server:

```cisco
logging host 10.0.0.5
```

You can configure multiple destinations:

```cisco
logging host 10.0.0.5
logging host 10.0.0.6
```

Set the severity threshold for remote logging:

```cisco
logging trap 4
```

This sends severity:

```text
0–4
```

to the configured remote Syslog destinations.

---

# 9. Logging Destinations

Cisco IOS can send messages to different destinations.

Common destinations include:

|Destination|Purpose|
|---|---|
|Console|Display messages on console|
|VTY/monitor|Display messages on terminal sessions|
|Buffer|Store messages in RAM|
|Syslog server|Send messages to remote collector|

Conceptually:

```text
                     +--> Console
                     |
Device logs ---------+--> VTY monitor
                     |
                     +--> Local buffer
                     |
                     +--> Remote Syslog server
```

---

# 10. Console Logging

Console logging controls messages displayed on the console.

Example:

```cisco
logging console
```

A severity threshold can also be configured.

For example:

```cisco
logging console warnings
```

The exact keyword form depends on the desired severity.

### Important

Console logging can be noisy, especially when debugging is enabled.

Excessive console logging can affect interactive access and, in extreme  
cases, device performance.

---

# 11. Terminal / VTY Logging

Messages can be displayed on active terminal sessions.

Enable:

```cisco
logging monitor
```

Then a user connected through VTY/terminal can receive logging messages.

A useful command during troubleshooting is:

```cisco
terminal monitor
```

This enables logging messages to appear in the current VTY/SSH session.

### Important distinction

```text
logging monitor
      |
      +-- Configures monitor logging behavior

terminal monitor
      |
      +-- Enables monitoring for the current terminal session
```

---

# 12. Logging Source Interface

Configure a stable source IP:

```cisco
logging source-interface Loopback0
```

This makes the router use the Loopback0 address as the source for Syslog  
messages.

Advantages:

- Stable source IP
    
- Easier ACL configuration
    
- Easier identification of the device
    
- Better management-plane consistency
    

Conceptually:

```text
Router
  |
  | Source = Loopback0
  v
Syslog Server
```

### Important

`logging source-interface` chooses the source address.

It does **not** bypass ACLs or routing requirements.

---

# 13. Timestamps

Timestamps are extremely important for troubleshooting and event  
correlation.

Configure:

```cisco
service timestamps log datetime msec
```

For debugging messages:

```cisco
service timestamps debug datetime msec
```

Example:

```text
Aug 14 22:10:15.123: %LINEPROTO-5-UPDOWN:
Line protocol on Interface GigabitEthernet0/1, changed state to up
```

Timestamps allow administrators to determine:

- When an event occurred
    
- Which event happened first
    
- Whether events across devices are related
    

---

# 14. NTP + Syslog

Accurate timestamps require accurate device clocks.

Therefore:

```text
NTP
 |
 v
Accurate device clock
 |
 v
Accurate Syslog timestamps
 |
 v
Reliable event correlation
```

Without NTP, different devices can have significantly different clocks,  
making troubleshooting and security investigations harder.

### Key concept

> **NTP provides accurate time; Syslog records events using that time.**

They complement each other.

---

# 15. Syslog vs SNMP

Do not confuse Syslog with SNMP.

|Feature|Syslog|SNMP|
|---|---|---|
|Primary purpose|Event/log collection|Monitoring/management|
|Typical transport|UDP 514|UDP 161/162|
|Polling|No|Yes|
|Notifications|Log messages|Traps/Informs|
|MIB/OID|No|Yes|
|Example|Interface-down event|Interface counter|

A device can generate both a Syslog message and an SNMP notification for  
the same underlying event, but:

> **Syslog does not inherently "feed" SNMP traps.**

They are separate mechanisms.

# 17. Verification

### Show logging configuration and statistics

```cisco
show logging
```

This is the primary Syslog verification command.

It can show:

- Logging status
    
- Configured destinations
    
- Logging levels
    
- Buffer contents
    
- Console/monitor settings
    
- Timestamps
    
- Syslog messages
    

### Clear buffered logs

```cisco
clear logging
```

This clears the local logging buffer.

Important:

> It does **not** delete logs already stored on a remote Syslog server.

# 18. Common Troubleshooting

## No logs reaching Syslog server

Check:

```text
1. Syslog server IP
2. Remote logging configuration
3. Logging threshold
4. Source interface
5. Routing
6. ACL/firewall
7. UDP 514
```

Verify:

```cisco
show logging
```

---

## Too many messages

Possible cause:

```text
Threshold is too verbose
```

For example:

```cisco
logging trap 7
```

allows levels:

```text
0–7
```

including debugging information.

Increase the threshold number only if you intentionally want more  
verbosity.

Remember:

```text
0 = least messages / most severe only
7 = most messages / most verbose
```

---

## Important clarification

If the objective is to **reduce** logging noise:

```text
logging trap 4
```

is less verbose than:

```text
logging trap 7
```

because level 4 permits only:

```text
0–4
```

while level 7 permits:

```text
0–7
```

---

# 19. No Messages in Buffer

Check:

```cisco
show logging
```

Verify that buffered logging is configured:

```cisco
logging buffered 4096
```

Also check the configured buffer severity.

# 20. Wrong Source IP

If the Syslog server expects messages from a particular management address:

```cisco
logging source-interface Loopback0
```

Then verify:

- Loopback is reachable
    
- Routing exists
    
- ACL permits the source
    
- Syslog server accepts the source IP

# 21. Logging Facility and Severity

Syslog messages contain information identifying the source subsystem and  
severity.

Cisco-style example:

```text
%OSPF-4-ERRRCV: Received invalid packet
```

Breakdown:

```text
OSPF
 |
 +-- Facility

4
 |
 +-- Severity = Warning

ERRRCV
 |
 +-- Mnemonic
```

The facility helps administrators identify the subsystem responsible for  
the message.

# 23. Severity Example

Suppose a device generates these messages:

```text
%SYS-0-...
%SYS-2-...
%SYS-4-...
%SYS-5-...
%SYS-6-...
```

With:

```cisco
logging trap 4
```

the remote Syslog server receives:

```text
0
2
4
```

It does not receive:

```text
5
6
7
```

because those are less severe than level 4.

# 24. Security Considerations

Traditional Syslog over UDP does not provide strong confidentiality or  
integrity protection.

Security considerations include:

- Protect the management network
    
- Restrict which devices can send logs
    
- Use secure transport when supported/required
    
- Protect the Syslog server
    
- Prevent unauthorized access to stored logs
    
- Synchronize device clocks with NTP
    

For sensitive environments, secure Syslog transports such as TLS can be  
used where supported.

# 25. Exam Traps

- Traditional Cisco Syslog commonly uses **UDP 514**.
    
- Syslog severity levels are **0–7**.
    
- **0 = most severe**.
    
- **7 = debugging / most verbose**.
    
- A severity threshold includes that level and all **numerically lower**  
    levels.
    
- `logging trap 4` sends levels **0–4** to remote Syslog hosts.
    
- `logging trap 7` is the most verbose threshold.
    
- `logging host X` configures a remote Syslog destination.
    
- `logging source-interface X` chooses the source IP/interface.
    
- `logging buffered` stores logs locally in RAM.
    
- `show logging` is the primary verification command.
    
- `clear logging` clears the local logging buffer.
    
- `logging console` controls console logging.
    
- `logging monitor` controls terminal/VTY logging behavior.
    
- `terminal monitor` enables logging display in the current terminal  
    session.
    
- `service timestamps log datetime msec` adds timestamps to log messages.
    
- NTP provides accurate time; Syslog records events using that time.
    
- Syslog and SNMP are **separate mechanisms**.
    
- Syslog does **not** inherently feed SNMP traps.
    
- Cisco message format commonly resembles:  
    `%FACILITY-SEVERITY-MNEMONIC`.
    
- UDP 514 is common, but Syslog is **not inherently limited to UDP**;  
    secure/stream transports such as TCP/TLS may be used depending on the  
    implementation.
