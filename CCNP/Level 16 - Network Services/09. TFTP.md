# TFTP (Trivial File Transfer Protocol)

> **Level 16 · Network Services** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

**TFTP** (Trivial File Transfer Protocol) is a simple, **connectionless file-transfer protocol** that uses **UDP**. It is commonly associated with network-device operations such as transferring **IOS images, configuration files, and IP-phone firmware/configuration files**.

TFTP provides **no built-in authentication, encryption, or directory-listing capability**. Its simplicity makes it easy to implement, but it also makes it unsuitable for sensitive file transfers across untrusted networks.

**Exam focus:** UDP 69, RRQ/WRQ, DATA/ACK, lack of authentication, simple file transfer, and Cisco device use.

---

## 2. Core Concepts

### 2.1 Protocol model

|Item|TFTP|
|---|---|
|Transport|UDP|
|Well-known port|UDP 69|
|Connection-oriented?|No|
|Authentication|None|
|Encryption|None|
|Directory listing|Not provided by TFTP|
|Reliability|Retransmission + acknowledgments|
|Classic operation|Lock-step DATA/ACK|
|Default/original data block size|512 bytes|

> **Important:** UDP 69 is used for the initial TFTP request. After the RRQ/WRQ, the actual transfer normally uses dynamically selected UDP transfer ports.

TFTP uses two types of requests:

- **RRQ — Read Request:** client requests a file from the server.
    
- **WRQ — Write Request:** client requests to send a file to the server.

## 3. TFTP Transfer Operation

### 3.1 Classic RRQ flow

```text
Client                         TFTP Server
  |                                |
  |------ RRQ (filename) --------->|
  |                                |
  |<----- DATA block 1 ------------|
  |                                |
  |------ ACK block 1 ------------>|
  |                                |
  |<----- DATA block 2 ------------|
  |                                |
  |------ ACK block 2 ------------>|
  |                                |
  |              ...               |
  |                                |
  |<----- Final DATA --------------|
  |------ ACK final -------------->|
```

In classic TFTP:

1. Client sends an **RRQ** or **WRQ**.
    
2. Server begins the transfer.
    
3. DATA packets contain numbered blocks.
    
4. The receiver acknowledges each DATA block.
    
5. Lost packets can be retransmitted after a timeout.
    
6. The transfer ends when the final DATA packet contains **less than the negotiated block size**.
    
7. If the file size is an exact multiple of the block size, a **zero-length final DATA packet** is required to signal EOF.
    

### 3.2 Lock-step operation

Classic TFTP operates in a **lock-step DATA/ACK pattern**:

```text
DATA 1 → ACK 1 → DATA 2 → ACK 2 → DATA 3 → ACK 3
```

Only after receiving the ACK does the sender normally proceed to the next block.

> **Exam trap:** TFTP is not reliable because UDP itself is reliable. TFTP adds its own acknowledgments and retransmission mechanism on top of UDP.

### 3.3 TFTP extensions

Modern TFTP can negotiate options such as:

- **blksize** — negotiated block size
    
- **tsize** — transfer size
    
- **windowsize** — allows multiple DATA packets to be outstanding
    

Therefore, **512 bytes is the classic/default block size**, not an absolute protocol maximum.

For CCNP ENCOR, remember the classic **DATA → ACK → DATA → ACK** model.

## 4. TFTP vs FTP vs SCP/SFTP

|Aspect|TFTP|FTP|SCP / SFTP|
|---|---|---|---|
|Transport|UDP|TCP|TCP|
|Well-known port|UDP 69|TCP 21 control|SSH, TCP 22|
|Authentication|None|Yes|Yes|
|Encryption|None|None with traditional FTP|Yes|
|Reliability|TFTP ACK/retransmission|TCP|TCP/SSH|
|Directory operations|No TFTP directory listing|Yes|Yes|
|Complexity|Very low|Moderate|Higher|
|Security|Weak|Weak/plaintext|Strong|
|Typical use|Simple device transfers|General file transfer|Secure file transfer|

### Key distinction

- **TFTP:** simple, lightweight, unauthenticated.
    
- **FTP:** authenticated but traditional FTP sends credentials/data without encryption.
    
- **SCP/SFTP:** secure file transfer using SSH.
    

> **Exam answer:** Use **SCP/SFTP rather than TFTP** when confidentiality and authentication are required, subject to platform support.

## 5. Cisco Router/Switch Usage

TFTP can be used to transfer Cisco IOS images and configuration files.

### Copy an IOS image from TFTP to flash

```text
copy tftp://10.0.0.5/ios.bin flash:
```

### Copy a configuration file from TFTP to startup configuration

```text
copy tftp://10.0.0.5/config.txt startup-config
```

### Copy a file from flash to a TFTP server

```text
copy flash:ios.bin tftp://10.0.0.5/
```

### Traditional IOS workflow

```text
TFTP Server
     |
     |  IOS image / configuration
     |
     v
Cisco Router/Switch
     |
     +--> flash:
     +--> running-config
     +--> startup-config
```

TFTP is particularly useful in **lab environments, device provisioning, image transfers, and configuration backup/restore workflows**.

## 6. TFTP and Cisco IP Phones

TFTP is historically important in Cisco voice environments.

**DHCP Option 150** can provide Cisco IP phones with the address of a **TFTP server**.

Typical flow:

```text
IP Phone
   |
   | DHCP
   v
DHCP Server
   |
   | Option 150
   v
TFTP Server
   |
   | Phone configuration / firmware
   v
IP Phone
```

### Exam point

**DHCP Option 150 → TFTP server address for Cisco IP phones**

Do not confuse:

- **Option 150** → commonly used for Cisco IP-phone TFTP server information
    
- **Option 66** → commonly used to provide a TFTP/boot-server hostname or address in generic DHCP environments

## 7. Security Risks

TFTP has significant security limitations.

|Risk|Explanation|Mitigation|
|---|---|---|
|No authentication|Server does not authenticate users through TFTP|Restrict access|
|No encryption|Files/data are transferred in cleartext|Use SCP/SFTP|
|Unauthorized file access|Exposure depends heavily on server configuration|ACLs/firewall|
|File modification|Untrusted users may attempt writes if permitted|Restrict WRQ/write access|
|DoS|TFTP service can be abused or overwhelmed|Filtering/rate limiting|
|Credential exposure|TFTP itself does not protect credentials because it has no authentication mechanism|Use secure protocols|

### Security principle

```text
Trusted management network
        |
        +---- TFTP ----> simple but insecure
        |
        +---- SCP -----> authenticated + encrypted
```

Use TFTP only where its limitations are acceptable and restrict access with **ACLs, firewalls, management-plane controls, or an isolated/OOB management network**.

## 8. Troubleshooting

|Symptom|Possible cause|Check|
|---|---|---|
|No transfer|UDP traffic blocked|ACL/firewall|
|RRQ/WRQ fails|Server unavailable or incorrect address|Connectivity/server|
|Transfer times out|Packet loss, filtering, or server problem|Ping, ACLs, packet capture|
|Transfer stops midway|Loss/filtering/MTU or server issue|Logs and packet capture|
|Permission denied|Server-side file permissions|TFTP server configuration|
|Wrong phone configuration|Incorrect DHCP Option 150|DHCP configuration|
|Phone cannot obtain configuration|TFTP server unreachable|IP connectivity and TFTP service|
|File transfer fails after request|Dynamic transfer-port traffic blocked|Firewall/ACL|

### Useful Cisco checks

```text
show ip interface brief
show ip route
ping 10.0.0.5
```

For packet-level troubleshooting, use a packet capture where available.

> **Note:** TFTP-specific debug commands vary by Cisco IOS/platform/release, so do not memorize `debug tftp` as a universally available command.

## 9. Exam Traps

### Trap 1 — TCP vs UDP

**TFTP = UDP**

```text
TFTP → UDP 69
FTP  → TCP 21 control
SSH  → TCP 22
```

---

### Trap 2 — TFTP is not FTP

TFTP is intentionally much simpler:

```text
TFTP
├── UDP
├── No authentication
├── No encryption
├── No directory listing
└── Simple file transfer
```

---

### Trap 3 — UDP does not mean unreliable TFTP

UDP itself does not provide reliability, but **TFTP implements acknowledgments and retransmissions**.

Classic operation:

```text
DATA → ACK → DATA → ACK
```

---

### Trap 4 — UDP 69 is not necessarily used for the entire transfer

**UDP 69** is the well-known port used for the initial TFTP request.

The subsequent transfer normally uses **dynamically selected UDP transfer ports**.

---

### Trap 5 — 512-byte block size

Classic TFTP uses **512-byte DATA blocks**, but the block size can be **negotiated using TFTP options**.

Therefore:

> **512 bytes = classic/default value, not an absolute maximum.**

---

### Trap 6 — End of file

A DATA packet smaller than the negotiated block size indicates the final block.

If the file size is an exact multiple of the block size, TFTP sends a **zero-length DATA packet** to terminate the transfer.

---

### Trap 7 — Option 150

For Cisco IP phones:

```text
DHCP Option 150
        ↓
TFTP Server Address
        ↓
Phone configuration / firmware
```
