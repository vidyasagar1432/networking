# NTP (Network Time Protocol)

> **Level 16 · Network Services** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

**NTP (Network Time Protocol)** synchronizes device clocks across a network.

NTP normally uses:

- **UDP 123**
    
- A hierarchical **stratum** system
    
- NTP servers, clients, and peers
    
- Optional authentication
    
- Polling and clock-selection algorithms
    

Accurate time is important for:

- Syslog timestamps
    
- Troubleshooting
    
- Security events
    
- Authentication/certificates
    
- Network monitoring
    
- Forensics
    
- Correlating events across multiple devices
    

Cisco IOS devices can operate as NTP clients, servers, or peers.

---

# 2. Stratum Hierarchy

NTP uses **stratum** to describe the distance from a reference clock.

|Stratum|Meaning|
|--:|---|
|**0**|Reference clock such as atomic clock, GPS, or other precise source|
|**1**|NTP server directly synchronized to a stratum-0 reference clock|
|**2**|Synchronizes from a stratum-1 source|
|**3**|Synchronizes from a stratum-2 source|
|**4+**|Continues down the hierarchy|
|**16**|Unsynchronized/unusable NTP source|

Conceptually:

```text
Stratum 0
   |
   v
Stratum 1
   |
   v
Stratum 2
   |
   v
Stratum 3
   |
   v
Stratum 4
```

### Important rule

A device normally becomes **one stratum higher than its selected synchronization  
source**.

Example:

```text
R1 → Stratum 2 server

R1 becomes approximately:
Stratum 3
```

### Key exam point

> **Lower stratum is generally preferred, but stratum alone does not determine  
> the complete NTP selection decision.**

NTP also considers factors such as clock quality, synchronization distance,  
reachability, and other selection criteria.

---

# 3. Stratum 0 vs Stratum 1

A common exam trap:

### Stratum 0

A stratum-0 device is the actual reference clock.

Examples:

- Atomic clock
    
- GPS receiver
    
- Other highly accurate reference source
    

It is **not itself an ordinary NTP server**.

### Stratum 1

A stratum-1 NTP server is directly synchronized to a stratum-0 reference.

```text
GPS / Atomic Clock
       |
       | reference
       v
Stratum-1 NTP Server
       |
       v
Stratum-2 Clients
```

# 4. NTP Operating Modes

## 4.1 Client / Server

The most common model:

```text
NTP Client
    |
    | UDP 123
    v
NTP Server
```

Cisco configuration:

```cisco
ntp server 10.0.0.5
```

The Cisco device polls the configured NTP server and attempts to synchronize  
its clock.

---

## 4.2 Peer

Two NTP devices can be configured as peers:

```cisco
ntp peer 10.0.0.6
```

Peers can synchronize with each other and provide redundancy.

Important:

> **NTP peers do not mean that both devices necessarily have the same  
> stratum.** NTP still uses stratum and other selection criteria when  
> determining the preferred clock.

---

## 4.3 NTP Master

Cisco IOS can provide NTP service using its local clock:

```cisco
ntp master 2
```

This tells the router to act as an NTP master at the configured stratum.

Conceptually:

```text
Router local clock
       |
       v
NTP Master
       |
       v
NTP Clients
```

### Important

An `ntp master` device is **not equivalent to a router synchronized to a  
real external reference clock**.

It is generally used in:

- Labs
    
- Isolated networks
    
- Networks without an external time source
    
- Backup/fallback situations
    

For production, an externally synchronized source is preferable.

---

# 5. NTP Broadcast

Cisco devices can also use broadcast-based NTP.

Broadcast mode allows a server to send NTP updates to clients without each  
client continuously polling the server in the normal unicast model.

Conceptually:

```text
             +--> Client
             |
NTP Server --+--> Client
             |
             +--> Client
```

Broadcast NTP can reduce polling overhead in some environments.

> Broadcast is a distribution method; it should not simply be described as  
> "less accurate." Accuracy depends on the overall NTP implementation and  
> synchronization conditions.

### Configure an NTP server


Multiple servers can be configured:

```cisco
ntp server 10.0.0.5
ntp server 10.0.0.6
ntp server 10.0.0.7
```

Multiple sources provide redundancy.


```cisco
ntp master 2
```

This makes the router provide NTP using its local clock at the configured

# 7. NTP Source Interface

Use:

```cisco
ntp source Loopback0
```

This specifies the interface/IP address used as the source of NTP packets.

Example:

```cisco
interface Loopback0
 ip address 10.10.10.1 255.255.255.255

ntp source Loopback0
ntp server 10.10.10.5
```

### Why use a loopback?

A loopback provides a stable source address that normally remains available  
as long as the router has working Layer 3 connectivity.

It can also simplify:

- ACLs
    
- NTP server access control
    
- Routing
    
- Device identification
    

### Important exam point

> `ntp source` chooses the source address/interface. It does **not** itself  
> bypass ACLs or guarantee reachability.

---

# 8. NTP Authentication

NTP authentication helps prevent unauthorized or spoofed NTP information  
from being accepted.

Cisco configuration commonly involves:

```cisco
ntp authentication-key 1 md5 MySecretKey
ntp trusted-key 1
ntp authenticate
```

### Components

|Command|Purpose|
|---|---|
|`ntp authentication-key`|Creates an authentication key|
|`ntp trusted-key`|Marks the key as trusted|
|`ntp authenticate`|Enables NTP authentication processing|

A configured NTP server/peer must also be configured appropriately to use  
the authentication mechanism.

Example:

```cisco
ntp authentication-key 1 md5 MySecretKey
ntp trusted-key 1
ntp authenticate

ntp server 10.0.0.5 key 1
```

The exact authentication syntax/features can vary by IOS/IOS XE release,  
so verify platform-specific syntax when configuring a production device.

---

# 9. NTP Polling

NTP clients do not normally send requests continuously every second.

They poll their configured sources at intervals determined by the NTP  
implementation and synchronization state.

The polling interval can change as NTP adjusts to the quality and stability  
of the time source.

This helps reduce unnecessary NTP traffic while maintaining synchronization.

---

# 10. NTP Selection

When multiple NTP sources are configured, the device evaluates the available  
candidates.

Factors can include:

- Stratum
    
- Synchronization distance
    
- Reachability
    
- Clock quality
    
- Delay
    
- Offset
    
- Jitter
    
- Other NTP selection criteria
    

Therefore:

> **Do not reduce NTP selection to "lowest stratum always wins."**

Lower stratum is generally desirable, but the complete NTP selection process  
uses more information.

---

# 11. NTP Reachability

NTP must be able to communicate between the client and server/peer.

NTP uses **UDP 123**.

Basic path:

```text
Client
  |
  | UDP/123
  v
NTP Server
```

Check:

- IP connectivity
    
- Routing
    
- ACLs
    
- Firewalls
    
- UDP 123
    
- NTP configuration
    
- Authentication

# 12. Cisco NTP Verification

### Show NTP status

```cisco
show ntp status
```

This provides information such as:

- Synchronization state
    
- NTP stratum
    
- Reference clock
    
- Reference ID
    
- Clock status
    

A synchronized router should indicate that the clock is synchronized.

---

## 12.1 Show NTP Associations

```cisco
show ntp associations
```

This shows configured and learned NTP peers/servers and their status.

Typical symbols include:

```text
*   Current system peer
+   Candidate / acceptable peer
-   Other candidate
```

The exact symbols and output can vary by IOS/IOS XE version.

### Important

The `*` entry is especially important:

> `*` identifies the NTP peer currently selected as the system peer.

---

## 12.2 Detailed Associations

```cisco
show ntp associations detail
```

Useful for deeper troubleshooting.

# 14. NTP Troubleshooting

## Problem: Device is unsynchronized

Check:

```cisco
show ntp status
show ntp associations
```

Possible causes:

- NTP server unreachable
    
- UDP 123 blocked
    
- Incorrect NTP server address
    
- Routing problem
    
- ACL/firewall
    
- Authentication mismatch
    
- NTP source problem
    
- Server itself unsynchronized
    

---

## Problem: NTP server is unreachable

Check:

```text
IP connectivity
Routing
ACL
Firewall
UDP 123
```

Test basic connectivity:

```cisco
ping 10.0.0.5
```

Remember:

> Successful ping does not prove that UDP 123 is permitted.

---

## Problem: Authentication failure

Check that both sides agree on:

- Key ID
    
- Key value
    
- Authentication configuration
    
- Trusted-key configuration
    

Example:

```cisco
ntp authentication-key 1 md5 MySecretKey
ntp trusted-key 1
ntp authenticate
```

---

## Problem: Wrong source address

If the NTP server expects a specific source address, configure:

```cisco
ntp source Loopback0
```

Then verify that routing and ACLs permit the selected source address.

---

## Problem: NTP source itself is bad

If an `ntp master` router is using only its local clock, its time may be  
inaccurate because it lacks a reliable external reference.

For production networks, prefer:

```text
GPS / Atomic / Reliable external source
              |
              v
       Stratum-1 Server
              |
              v
       Enterprise NTP
              |
              v
        Network Devices
```

# 15. NTP Master vs NTP Server

This is a high-value CCNP distinction.

|Command|Meaning|
|---|---|
|`ntp server X`|Synchronize this device to another NTP server|
|`ntp peer X`|Establish an NTP peer relationship|
|`ntp master N`|Make this device provide NTP using its local clock at stratum N|

Example:

```cisco
ntp server 10.0.0.5
```

means:

```text
"I want my clock synchronized from 10.0.0.5."
```

Whereas:

```cisco
ntp master 2
```

means:

```text
"I can provide NTP using my local clock as a stratum-2 source."
```

---

# 16. NTP and Routing Protocols

NTP is important for operational visibility, but do not confuse NTP with  
routing-protocol timers.

OSPF, BGP, EIGRP, and other protocols maintain their own protocol timers.

NTP does **not** make those timers function correctly.

Instead, synchronized time is important for:

- Event timestamps
    
- Syslog
    
- Troubleshooting
    
- Security monitoring
    
- Authentication systems
    
- Certificates
    
- Incident investigation
    
- Correlating events between devices
    

---

# 17. NTP vs PTP

For ENCOR-level awareness:

|Feature|NTP|PTP|
|---|---|---|
|Purpose|Network-wide time synchronization|High-precision time synchronization|
|Protocol|UDP 123|IEEE 1588|
|Typical precision|Millisecond-level depending on network/environment|Can achieve much higher precision|
|Common use|Enterprise network devices, servers|Industrial, telecom, financial, specialized systems|

NTP is generally sufficient for normal enterprise network-management  
requirements.

---

# 18. NTP Security

Potential NTP security issues include:

- NTP spoofing
    
- Unauthorized time sources
    
- Malicious time manipulation
    
- NTP amplification abuse
    
- Unauthorized NTP server access
    

Security practices include:

- Use trusted NTP sources
    
- Restrict NTP access with ACLs/firewalls
    
- Use NTP authentication where appropriate
    
- Disable unnecessary NTP services
    
- Use reliable upstream time sources

# 19. Exam Traps

- **NTP uses UDP 123.**
    
- Stratum **0** = reference clock.
    
- Stratum **1** = server directly synchronized to a stratum-0 reference.
    
- A synchronized device normally has a stratum **one greater than its selected source**.
    
- **Stratum 16** indicates an unsynchronized/unusable source.
    
- Lower stratum is generally preferred, but **stratum alone does not determine  
    every selection decision**.
    
- `ntp server X` = synchronize with an NTP server.
    
- `ntp peer X` = configure an NTP peer relationship.
    
- `ntp master N` = provide NTP using the local clock at configured stratum.
    
- `ntp source Loopback0` = use Loopback0's address as the NTP packet source.
    
- `ntp authentication-key` creates an authentication key.
    
- `ntp trusted-key` identifies trusted authentication keys.
    
- `ntp authenticate` enables NTP authentication processing.
    
- Authentication must be correctly configured on both sides when used.
    
- `show ntp status` = synchronization status and stratum.
    
- `show ntp associations` = NTP peers/servers and selection state.
    
- `show clock` = current device time.
    
- `*` in NTP associations normally identifies the selected system peer.
    
- `ntp max-associations` is **not a solution for clock drift**.
    
- Successful ICMP ping does **not** prove UDP 123 works.
    
- NTP is important for timestamps and operational/security correlation, not  
    for making OSPF/BGP timers function.
