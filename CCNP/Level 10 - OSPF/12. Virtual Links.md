# OSPF Virtual Link

> **Level 10 · OSPF** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

A **virtual link** is a logical OSPF tunnel that **connects an area to the backbone**
(Area 0) through a transit area — or **patches a discontiguous Area 0**. It's a
**last-resort** fix, not a design tool: it masks a broken topology, adds SPF/failure
complexity, and has specific constraints. The exam wants to know *when* it's legal and
*when it isn't*.

---

## 2. Core Concepts

### 2.1 The two use cases (memorize)

| Case | Situation |
|------|-----------|
| **Area without backbone access** | an area physically isolated from Area 0 → virtual link through a transit area to Area 0 |
| **Discontiguous Area 0** | backbone split into two pieces → virtual link stitches them together |

- In both cases the virtual link is configured **on the ABRs at both ends**.

### 2.2 Transit area rules

- The transit area **must not be a stub / totally stubby / NSSA** — no external-filtered
  areas can carry the virtual link.
- Both endpoints are **ABRs**; the transit area must be in both routers' LSDB.
- The virtual link is **area 0 traffic** riding over the transit area's network.

### 2.3 Configuration

```text
! On BOTH endpoint ABRs:
router ospf 1
 area 2 virtual-link 1.1.1.1        ! 1.1.1.1 = other ABR's router-id
```

| Side | Router-ID of the peer |
|------|-----------------------|
| ABR-A (in area 2) | ABR-B's RID |
| ABR-B (in area 2) | ABR-A's RID |

- Uses **router-ids**, not interface IPs — stable identity matters (note 03).

### 2.4 Cost & routing through a virtual link

- The virtual link's cost = the **cost of the transit-area path** between the two ABRs.
- Routers in the transit area see the path normally; the two ABRs treat it as a backbone
  adjacency (`show ip ospf virtual-links`).

### 2.5 Constraints checklist (exam list)

1. Cannot pass through **stub / totally stubby / NSSA** areas.
2. **Area 0 itself cannot be configured as the transit area.**
3. Not a substitute for correct design — use only to recover topology.
4. Both endpoints must be **ABRs** (interface in transit area + area 0 reachable).
5. Area 0 cannot be a stub area at all.

## 3. Configuration / Commands

```text
router ospf 1
 area 2 virtual-link 2.2.2.2
 area 2 virtual-link 2.2.2.2 authentication message-digest
 area 2 virtual-link 2.2.2.2 message-digest-key 1 md5 secret

show ip ospf virtual-links          ! state: Up / DOWN
show ip ospf neighbor
show ip ospf | include Virtual
```

## 4. Troubleshooting & common failures

| Symptom | Likely cause | Check |
|---------|--------------|-------|
| Virtual link DOWN | no adjacency in transit area / RID wrong | `show ip ospf virtual-links` |
| Won't form through area | transit is stub/NSSA/totally-stubby | change transit area type |
| Flaps after renumber | RID changed (note 03) | stabilize RIDs |
| Cost wrong | transit path changed | verify via `show ip route` |
| Auth mismatch | key mismatch on link | verify keys both ABRs |

---

## 5. Exam Traps

- **Virtual link rides a transit area that must be standard** (not stub/NSSA/totally).
- **Configured on ABRs using peer RIDs.**
- **It connects an isolated area to Area 0 or patches discontiguous backbone.**
- **Area 0 cannot be the transit area.**
- It's a **repair mechanism** — design answers should avoid it unless asked to fix a break.
- State check command: `show ip ospf virtual-links`.
