# OSPF Authentication

> **Level 10 · OSPF** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

OSPF authentication validates the **origin of Hello/LSA packets** to stop rogue routers or
injected LSAs from poisoning the domain. OSPFv2 supports **null (none), plaintext, and
MD5/SHA message-digest** authentication carried in the header. OSPFv3 has **no OSPF-level
auth** — it relies on **IPv6 AH/ESP (IPsec)**. Adjacencies fail if the auth method or key
mismatches.

---

## 2. Core Concepts

### 2.1 OSPFv2 authentication types (memorize)

| Type | Value | Security | Notes |
|------|-------|----------|-------|
| Null | 0 | none | default |
| Plaintext (Simple) | 1 | weak, sent in clear | avoids misconfig, not security |
| MD5 / HMAC-SHA | 2 | strong digest | recommended; key not in packet |
| Cryptographic (SHA-256+) | 2+ | strongest | newer IOS/XE |

- **Type 2 (message-digest)** is the correct security answer on the exam.

### 2.2 Configuration levels

| Scope | Command |
|-------|---------|
| Per-interface | `ip ospf authentication message-digest` + key |
| Per-area (all interfaces) | `area N authentication message-digest` |
| Per-virtual-link | `area N virtual-link X authentication message-digest` |

```text
interface Gi0/1
 ip ospf authentication message-digest
 ip ospf message-digest-key 1 md5 SecretKey123

router ospf 1
 area 0 authentication message-digest    ! all area-0 interfaces
```

### 2.3 The MD5 digest process (conceptual)

1. Each OSPF packet gets a **key ID** + **cryptographic sequence number** in its header.
2. Digest computed over the packet with the shared key.
3. Receiver verifies digest + sequence, rejects replay/reforged packets.

### 2.4 OSPFv3 (the difference, exam favorite)

| Version | Native auth | Real protection |
|---------|-------------|-----------------|
| OSPFv2 | MD5/SHA in header | yes (in-band) |
| OSPFv3 | none | IPv6 AH / ESP / IPsec |

- OSPFv3 "authentication" answers point to **IPsec/AH**, not OSPF keys.

### 2.5 Failure behavior

- Auth mismatch, neighbor **stuck in INIT** (hellos dropped), never reaches 2-Way.
- Key/type mismatch on both ends, silence, no adjacency, logged errors.
- Rotate keys via **key ID + sequence number** (multiple keys valid during transition).

## 3. Configuration / Commands

```text
! Interface mode (v2)
interface Gi0/1
 ip ospf authentication message-digest
 ip ospf message-digest-key 1 md5 SecretKey123

! Area mode
router ospf 1
 area 0 authentication message-digest

! Virtual link
router ospf 1
 area 2 virtual-link 2.2.2.2 authentication message-digest
 area 2 virtual-link 2.2.2.2 message-digest-key 1 md5 SecretKey123

show ip ospf interface Gi0/1        ! auth type shown
show ip ospf neighbor
show ip ospf | include Authentication
```

## 4. Troubleshooting & common failures

| Symptom | Likely cause | Check |
|---------|--------------|-------|
| Neighbor stuck INIT | auth mismatch / key wrong | `show ip ospf interface` auth |
| Key not used | key ID mismatch / type (1 vs 2) | verify key-id + type both ends |
| Flap on key rotation | removed old key before adding new | add new key first, keep both briefly |
| OSPFv3 auth not working | using v2-style keys | use IPsec/AH |
| Logs "wrong authentication" | type or key mismatch | compare key + type |

---

## 5. Exam Traps

- **Type 2 (message-digest / MD5) is the strong auth**; plaintext Type 1 is legacy.
- **Auth mismatch = stuck in INIT** — the neighbor-state clue.
- **Configured per interface or per area**; area applies to all its interfaces.
- **Virtual links need their own auth config** on the `virtual-link` line.
- **OSPFv3 has no native auth** — IPv6 AH/ESP/IPsec.
- Key rotation uses **sequence number + key ID**, multiple keys allowed.
