# BPDU (Bridge Protocol Data Unit)

> **Level 08 · STP** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

A **Bridge Protocol Data Unit (BPDU)** is an STP control message exchanged between
switches to build and maintain the Layer 2 spanning tree.

BPDUs carry information such as:

- Root Bridge ID
- Root Path Cost
- Sender Bridge ID
- Sender Port ID
- STP timers
- Topology-change information
- RSTP role/state and proposal/agreement information

STP uses this information to:

```text
Elect the Root Bridge
        ↓
Select Root Ports
        ↓
Select Designated Ports
        ↓
Place redundant paths into a non-forwarding role/state
        ↓
Maintain a loop-free Layer 2 topology
```

> **CCNP Mental Model:**  
> **BPDUs are the information STP switches exchange to decide who is root, which  
> paths are preferred, and which ports should forward or block/discard.**

BPDUs are **control-plane traffic**, not normal user-data traffic.

---

# 2. Core Concepts

## 2.1 BPDU Types

There are two important BPDU categories to understand for CCNP:

|BPDU|Protocol|Purpose|
|---|---|---|
|**Configuration BPDU**|Classic 802.1D STP|Root election and STP topology information|
|**RSTP BPDU**|802.1w / Rapid PVST+|Rapid STP operation, role/state information, proposal/agreement|
|**TCN BPDU**|Classic 802.1D STP|Notify the root that a topology change occurred|

### Important distinction

A **TCN BPDU is not the same thing as a Configuration BPDU**.

Classic STP uses:

```text
Configuration BPDU
        +
TCN BPDU
```

RSTP integrates topology-change signaling into its normal BPDUs and does not use  
the separate 802.1D TCN mechanism in the same way.

---

# 3. BPDU Contents

A BPDU contains information that allows switches to compare STP paths.

Important fields include:

```text
Protocol Identifier
Protocol Version
BPDU Type
Flags
Root Bridge ID
Root Path Cost
Sender Bridge ID
Sender Port ID
Message Age
Max Age
Hello Time
Forward Delay
```

---

## 3.1 Root Bridge ID

The **Root Bridge ID** identifies the bridge currently being advertised as the root.

Conceptually:

```text
Root Bridge ID
│
├── Bridge Priority
├── Extended System ID
└── MAC Address
```

The switch with the **lowest Bridge ID** becomes the root.

```text
Lowest Bridge ID
        ↓
Root Bridge
```

---

## 3.2 Root Path Cost

**Root Path Cost** represents the total STP path cost from the sending switch toward  
the Root Bridge.

Example:

```text
SW1 (Root)
   │
   │ cost 4
   │
  SW2
   │
   │ cost 4
   │
  SW3
```

SW3 advertises:

```text
Root Path Cost = 8
```

because:

```text
4 + 4 = 8
```

A lower Root Path Cost is preferred when comparing paths to the same root.

---

## 3.3 Sender Bridge ID

The **Sender Bridge ID** identifies the switch that transmitted the BPDU.

It becomes important when switches compare BPDUs that already advertise the same:

```text
Root Bridge ID
+
Root Path Cost
```

The lower Sender Bridge ID is preferred.

---

## 3.4 Sender Port ID

The **Sender Port ID** identifies the port from which the BPDU was transmitted.

It can be used as a tie-breaker when the earlier BPDU comparison criteria are equal.

Conceptually:

```text
Sender Port ID
│
├── Port Priority
└── Port Number
```

Lower Port ID wins the relevant tie-break.

---

## 3.5 Message Age

**Message Age** indicates how much time has elapsed since the root originated the  
information represented by the BPDU.

As the BPDU moves through the topology, Message Age increases.

Conceptually:

```text
Root
 │
 │ Message Age ≈ 0
 ↓
SW2
 │
 │ Message Age increases
 ↓
SW3
```

A BPDU is considered stale when the relevant information exceeds the configured  
**Max Age**.

---

## 3.6 STP Timers

Important classic STP timer values are:

|Timer|Default|Purpose|
|---|--:|---|
|**Hello Time**|2 seconds|Interval between root BPDUs|
|**Max Age**|20 seconds|BPDU information aging|
|**Forward Delay**|15 seconds|Listening/Learning duration|

Remember:

```text
Hello      = 2 s
Max Age    = 20 s
Forward    = 15 s
```

> Do not interpret these as a universal "50-second convergence" formula. Their  
> functions are different, and actual convergence depends on the topology and  
> failure condition.

---

# 4. RSTP BPDU

RSTP uses a **Version 2 BPDU**.

RSTP BPDUs carry additional information through the **Flags** field, including:

```text
Topology Change
Topology Change Acknowledgment
Agreement
Forwarding
Learning
Port Role
Proposal
```

Conceptually:

```text
RSTP BPDU
│
├── Root information
├── Path cost
├── Sender information
├── Timers
└── Flags
      ├── Proposal
      ├── Agreement
      ├── Role
      ├── Learning
      ├── Forwarding
      └── Topology Change
```

This allows RSTP to use explicit **proposal/agreement** and role/state information  
for rapid convergence.

> **Correction:** RSTP is not simply "classic STP plus a flag byte." RSTP changes  
> the BPDU format/version and the STP operating model, including rapid role  
> transitions and proposal/agreement.

---

# 5. How BPDUs Flow

The Root Bridge originates the spanning-tree information.

Conceptually:

```text
                 ROOT
                  SW1
                  │
          Configuration BPDU
                  ↓
                 SW2
                  │
          Configuration BPDU
                  ↓
                 SW3
```

The information propagates outward through the spanning-tree topology.

### Important terminology

It is better to think of non-root switches as **transmitting/propagating their  
current STP information** rather than simply saying they "relay the exact same  
BPDU."

A downstream switch can transmit a BPDU containing the root information it has  
learned, with its own sender information.

---

# 6. BPDU Transmission and Non-Forwarding Ports

A common exam trap is:

> "A blocked port does not receive or process BPDUs."

That is **wrong**.

A non-forwarding STP port can still participate in STP control processing.

For classic STP:

```text
Forwarding port
    ↓
Transmit/receive BPDUs

Blocking port
    ↓
Does not forward user data
    ↓
Still receives/processes BPDUs
```

This is essential because STP must continue monitoring the topology even when a  
port is not forwarding user traffic.

> Exact BPDU transmission behavior depends on the STP role/protocol state. Do not  
> reduce it to "all blocked ports transmit BPDUs."

---

# 7. BPDU Processing and STP Decisions

A switch compares received STP information to determine the superior path.

For a given STP instance, the conceptual comparison is:

```text
1. Lowest Root Bridge ID
        ↓
2. Lowest Root Path Cost
        ↓
3. Lowest Sender Bridge ID
        ↓
4. Lowest Sender Port ID
        ↓
5. Local Port ID when required
```

However, the **context matters**.

### Root election

Primarily determined by:

```text
Lowest Root/Bridge ID
```

### Root Port selection

Once the root is known, the switch compares candidate paths using:

```text
Lowest Root Path Cost
        ↓
Sender Bridge ID
        ↓
Sender Port ID
        ↓
Local Port ID if required
```

### Designated Port selection

The switch on a segment advertising the superior BPDU becomes the designated  
bridge/port for that segment.

> **Exam tip:** Do not memorize the comparison as one universal list without  
> considering whether you are solving **root election**, **Root Port selection**,  
> or **Designated Port selection**.

---

# 8. BPDU Topology Change Signaling

## 8.1 Classic 802.1D STP

Classic STP uses a separate **Topology Change Notification (TCN) BPDU**.

A switch detecting a topology change can send:

```text
TCN BPDU
   ↓
Upstream toward Root
   ↓
Root receives TCN
   ↓
Root sets TC flag in Configuration BPDUs
   ↓
Switches temporarily reduce MAC aging
```

The classic topology-change process therefore involves:

```text
TCN BPDU
+
Configuration BPDU with TC indication
```

---

## 8.2 RSTP

RSTP integrates topology-change signaling into its normal BPDUs.

Therefore:

```text
Classic STP
    ↓
Separate TCN mechanism

RSTP
    ↓
Topology Change flag/mechanism in normal RSTP BPDUs
```

This is one reason RSTP has a simpler and faster topology-change process.

---

# 9. Topology Change and MAC Aging

When a topology change occurs, switches need to quickly remove stale MAC entries  
that may now point toward the wrong path.

Classic STP can temporarily reduce the effective MAC aging time during the  
topology-change process.

A commonly taught Cisco value is:

```text
Forward Delay = 15 seconds
```

so the temporary aging behavior is commonly associated with approximately  
**15 seconds**.

> **Exam focus:** A topology change causes switches to age MAC entries more  
> aggressively so traffic can relearn the correct path.

Do not confuse:

```text
Forward Delay
```

with:

```text
MAC aging time
```

They are different concepts even though classic STP topology-change processing  
uses the Forward Delay value for temporary MAC aging behavior.

---

# 10. BPDU and VLANs

The relationship between BPDUs and VLANs depends on the STP implementation.

### PVST+

Cisco PVST+ maintains a separate spanning-tree instance per VLAN.

On an 802.1Q trunk:

```text
Native VLAN BPDU
    ↓
Normally untagged

Non-native VLAN BPDUs
    ↓
802.1Q tagged
```

This allows PVST+ to carry the different VLAN-specific STP information across a  
trunk.

### Rapid PVST+

Rapid PVST+ similarly runs a separate RSTP instance per VLAN.

### MST

MST reduces the number of spanning-tree instances by mapping multiple VLANs to  
MST instances.

```text
Many VLANs
    ↓
MST VLAN mapping
    ↓
Few MST instances
    ↓
MST BPDUs
```

> **Exam point:** Do not assume every STP mode sends one independent BPDU per VLAN  
> in the same way. The BPDU behavior depends on PVST+/Rapid PVST+, MST, and the  
> trunk/region context.

---

# 11. BPDU Security and Protection

Cisco provides several features that react to unexpected or missing BPDUs.

|Feature|Trigger|Typical Result|
|---|---|---|
|**BPDU Guard**|BPDU received on a PortFast/edge port|Port is typically errdisabled|
|**BPDU Filter**|Configured to suppress/ignore BPDUs|Can prevent normal STP participation; risky|
|**Root Guard**|Superior BPDU received|Port becomes root-inconsistent|
|**Loop Guard**|Expected BPDUs stop arriving|Port becomes loop-inconsistent rather than incorrectly forwarding|

---

# 12. BPDU Guard

**BPDU Guard** protects an edge/PortFast port from receiving BPDUs.

Typical design:

```text
             Enterprise Switch
                    │
                    │
                PortFast
                    │
                  PC
```

If another switch is connected and sends a BPDU:

```text
Unexpected BPDU
       ↓
BPDU Guard
       ↓
Port protection
       ↓
Err-disabled
```

Verification:

```text
show interfaces status
show errdisable recovery
show logging
```

> **Mental model:**  
> **PortFast says "this is an edge port."**  
> **BPDU Guard says "if a BPDU appears here, shut it down."**

---

# 13. BPDU Filter

**BPDU Filter** suppresses BPDU transmission/reception behavior depending on  
where and how it is configured.

It can effectively prevent a port from participating normally in STP.

Because this can hide the presence of a Layer 2 loop, BPDU Filter must be used  
carefully.

> **Exam trap:** BPDU Filter is **not** a safer version of BPDU Guard.

Remember:

```text
BPDU Guard
    ↓
Unexpected BPDU
    ↓
Protect by shutting/errdisabling the port

BPDU Filter
    ↓
Suppress/filter BPDUs
    ↓
Can hide STP information
    ↓
Potentially dangerous
```

---

# 14. Root Guard

**Root Guard** prevents a port from becoming the path toward an unexpected  
superior root.

If the port receives a **superior BPDU**:

```text
Superior BPDU
      ↓
Root Guard
      ↓
Root-inconsistent
      ↓
Port stops forwarding
```

Verification:

```text
show spanning-tree inconsistentports
```

Typical use:

```text
Core/Distribution
       │
       │
   Root Guard
       │
       ↓
Access/downstream switch
```

---

# 15. Loop Guard

**Loop Guard** protects against a situation where a port that should remain  
non-designated stops receiving BPDUs and incorrectly transitions toward  
forwarding.

Example:

```text
Expected BPDUs
      ↓
BPDUs suddenly stop
      ↓
Possible unidirectional failure
      ↓
Loop Guard
      ↓
Loop-inconsistent
```

This helps prevent a Layer 2 loop caused by loss of BPDU reception.

Verification:

```text
show spanning-tree inconsistentports
```

> **Mental model:**  
> **Root Guard = protects the root placement.**  
> **Loop Guard = protects against unexpected forwarding when BPDUs disappear.**

---

# 16. BPDU Guard vs Root Guard vs Loop Guard

```text
BPDU GUARD
│
└── Unexpected BPDU on edge port
      ↓
   Err-disabled


ROOT GUARD
│
└── Superior BPDU
      ↓
   Root-inconsistent


LOOP GUARD
│
└── Expected BPDUs disappear
      ↓
   Loop-inconsistent


BPDU FILTER
│
└── Suppress/filter BPDUs
      ↓
   Risk of hiding STP information
```

# 18. Troubleshooting

|Symptom|Likely Cause|Check|
|---|---|---|
|Unexpected Root Bridge|Superior Bridge ID is being advertised|Check Root ID and STP topology|
|Port becomes err-disabled after switch is connected|BPDU Guard|`show interfaces status`, `show logging`|
|Port becomes root-inconsistent|Root Guard received superior BPDU|`show spanning-tree inconsistentports`|
|Port becomes loop-inconsistent|Loop Guard detected missing expected BPDUs|`show spanning-tree inconsistentports`|
|PVST+ trunk STP problem|VLAN/trunk/native-VLAN issue|`show interfaces trunk`|
|STP path is not what expected|Root Path Cost / Bridge ID / Port ID|`show spanning-tree vlan N`|
|MAC addresses appear to move/flap|Possible Layer 2 loop or topology instability|Check STP, MAC table and topology|
|STP topology changes frequently|Link instability, endpoint flaps or topology changes|Check logs, interfaces and TCN/topology-change information|

# 19. Reading a BPDU — CCNP Method

When troubleshooting an STP decision, think:

```text
BPDU
│
├── Who does it say is Root?
│       ↓
│   Root Bridge ID
│
├── What is the cost to the Root?
│       ↓
│   Root Path Cost
│
├── Who sent it?
│       ↓
│   Sender Bridge ID
│
├── Which port sent it?
│       ↓
│   Sender Port ID
│
└── How old is the information?
        ↓
    Message Age / Max Age
```

Then ask:

```text
Is this BPDU superior or inferior
to the BPDU currently known?
```

That is the key question behind many STP troubleshooting problems.

# 21. BPDU Fields and What They Help Determine

|Field|Purpose|
|---|---|
|**Root Bridge ID**|Identifies the advertised root|
|**Root Path Cost**|Helps select the best path to root|
|**Sender Bridge ID**|Identifies the BPDU sender; tie-break|
|**Sender Port ID**|Identifies sending port; tie-break|
|**Message Age**|Age of root information|
|**Max Age**|Determines BPDU information expiration|
|**Hello Time**|BPDU generation interval|
|**Forward Delay**|Listening/Learning timing in classic STP|
|**Flags**|RSTP role/state, proposal/agreement and topology-change information|
|**BPDU Type/Version**|Identifies the STP BPDU format/protocol|

# 22. Exam Traps

### Trap 1 — Blocking ports do not process BPDUs

**Wrong:**

> Blocking means the switch ignores BPDUs.

**Correct:**

> A non-forwarding STP port can still receive/process BPDUs and participate in STP.

---

### Trap 2 — BPDU is user traffic

**Wrong:**

> BPDUs are normal Layer 2 data frames.

**Correct:**

> BPDUs are **STP control-plane protocol messages**.

---

### Trap 3 — TCN is used by RSTP

**Wrong:**

> RSTP sends the classic TCN BPDU whenever topology changes.

**Correct:**

> Classic 802.1D uses a separate TCN mechanism; RSTP integrates topology-change  
> signaling into its normal RSTP BPDUs.

---

### Trap 4 — Root Path Cost belongs to the root

**Wrong:**

> Root Path Cost is always 0 in every BPDU.

**Correct:**

> The **root itself** has a path cost of 0 to itself. A BPDU transmitted by another  
> switch advertises that switch's accumulated Root Path Cost.

---

### Trap 5 — Lowest MAC always wins

**Wrong:**

> STP chooses the switch with the lowest MAC.

**Correct:**

> STP first compares **Bridge ID**, which includes priority/system ID and MAC.  
> MAC becomes the tie-break after the priority/system-ID portion is equal.

---

### Trap 6 — BPDU Guard and BPDU Filter are equivalent

**Wrong:**

> Both simply block BPDUs.

**Correct:**

```text
BPDU Guard
    ↓
Unexpected BPDU
    ↓
Err-disable protection

BPDU Filter
    ↓
Suppress/filter BPDUs
    ↓
Potentially dangerous
```

---

### Trap 7 — Root Guard reacts to missing BPDUs

**Wrong:**

> Root Guard protects against BPDU loss.

**Correct:**

> Root Guard reacts to **superior BPDUs**.

Loop Guard is the feature associated with protection against expected BPDUs  
disappearing.

---

### Trap 8 — Loop Guard elects a new root

**Wrong:**

> Loop Guard changes the Root Bridge.

**Correct:**

> Loop Guard prevents an STP port from incorrectly transitioning to forwarding  
> when expected BPDUs disappear.

---

### Trap 9 — Every BPDU is identical

**Wrong:**

> Every switch simply forwards the exact BPDU it received.

**Correct:**

> Switches propagate their current STP information and generate BPDUs containing  
> their own sender information.

---

### Trap 10 — 20 + 15 + 15 always equals convergence time

**Wrong:**

> Classic STP always takes exactly 50 seconds.

**Correct:**

> **Hello = 2 s, Max Age = 20 s, Forward Delay = 15 s** are default timer values,  
> but actual convergence depends on the topology and failure scenario.
