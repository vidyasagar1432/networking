# EtherChannel — Static (ON)

> **Level 08 · STP / EtherChannel** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

The **static/ON** EtherChannel mode bundles links **without any negotiation** — you tell
the switch "these are one channel." Useful toward devices that don't support LACP/PAgP
(some load balancers/servers/TAPs) or when you explicitly want no protocol overhead.
**Both ends must be configured ON** (with matching physical config) or you risk a loop /
STP misbehavior.

---

## 2. Core Concepts

### 2.1 The three modes in one table

| Mode | Protocol | Negotiation | Both ends |
|------|----------|-------------|-----------|
| **ON** | none | none — forced | both must be ON |
| LACP | 802.3ad/1AX | PDU-based | active/passive combo |
| PAgP | Cisco proprietary | PDU-based | desirable/auto combo |

### 2.2 When ON makes sense

| Use | Why |
|-----|-----|
| Peer doesn't support LACP/PAgP | bridge-mode devices, some older NICs/TAPs |
| Explicit no-negotiation | strict deterministic setup |
| Quick lab bundle | skip protocol state |
| Disaggregated gear | any on-port; match config |

### 2.3 The danger of ON mismatch

- If **one side `on` and the other negotiates**, or `on` with mismatched config, the links
  may behave as **two independent links** → **L2 loop** without STP treating them as one
  logical port, or STP blocking one link and wasting capacity.
- **Requirement: BOTH ends `on` + identical config** (speed, duplex, VLAN/trunk).

### 2.4 Configuration

```text
interface GigabitEthernet0/1
 channel-group 1 mode on
interface GigabitEthernet0/2
 channel-group 1 mode on
interface Port-channel1
 switchport mode trunk
 switchport trunk allowed vlan 10,20
```

- No PDUs are sent; the switch just bundles the members into the logical channel.

### 2.5 Verification & pitfalls

```text
show etherchannel summary            # SU (in use); protocol column shows "-"
show etherchannel 1 detail
show interfaces port-channel 1
```

- A member showing `I` (idle/not in bundle) indicates config mismatch — fix consistency.
- Prefer **LACP** unless a real reason to avoid negotiation (the modern answer).

## 4. Troubleshooting & common failures

| Symptom | Likely cause | Fix |
|---------|--------------|-----|
| Member `I` (not bundled) | config mismatch on one side | align speed/duplex/VLAN/trunk |
| Loop after adding links | one side negotiating, other `on` | make both ends `on` or both LACP |
| STP blocking one link | two independent links visible | ensure proper bundle formation |
| No traffic through bundle | hash policy or mode mismatch | fix mode; `port-channel load-balance` |

---

## 5. Exam Traps

- **ON = no negotiation** — "which mode has no protocol?" → ON.
- **Both ends must be ON** — mismatch with negotiated modes = loop/waste.
- **Not the default recommendation** — LACP is the standard; ON for special peers.
- **`mode on` still needs matching physical config** (speed/duplex/trunk/VLANs).
- **It counts as ONE STP port only if correctly bundled** — misconfigured, it's two links
  and STP blocks one.
