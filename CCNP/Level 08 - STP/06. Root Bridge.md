# Root Bridge

> **Level 08 · STP** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

The **root bridge** is the reference point of an STP topology. Every non-root switch calculates its best path toward the root, and STP uses that information to determine port roles and prevent Layer 2 loops.

The root bridge is elected using the **lowest Bridge ID**:

```text
Lowest Bridge ID
       │
       ├── Lowest Bridge Priority
       │
       └── If tied → Lowest MAC Address
```

There is **one root bridge per spanning-tree instance**.

Therefore:

- **PVST+/Rapid PVST+** → one root per VLAN
    
- **MST** → one root per MST instance
    
- **Classic STP/RSTP** → one root per spanning-tree instance
    

The root bridge has **no Root Port**. Its participating active ports can become **Designated Ports**.

---

## 2. Core Concepts

### 2.1 Bridge ID — Root Election

The root bridge is selected using the lowest Bridge ID.

Conceptually:

```text
Bridge ID
│
├── Bridge Priority
│     │
│     └── System ID Extension
│           └── VLAN ID in PVST+/Rapid PVST+
│
└── MAC Address
```

The election rule is:

```text
Lowest Priority
      ↓
If tied
      ↓
Lowest MAC Address
      ↓
Root Bridge
```

### Extended System ID

Cisco switches use the **12-bit System ID Extension** when the Extended System ID is enabled.

In PVST+/Rapid PVST+, the VLAN ID is incorporated into the Bridge ID.

For example:

```text
Configured priority = 32768
VLAN                = 10

Displayed/effective priority ≈ 32778
```

Another example:

```text
Configured priority = 4096
VLAN                = 10

Displayed/effective priority ≈ 4106
```

> **Important:** The configured STP priority is normally set in increments of **4096**.

Common values:

```text
0
4096
8192
12288
16384
20480
24576
28672
32768
...
```

## 2.2 How Root Election Happens

When STP starts, each switch initially considers itself the root and advertises that information in BPDUs.

Example:

```text
SW1                    SW2                    SW3
 │                      │                      │
 │ "I am root"          │ "I am root"         │ "I am root"
 └──────────────────────┴──────────────────────┘
```

Switches compare the received BPDU information.

If SW1 has the superior Bridge ID:

```text
SW1
 │
 ├── Root ID = SW1
 │
SW2
 │
 └── learns SW1 is better than itself
```

The switches eventually converge on the same root bridge.

Non-root switches then advertise BPDUs containing the **best root information they have learned**, rather than simply forwarding the root's original BPDU unchanged.

---

## 2.3 Root Bridge Characteristics

|Attribute|Root Bridge|Non-Root Switch|
|---|---|---|
|Root Port|None|Normally one|
|Root Bridge ID|Own Bridge ID|Learned from root path|
|Root Path Cost|0|Cost toward root|
|Port roles|Participating ports can be Designated|Root/Designated/Alternate as applicable|
|Root selection|Lowest Bridge ID|Must accept elected root|
|Topology role|Reference point|Calculates path toward root|

### Important

The root bridge has:

```text
Root Port = NONE
```

A root bridge does **not** need a Root Port because it is already the root.

Its active participating ports are normally **Designated Ports** for that spanning-tree instance.

---

## 2.4 Root Port on Non-Root Switches

Each non-root switch normally selects **one Root Port** per spanning-tree instance.

The Root Port is the port that provides the **best path toward the root bridge**.

Selection is based primarily on:

1. Lowest Root Path Cost
    
2. Lowest upstream Bridge ID
    
3. Lowest upstream Port ID
    
4. Local port ID as the final tie-break in relevant cases
    

Conceptually:

```text
                Root
                 │
          ┌──────┴──────┐
          │             │
         SW2           SW3
          │             │
       Root Port     Root Port
```

The Root Port always points logically toward the root.

---

## 2.5 Root Path Cost

Every non-root switch calculates the cost of reaching the root.

Example:

```text
SW1 ===== 1G ===== SW2 ===== 1G ===== SW3
Root                  │
                      │
                    SW3
```

If each link has cost 4:

```text
SW1 → SW2 = 4
SW1 → SW2 → SW3 = 8
```

Therefore:

```text
SW2 Root Path Cost = 4
SW3 Root Path Cost = 8
```

The switch chooses the path with the **lowest total root path cost**, subject to STP tie-breakers.

---

## 2.6 Root in PVST+ and Rapid PVST+

In **PVST+/Rapid PVST+**, each VLAN has its own spanning-tree instance.

Therefore:

```text
VLAN 10 → Root = SW1
VLAN 20 → Root = SW2
VLAN 30 → Root = SW1
VLAN 40 → Root = SW2
```

This allows STP-based Layer 2 load balancing.

Example:

```text
             SW1
        Root for VLAN 10
           /       \
          /         \
        SW3         SW4
          \         /
           \       /
             SW2
        Root for VLAN 20
```

Traffic for VLANs 10 and 20 can therefore use different preferred Layer 2 paths.

> **Exam rule:** PVST+/Rapid PVST+ = **root per VLAN**.

---

## 2.7 Root in MST

MST groups VLANs into MST instances.

Therefore, the root is elected **per MST instance**, not per VLAN.

Example:

```text
MSTI 1 → Root = SW1
MSTI 2 → Root = SW2
```

If VLANs 10-20 are mapped to MSTI 1:

```text
VLAN 10 ─┐
VLAN 11  │
VLAN 12  ├── MSTI 1 → SW1 is root
...      │
VLAN 20 ─┘
```

All VLANs mapped to MSTI 1 share the same MSTI topology.

## 3. Root Bridge Placement

The root bridge should normally be positioned at an appropriate **core/distribution location** in the Layer 2 topology.

Good placement generally means:

- High-bandwidth paths are available toward the root.
    
- The root is centrally positioned relative to Layer 2 traffic.
    
- The root is stable and highly available.
    
- Access switches are prevented from accidentally becoming root.
    
- Root placement matches the intended traffic flow.
    

Example:

```text
                 Core
              ┌────────┐
              │   SW1  │
              │  ROOT  │
              └───┬────┘
                  │
          ┌───────┴───────┐
          │               │
        DIST1           DIST2
          │               │
       ACCESS          ACCESS
```

Avoid allowing an ordinary access switch to accidentally win the election.

## 4. Root Priority Configuration

### Manually set priority

```text
spanning-tree vlan 10 priority 4096
```

For VLAN 10:

```text
Configured priority = 4096
VLAN ID             = 10
Effective/displayed = 4106
```

A lower priority makes the switch more likely to become root.

---

## 5. `root primary` and `root secondary`

Cisco provides convenience macros for root placement.

### Primary root

```text
spanning-tree vlan 10 root primary
```

This adjusts the switch's priority to make it a likely root bridge.

### Secondary root

```text
spanning-tree vlan 10 root secondary
```

This adjusts the priority to make the switch a likely backup root.

Typical Cisco behavior with default-priority roots commonly results in:

```text
Primary   → 24576
Secondary → 28672
```

However, these should be understood as **priority-adjustment macros**, not as a universal guarantee that the switch will always end with exactly those values.

> **Exam trap:** `root primary` and `root secondary` are **configuration macros**, not separate STP roles or protocols.

## 6. Root Election Example

Suppose three switches have:

```text
SW1 → Priority 32768, MAC 0000.0000.0001
SW2 → Priority 24576, MAC 0000.0000.0002
SW3 → Priority 32768, MAC 0000.0000.0003
```

Election:

```text
SW1 → 32768
SW2 → 24576   ← Lowest priority
SW3 → 32768
```

Therefore:

```text
SW2 = Root Bridge
```

Now suppose:

```text
SW1 → Priority 32768, MAC 0000.0000.0001
SW2 → Priority 32768, MAC 0000.0000.0002
```

Priority is tied.

Compare MAC addresses:

```text
0000.0000.0001
        <
0000.0000.0002
```

Therefore:

```text
SW1 = Root Bridge
```

## 7. Root Bridge and Port Roles

Example:

```text
                  SW1
                 ROOT
              /        \
             /          \
            SW2        SW3
             \          /
              \        /
                 SW4
```

The root bridge:

```text
SW1
│
├── Port → Designated
└── Port → Designated
```

SW2:

```text
SW2
│
└── Port toward SW1 → Root Port
```

SW3:

```text
SW3
│
└── Port toward SW1 → Root Port
```

SW4 may have:

```text
Root Port
Designated Port
Alternate/Blocking path
```

depending on the topology and path costs.

> STP determines port roles **per spanning-tree instance**.

## 8. Root Misplacement

An incorrect root can create inefficient Layer 2 paths.

### Example

```text
                 ACCESS-SW
                    ROOT
                   /    \
                  /      \
               DIST1    DIST2
```

If the access switch becomes root accidentally, traffic may be forced through an undesirable location.

Possible consequences:

- Suboptimal traffic paths
    
- Unexpected blocked links
    
- Poor use of high-bandwidth uplinks
    
- Increased Layer 2 traffic through access switches
    
- Difficult troubleshooting
    
- Potential topology instability if the root keeps changing
    

---

## 9. Root Changes and Instability

A root change can occur when another switch advertises a superior Bridge ID.

Example:

```text
Current Root
     │
     │
New Switch
     │
     └── Superior Bridge ID
              ↓
        Root election changes
```

Frequent root changes can cause repeated STP reconvergence.

Possible causes include:

- Incorrect priority configuration
    
- New switch with unexpectedly low priority
    
- Uncontrolled STP participation
    
- Rogue/legacy switch
    
- Switch rebooting and repeatedly rejoining
    
- Incorrect Layer 2 topology
    

---

## 10. Root Guard

**Root Guard** protects a designated port from becoming a path toward a superior root.

It is commonly used on ports where downstream switches should **never influence the root election**.

Example:

```text
                Distribution
                    │
                Root Guard
                    │
                Access SW
```

If the downstream switch sends a superior BPDU, Root Guard can place the port into a **root-inconsistent** state instead of allowing the superior root information to change the intended topology.

Configuration:

```text
interface GigabitEthernet0/24
 spanning-tree guard root
```

> **Root Guard is a protection mechanism against an unexpected superior BPDU.**

## 12. Troubleshooting

|Symptom|Likely Cause|Check/Fix|
|---|---|---|
|Wrong switch is root|Priority not configured|Set explicit STP priority|
|Access switch became root|Lowest Bridge ID|Configure intended root priority|
|Root changes repeatedly|Superior BPDUs from another switch|Check STP topology and Root Guard|
|Expected core is not root|Another switch has lower Bridge ID|Compare priority and MAC|
|Unexpected blocked link|Root/path selection differs from design|Check Root ID, root path cost and port roles|
|VLAN 10 has unexpected root|PVST+ root configured incorrectly|`show spanning-tree vlan 10`|
|MST instance has unexpected root|MSTI priority/root placement incorrect|`show spanning-tree mst`|
|New switch changes root|New switch has superior Bridge ID|Set proper priority before connecting|
|Downstream switch tries to become root|Superior BPDU received|Use Root Guard where appropriate|

## 14. Exam Traps

### Trap 1 — Highest Bridge ID wins

**Wrong:**

> The switch with the highest priority becomes root.

**Correct:**

> The switch with the **lowest Bridge ID** becomes root.

---

### Trap 2 — Highest MAC wins

**Wrong:**

> The switch with the highest MAC becomes root.

**Correct:**

> MAC is only compared when Bridge Priority is tied, and the **lowest MAC wins**.

---

### Trap 3 — Root has a Root Port

**Wrong:**

> Every switch has one Root Port.

**Correct:**

> A non-root switch normally has one Root Port. The **root bridge has no Root Port**.

---

### Trap 4 — Root is global across all VLANs

**Wrong:**

> There is always one root switch for the entire network.

**Correct:**

```text
PVST+/Rapid PVST+ → Root per VLAN
MST               → Root per MSTI
```

---

### Trap 5 — `root primary` is a fixed STP priority

**Wrong:**

> `root primary` always means priority 24576.

**Correct:**

> It is a **Cisco macro that adjusts priority** to make the switch a likely primary root. `24576` is a common resulting value under default conditions.

---

### Trap 6 — Root simply forwards every BPDU unchanged

**Wrong:**

> Non-root switches forward the root's BPDU unchanged.

**Correct:**

> Non-root switches transmit BPDUs containing the **best root information they have learned**, with their own bridge/port information used in the BPDU.

---

### Trap 7 — Every physical root port is forwarding

**Wrong:**

> Every port on the root is automatically forwarding regardless of state.

**Correct:**

> The root bridge has no Root Port, and its **active participating ports are normally Designated Ports**. Administrative/down/disabled interfaces are not forwarding simply because the switch is root.
