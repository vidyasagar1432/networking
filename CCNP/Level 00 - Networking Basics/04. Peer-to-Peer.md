# Peer-to-Peer

> **Level 00 · Level 00 - Networking Basics** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

Peer-to-peer (P2P) networks treat every node as an **equal peer**: each device can
both request and provide services directly to others, without a dedicated central
server. It is a model for sharing resources (files, processing, bandwidth) among
nodes that are functionally equivalent.

---

## 2. Core Concepts

### 2.1 How it works
- There is **no central authority**; directory/coordination duties are distributed.
- Each peer maintains a partial view of the network; discovery is done via
  broadcast, DHT (distributed hash tables), or trackers.
- Examples: BitTorrent (file sharing), blockchain nodes, VoIP (early SIP without
  central proxy), Windows workgroup file shares, chat applications.

### 2.2 Advantages
- **No server cost or bottleneck**, no single point of failure.
- **Scales with demand** — each new peer adds capacity as well as load.
- **Resilience** — no central directory to take down; traffic is distributed.
- **Cheap to start** for small/home groups consuming local resources.

### 2.3 Disadvantages
- **Security risk** — no centralized authentication/authorization; any peer can expose
  devices to the others.
- **No central management, patching, or audit trail** — very hard to govern in an
  enterprise.
- **Unpredictable performance** — availability depends on peers being online.
- **Discovery overhead** on larger networks; variable addressing and NAT
  traversal (peers behind NAT need hole punching/stun/turn).
- **No SLA, backup, or data integrity guarantees.**

### 2.4 P2P vs Client-Server decision

| Factor | Client-Server | Peer-to-Peer |
|--------|--------------|--------------|
| Control | Centralized | Distributed |
| Security | Central auth & audit | Weak/none by default |
| Cost | Server hardware/software | No server, but chaos |
| Scale | Cluster/load-balanced | Organic, grows with users |
| Best for | Enterprise, required uptime & compliance | Small groups, file distribution at scale |
| Enterprise verdict | Preferred | Restricted to specific apps (updates, caching) |

### 2.5 Networking perspective (P2P in routing)
"Peer" has a specific meaning in routing: routers that build adjacencies and exchange
updates as equals (eBGP/iBGP neighbors, OSPF/EIGRP adjacency). These protocols are P2P
in *control plane* behavior even inside a client–server style network. That distinction
between **data plane** (end-user C/S apps) and **control plane** (routers peering)
is a recurring ENCOR theme.

## 3. Configuration / Commands

```text
# Windows workgroup share (de facto P2P file sharing)
net share notes=D:\notes /grant:everyone,read

# Sample of a P2P-like routing relationship (BGP peers are equals)
router bgp 65001
 neighbor 10.0.0.2 remote-as 65002
 neighbor 10.0.0.2 description P2P eBGP peer
```

---

## 4. Exam Traps

- **P2P is a logical/application model, not a physical topology.** A P2P app can run
  over a star-switched network.
- **BGP/OSPF "peers" ≠ file-sharing P2P** — same word, different meaning; know BOTH.
- **Avoid recommending P2P for enterprise services:** no central security/compliance.
- **P2P is not automatically "peer-to-peer" in OSI** — the model applies at the
  application layer; transport still uses TCP/UDP connections.
- ENCOR: expect a question that contrasts P2P vs C/S when choosing where to place
  an enterprise service — answer C/S for manageability.

## 5. Quick Review Table

| Aspect | Peer-to-Peer | Client-Server |
| ------ | ------------ | ------------- |
| Authority | Distributed/equal | Central server |
| Security | Weak by default | Central auth, audit |
| Failure mode | No SPOF, but peers may be offline | Server SPOF unless clustered |
| Performance | Variable, peer-dependent | Predictable (clustered) |
| Management | Almost none | Full lifecycle control |
| Enterprise use | Restricted | Default choice |
| Example | BitTorrent, Windows workgroup | HTTP, DNS, DHCP |
