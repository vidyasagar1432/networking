# Network Design Principles

> **Level 00 · Level 00 - Networking Basics** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

Design principles are the *why* behind every topology choice in the earlier notes:
they turn "connect some switches" into a network that is **fast, reliable, secure,
scalable, and inexpensive to run**. ENCOR tests these by presenting a design scenario
and asking which principle it satisfies or violates.

The five canonical attributes: **Fault Tolerance, Scalability, QoS, Security** (the
Cisco "four characteristics of network design") plus **manageability/automation** as
the modern fifth.

---

## 2. Core Concepts

### 2.1 The four (now five) pillars
1. **Fault tolerance / reliability**
   Eliminate single points of failure: redundant links, redundant devices, rapid
   convergence (RSTP/EtherChannel, HSRP/VRRP, NSF/SSO). Designed tolerance, not
   just "two of everything" — some failures are detected & recovered faster than others.
2. **Scalability**
   Hierarchical design so more sites/users must not redesign the core; modular blocks
   grow vertically (DC) or horizontally (campus). Address plan with room to grow
   (VLSM, summarization).
3. **Quality of Service (QoS)**
   Network must differentiate traffic: classify, mark, queue (voice/ video first).
   Achieves predictable delay/jitter/loss under congestion (see Level 21).
4. **Security**
   Defense-in-depth: ACLs, segmentation (VLAN/VRF/SGT), 802.1X, device hardening,
   encrypted management, firewalls. Secure by design, not bolt-on (see Level 17).
5. **Manageability & automation** (modern)
   Centralized control (DNA Center/ISE), model-driven APIs (NETCONF/RESTCONF), telemetry,
   consistent baselines — reduces human error, speeds change (see Level 24).

### 2.2 Supporting design rules
- **Hierarchy** — three-tier / layered modules give consistent behavior & isolation.
- **Modularity** — keep functions in blocks; change one block without touching the rest.
- **Redundancy with simplicity** — dual everything, but avoid over-engineering
  (STP complexities; know when to route instead of bridge).
- **The 80/20 and 20/80 rules (historical but still exam-relevant):** LOCAL traffic
  dominates where applications are local (80/20); with centralized apps/data, most
  traffic crosses to the core/DC (20/80) — that changes where switches/VLANs live.
- **Speed of convergence > raw speed of reconfiguration** for most outages.

### 2.3 Design trade-off example
- Cheapest design: no redundancy, flat L2. → Violates fault tolerance.
- Most secure: everything segmented and firewalled. → Higher cost, more ops.
- Answer pattern: pick the design that satisfies the *stated* priorities (guaranteed
  uptime → dual everything + HA protocols; biggest complaint is delay for voice →
  QoS with priority queuing).

### 2.4 Common design anti-patterns (trap material)
- Redundant links without EtherChannel/STP tuning → loops/broadcast storms.
- Single default gateway in a redundant switch pair → no HSRP/VRRP.
- Applying policy at the core → slow core, complex changes.
- Flat L2 campus with no summarization → giant broadcast domain, black-hole tagging,
  scaling pain.
- No separation of management VLAN / management VRF → the network management plane is
  exposed to users.

## 3. Configuration / Commands

```text
# Applying two principles concurrently (failure tolerance + QoS)
# 1) Fault tolerance: redundancy on access-distribution
interface Port-channel1
 channel-group 1 mode active    # LACP EtherChannel doubles bandwidth + HA

# 2) QoS: protect VoIP (classification + priority)
class-map match-any VOICE
 match ip dscp ef
policy-map WAN-OUT
 class VOICE
  priority percent 10          # strict priority for voice
```

## 4. Exam Traps

- **"Two identical switches is redundant" is not enough** — the *control plane* must
  converge too (HSRP/VRRP for gateways, RSTP for loops, NSF/SSO for SUP failover).
- **Scalability ≠ adding SSID/power** — it's about design that grows without redesign.
- **QoS is not "faster internet"** — it reorders/prioritizes existing capacity.
- **Security is defense-in-depth** — one ACL on the edge is not "secure design";
  layered controls, segmented zones, hardened devices, encrypted mgmt are all required.
- **Management plane exposure** is a classic simple question — the answer is a dedicated,
  separate management segment (and ideally a management VRF).

## 5. Quick Review Table

| Principle | What it means | Exam signal |
|-----------|---------------|-------------|
| Fault Tolerance | No SPOF; fast convergence | Dual devices + HA protocols |
| Scalability | Grows without redesign | Hierarchy + modular design + summarization |
| QoS | Prioritized, predictable traffic | Classification + queuing (voice first) |
| Security | Defense-in-depth | Segmentation, 802.1X, hardening, encrypted mgmt |
| Manageability | Central, automatable | DNA Center, NETCONF, telemetry |
| Hierarchy | Clean layering | 3-tier / modular blocks |
| Modularity | Isolated change units | Block-based expansion |
| Local-icity | 80/20 vs 20/80 | Determines VLAN/DC placement |
| Speed of convergence | Outage recovery time | RSTP, fast OSPF/BGP timers, NSF/SSO |
