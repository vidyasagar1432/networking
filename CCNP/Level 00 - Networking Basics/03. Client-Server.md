# Client-Server

> **Level 00 · Level 00 - Networking Basics** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

The client–server model centralizes services on dedicated **servers** that clients
request work from. Servers *provide* a service (spool, share, resolve, host);
clients *consume* it. This is the dominant model for enterprise networks because it
centralizes control, authentication, and data.

---

## 2. Core Concepts

### 2.1 Roles
- **Client** — initiates requests; typically a user device (PC, phone, browser,
  NMS, DHCP client). Clients do not share most of their resources.
- **Server** — listens passively, waits for requests, answers them; provides
  computing/storage/application service.
- One device can be both a client of one service and server of another
  (e.g., a file server is a client of DNS and NTP).

### 2.2 Request–response flow
1. Client resolves server → DNS query.
2. Client opens a connection → TCP handshake (for TCP-based services).
3. Client sends request (HTTP GET, DHCP Discover, LDAP bind, SQL query).
4. Server processes and replies.
5. Session/Presentation/Application layer logic may keep state (cookies, sessions) —
   offloaded from client.

### 2.3 Why enterprises choose it
- **Centralized management & security** — enforce policy, patch, and audit in one place.
- **Scalability** — servers/clusters scale resources where the load is.
- **Data integrity & backup** — single source of truth, easier to back up.
- **Thin clients possible** — small clients, rich servers (web apps, VDI, Citrix/RDP).
- **Standard interfaces** — well-known ports and protocols make interoperability easy.

### 2.4 Example services

| Service | Client | Server | Port/Protocol |
|---------|--------|--------|---------------|
| Web | Browser | HTTP/HTTPS server | 80 / 443 (TCP) |
| Email | Mail client | SMTP/IMAP/POP3 server | 25/465, 143/993, 110/995 |
| DHCP | Host (Discover) | DHCP server | 67/68 (UDP) |
| DNS | Resolver | DNS server | 53 (UDP/TCP) |
| File sharing | SMB/CIFS client | File server | 445 (TCP) |
| Remote access | SSH client | SSH daemon | 22 (TCP) |

### 2.5 Scaling the model
- **Server farm / cluster** — multiple servers behind a load balancer for capacity + HA.
  (See [[Level 27 - High Availability]].)
- **N-tier design** — separate web / app / DB tiers to scale independently
  (see [[06. Enterprise Network Architecture]]).

## 3. Configuration / Commands

Conceptual, but lab examples:

```text
# Server-side (Linux)
ss -tlnp                # list listening server sockets
nginx or httpd          # web server

# Client-side (Windows/Linux)
curl http://server/     # issue an HTTP request
nslookup www.example.com

# On a router as a DHCP client (router plays "client" role)
interface GigabitEthernet0/0
 ip address dhcp
```

## 4. Exam Traps

- **Servers are not always "bigger PCs."** A server is defined by its *role*.
- **Clients can be servers too** — role is protocol/port-specific, not device-specific.
- **DNS and DHCP are client-server services** — the naming layer and the bootstrap
  provisioning are themselves C/S models.
- **Not all traffic is C/S:** routing protocol peerings (OSPF/BGP neighbors) were
  historically modeled as peers/equal partners, though modern designs still use
  centralized controllers where it helps (see [[04. Peer-to-Peer]]).
- **ENCOR emphasis:** recognize where a C/S service will live in the campus model
  (DMZ, server farm VLAN, north-south vs east-west flow).
