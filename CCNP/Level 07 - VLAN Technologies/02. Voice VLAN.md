# Voice VLAN

> **Level 07 · VLAN Technologies** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

A **Voice VLAN** is a dedicated VLAN used to carry **IP phone/VoIP traffic** separately  
from normal data traffic.

A common Cisco campus design allows an IP phone and a PC to share the **same physical  
switch port**:

- The PC uses the **data VLAN**.
    
- The phone uses the **voice VLAN**.
    
- PC traffic is normally **untagged**.
    
- The phone normally sends voice traffic **802.1Q-tagged** with the voice VLAN ID.
    

The switch port remains configured as an **access port** with an additional voice VLAN  
association.

> **Key idea:** One physical access port can provide separate logical VLANs for a phone  
> and a device connected through the phone's built-in switch.

---

## 2. Why Use a Voice VLAN?

A separate voice VLAN provides logical separation of voice traffic from normal user  
traffic.

|Purpose|Benefit|
|---|---|
|Segmentation|Separates voice and data Layer 2 traffic|
|QoS|Allows voice traffic to receive appropriate priority|
|Addressing|Phones can use a dedicated IP subnet|
|DHCP|Phones can receive voice-specific DHCP configuration|
|Security|Voice traffic can be controlled separately from user traffic|
|Management|Voice endpoints can be administered as a separate class of devices|
|Troubleshooting|Voice and data traffic can be analyzed independently|

Example:

```text
VLAN 10 → User/Data
VLAN 20 → Voice
```

A typical addressing design might be:

```text
VLAN 10 → 10.10.10.0/24
VLAN 20 → 10.10.20.0/24
```

## 3. Typical Topology

```text
                 ┌───────────────┐
                 │    Switch     │
                 │               │
                 │ Access Port   │
                 │ Data VLAN 10  │
                 │ Voice VLAN 20 │
                 └───────┬───────┘
                         │
                         │
                    ┌────▼────┐
                    │ IP Phone│
                    └────┬────┘
                         │
                         │
                        PC
```

Traffic behavior:

```text
PC ────────────── untagged ──────────────► Data VLAN 10

IP Phone ──────── tagged VLAN 20 ────────► Voice VLAN 20
```

The phone's integrated switch provides the connection for the PC.

---

## 4. How the Switch Port Works

Example configuration:

```cisco
interface GigabitEthernet0/1
 switchport mode access
 switchport access vlan 10
 switchport voice vlan 20
 spanning-tree portfast
```

This creates the following logical behavior:

```text
Physical Port Gi0/1
        │
        ├── Untagged traffic → VLAN 10 → PC
        │
        └── Tagged VLAN 20 → Voice VLAN → IP Phone
```

The port is still configured as:

```cisco
switchport mode access
```

It is **not** configured as:

```cisco
switchport mode trunk
```

> `switchport voice vlan 20` allows the access port to support a separate voice VLAN  
> for an IP phone while continuing to provide the access VLAN for normal untagged  
> endpoint traffic.

---

## 5. Phone VLAN Discovery

The phone needs to learn which VLAN it should use for voice traffic.

Cisco environments commonly use:

- **CDP (Cisco Discovery Protocol)**
    
- **LLDP-MED (Link Layer Discovery Protocol - Media Endpoint Discovery)**
    

These protocols can advertise network information such as the voice VLAN.

### Important distinction

The switch can be configured with:

```cisco
switchport voice vlan 20
```

The phone can then learn that VLAN information through supported discovery mechanisms.

However:

> CDP/LLDP is a common method of automatic voice-VLAN discovery, but it is not the  
> only possible method. A phone can also be manually configured or use vendor-specific  
> provisioning mechanisms.

---

## 6. DHCP for Voice Devices

Phones normally obtain their IP configuration using DHCP.

A typical voice DHCP scope provides:

```text
IP address
Subnet mask
Default gateway
DNS information
Voice/provisioning server information
```

Example:

```text
Voice VLAN 20
Network:     10.10.20.0/24
Gateway:     10.10.20.1
DHCP pool:   10.10.20.100–10.10.20.200
```

### DHCP Option 150

**DHCP Option 150** is commonly used in Cisco IP telephony environments to provide  
the address of a **TFTP server** used for phone configuration/provisioning.

Example concept:

```text
Phone
  ↓ DHCP
Gets IP address + gateway + Option 150
  ↓
Contacts TFTP/provisioning server
  ↓
Downloads configuration
```

### DHCP Option 66

**DHCP Option 66** can also provide a TFTP/server hostname or address and is used by  
various network devices and VoIP implementations.

### DHCP Option 242

**Option 242** is associated particularly with **Avaya** environments and should not  
be described as a generic Cisco VoIP option.

> **Exam point:** Option 150 is strongly associated with Cisco IP phone/TFTP  
> provisioning.

## 7. Voice VLAN and QoS

Voice traffic is sensitive to:

- Delay
    
- Jitter
    
- Packet loss
    

Therefore, QoS is important in enterprise voice networks.

### RTP media

Voice media commonly uses **RTP (Real-time Transport Protocol)**.

A common QoS marking for voice bearer/media traffic is:

```text
DSCP EF = 46
```

EF is commonly used for low-latency voice media.

### Signaling

Voice signaling can use protocols such as:

- SIP
    
- SCCP
    
- H.323
    

The appropriate DSCP marking for signaling depends on the platform and QoS design.

Cisco QoS designs commonly use markings such as **CS3** for signaling, but this should  
not be treated as a universal rule for every VoIP implementation.

> **Exam distinction:** Do not confuse voice **media/RTP** with voice **signaling**.  
> They are separate traffic classes and may receive different QoS markings.

## 8. Trust Boundary

A major reason for using a voice VLAN is to apply different QoS/security treatment to  
the phone and the attached PC.

A common design is:

```text
             Switch
               │
               │
        ┌──────┴──────┐
        │   IP Phone  │
        └──────┬──────┘
               │
              PC
```

The phone can generate voice traffic with appropriate QoS markings.

The switch can be configured to trust markings from a trusted Cisco phone while treating  
the attached PC as untrusted.

Conceptually:

```text
IP Phone → trusted voice markings

PC → do not automatically trust endpoint markings
```

The exact QoS trust configuration is **platform and IOS/IOS XE dependent**.

For example, some Cisco platforms support:

```cisco
mls qos trust device cisco-phone
```

but this should not be treated as a universal command across all modern Cisco  
platforms.

> **CCNP focus:** Understand the **trust boundary concept** rather than memorizing a  
> platform-specific QoS command without checking the platform.

---

## 9. PoE

Many enterprise IP phones receive electrical power using **PoE (Power over Ethernet)**.

Common standards include:

- IEEE 802.3af — PoE
    
- IEEE 802.3at — PoE+
    
- IEEE 802.3bt — higher-power PoE variants
    

PoE allows the switch to provide both:

```text
Ethernet connectivity
+
Electrical power
```

through the same cable.

If a phone requires PoE and the switch cannot provide sufficient power, the phone may  
fail to power up even though the Ethernet connection itself is functional.

## 10. Configuration

### Basic Voice VLAN Configuration

```cisco
interface GigabitEthernet0/1
 switchport mode access
 switchport access vlan 10
 switchport voice vlan 20
 spanning-tree portfast
```

This provides:

```text
Data VLAN  → 10
Voice VLAN → 20
```

### Optional QoS configuration

QoS configuration is platform-specific.

Do not blindly apply a legacy `mls qos` configuration without verifying the switch  
platform and IOS/IOS XE release.

## 11. Verification Commands

### Check VLAN configuration

```cisco
show vlan brief
```

### Check the interface switchport configuration

```cisco
show interfaces GigabitEthernet0/1 switchport
```

Look for information similar to:

```text
Administrative Mode: static access
Operational Mode: static access
Access Mode VLAN: 10
Voice VLAN: 20
```

### Check trunk information

Not normally required for the phone-facing access port, but useful when troubleshooting  
the VLAN path:

```cisco
show interfaces trunk
```

### Check CDP neighbors

```cisco
show cdp neighbors
show cdp neighbors detail
```

### Check LLDP neighbors

```cisco
show lldp neighbors
show lldp neighbors detail
```

### Check PoE

On supported Cisco switches:

```cisco
show power inline
```

or:

```cisco
show power inline GigabitEthernet0/1
```

### Check MAC addresses

```cisco
show mac address-table interface GigabitEthernet0/1
```

### Check IP configuration

```cisco
show ip interface brief
```

## 12. Troubleshooting Voice VLAN

Use a structured troubleshooting sequence.

### Step 1 — Check physical connectivity

Verify:

- Cable
    
- Switch port
    
- Phone power
    
- PoE availability
    
- Link status
    

```cisco
show interfaces status
show power inline
```

### Step 2 — Verify access and voice VLAN

```cisco
show interfaces Gi0/1 switchport
```

Confirm:

```text
Access VLAN = expected data VLAN
Voice VLAN  = expected voice VLAN
```

### Step 3 — Verify VLAN existence

```cisco
show vlan brief
```

Confirm the voice VLAN exists.

### Step 4 — Verify VLAN propagation

If the phone's voice VLAN must cross trunks, verify the VLAN is allowed on the  
required trunk links:

```cisco
show interfaces trunk
```

Check:

- Allowed VLAN list
    
- Native VLAN
    
- Trunk state
    
- VLAN forwarding
    

### Step 5 — Verify phone VLAN discovery

Check:

```cisco
show cdp neighbors detail
show lldp neighbors detail
```

Make sure the phone can learn the appropriate voice VLAN information when using  
CDP/LLDP-MED.

### Step 6 — Verify DHCP

Confirm the phone receives:

```text
IP address
Subnet mask
Default gateway
Required provisioning information
```

### Step 7 — Verify QoS

Check that voice traffic receives the intended markings and queue treatment.

## 13. Common Failure Scenarios

|Symptom|Possible Cause|
|---|---|
|Phone has no power|PoE problem|
|Phone powers on but no IP|Voice VLAN/DHCP problem|
|Phone receives data VLAN address|Voice VLAN configuration/discovery problem|
|Phone cannot reach call server|Routing/ACL/DHCP/provisioning issue|
|Phone works but voice quality is poor|QoS, congestion, delay, jitter, or packet loss|
|Phone works on one switch but not another|VLAN, PoE, CDP/LLDP, or platform configuration difference|
|Phone VLAN works locally but not across switches|Voice VLAN not allowed on trunk|
|PC works but phone does not|Phone VLAN, PoE, DHCP, or discovery issue|
|Phone works but PC does not|Data VLAN/access-port or phone passthrough issue|

## 14. Exam Traps

### Trap 1 — Voice VLAN makes the port a trunk

**False.**

The interface remains an access port:

```cisco
switchport mode access
switchport voice vlan 20
```

---

### Trap 2 — PC traffic is tagged

**Normally false.**

The PC connected behind the phone normally sends untagged traffic.

The phone's voice traffic is normally tagged with the voice VLAN.

---

### Trap 3 — Voice VLAN is just another trunk VLAN

**Misleading.**

A voice VLAN on an access port provides special handling for a phone and its attached  
PC. It is not equivalent to configuring:

```cisco
switchport mode trunk
```

---

### Trap 4 — CDP/LLDP is mandatory

**False.**

CDP/LLDP-MED is commonly used for automatic discovery, but phones may also be  
configured through other mechanisms.

---

### Trap 5 — Option 150 is required for every VoIP phone

**False.**

Option 150 is commonly used in Cisco IP telephony environments for TFTP provisioning.  
Other vendors and implementations may use different options or provisioning methods.

---

### Trap 6 — Option 242 is Cisco Skinny

**False.**

Option 242 is particularly associated with Avaya environments.

Cisco's Skinny protocol is **SCCP (Skinny Client Control Protocol)**.

---

### Trap 7 — EF is the signaling marking

**Usually false.**

**DSCP EF (46)** is commonly used for voice bearer/RTP media.

Signaling is a separate traffic class and commonly uses a different marking such as  
CS3, depending on the QoS design.

---

### Trap 8 — Trust the PC because it is connected through the phone

**False.**

The phone can be a QoS trust boundary.

A common design trusts appropriate markings from the phone but does not automatically  
trust markings generated by the attached PC.

---

### Trap 9 — PoE is required for voice VLANs

**False.**

Voice VLAN operation does not require PoE.

PoE is simply a common method of powering IP phones.

A phone can receive power from another source and still use a voice VLAN.

---

### Trap 10 — Voice VLAN provides complete security

**False.**

Voice VLAN provides Layer 2 segmentation.

Security still depends on:

- ACLs
    
- Firewall policies
    
- QoS/security configuration
    
- Endpoint security
    
- Network design

## 16. Key Takeaways

1. **Voice VLAN separates IP phone traffic from normal data traffic.**
    
2. **A phone and PC can share one physical switch port.**
    
3. **PC traffic is normally untagged and belongs to the access/data VLAN.**
    
4. **Phone voice traffic is normally 802.1Q-tagged with the voice VLAN.**
    
5. **The phone-facing switch port remains an access port.**
    
6. **`switchport voice vlan X` associates a voice VLAN with the access port.**
    
7. **CDP/LLDP-MED can advertise voice VLAN information to the phone.**
    
8. **DHCP provides the phone's IP configuration and may provide provisioning information.**
    
9. **DHCP Option 150 is strongly associated with Cisco IP phone/TFTP provisioning.**
    
10. **RTP voice media is commonly marked DSCP EF (46).**
    
11. **Voice signaling is a separate traffic class from RTP media.**
    
12. **QoS trust should normally be established at a controlled trust boundary.**
    
13. **PoE is commonly used to power IP phones but is not required for Voice VLANs.**
    
14. **When troubleshooting, verify PoE → voice VLAN → DHCP → VLAN propagation → routing →  
    QoS.**
