# QinQ (802.1ad / VLAN Stacking)

> **Level 07 · VLAN Technologies** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

**QinQ** (commonly associated with **IEEE 802.1ad Provider Bridges**) is a Layer 2 VLAN-stacking technique that adds an **outer VLAN tag** to an Ethernet frame that already contains an **inner customer VLAN tag**.

The provider uses the outer **S-Tag (Service VLAN)** to transport customer VLANs across its Layer 2 network while preserving the customer's original **C-Tag (Customer VLAN)**.

### Core idea

```text
Customer Network
      │
      │ C-Tag
      ▼
┌──────────────────────────────┐
│ Customer VLAN 10             │
└──────────────────────────────┘
      │
      │ Provider adds S-Tag
      ▼
┌──────────────────────────────────────────────┐
│ S-Tag: VLAN 100 │ C-Tag: VLAN 10             │
└──────────────────────────────────────────────┘
      │
      │ Provider Network
      ▼
   Customer VLAN 10
      │
      │ S-Tag removed
      ▼
Customer Network
```

> **CCNP Mental Model:**  
> **C-VLAN identifies the customer's VLAN. S-VLAN identifies the provider's service/tunnel.**

---

## 2. QinQ Frame Structure

A typical QinQ Ethernet frame contains two VLAN tags:

```text
[ DA | SA | S-TAG | C-TAG | EtherType | Payload | FCS ]
              │       │
              │       └── Customer VLAN
              │
              └── Service Provider VLAN
```

More specifically:

```text
[DA | SA | 0x88A8 | S-VID | 0x8100 | C-VID | Type | Payload | FCS]
              └──── S-Tag ────┘ └──── C-Tag ────┘
```

### S-Tag

```text
TPID = 0x88A8
```

The **S-Tag** is the outer provider tag.

It identifies the provider's **service VLAN / transport context**.

### C-Tag

```text
TPID = 0x8100
```

The **C-Tag** is the customer's original 802.1Q VLAN tag.

It identifies the customer's VLAN.

> **Exam focus:** `0x88A8` = common S-Tag TPID, `0x8100` = common C-Tag TPID.

Implementations can support other TPIDs, so these values should be treated as the common QinQ model rather than an absolute requirement for every implementation.

---

## 3. VLAN Tags and Overhead

Each VLAN tag adds **4 bytes**:

```text
S-Tag = 4 bytes
C-Tag = 4 bytes

Total QinQ VLAN-tag overhead = 8 bytes
```

Therefore:

```text
Normal Ethernet
      │
      └── + C-Tag = +4 bytes

802.1Q frame
      │
      └── + S-Tag = +4 additional bytes

QinQ frame
      │
      └── 2 VLAN tags = +8 bytes vs untagged Ethernet
```

### MTU consideration

The provider network must be able to accommodate the larger QinQ frame.

Do **not** memorize a universal `1508` or `1510` value without considering the original frame size, whether a customer VLAN tag already existed, and how the platform defines/configures MTU.

> **Exam point:** QinQ adds **8 bytes of VLAN-tag overhead compared with an untagged Ethernet frame**.

## 4. CE and PE Roles

|Device|Role|
|---|---|
|**CE**|Customer Edge device|
|**PE**|Provider Edge device|
|**S-VLAN**|Provider/service VLAN|
|**C-VLAN**|Customer VLAN|

### CE

The **Customer Edge (CE)** is part of the customer's network.

It normally sends standard Ethernet frames or 802.1Q-tagged customer frames.

Example:

```text
Customer VLAN 10
      │
      ▼
C-Tag = VLAN 10
```

### PE

The **Provider Edge (PE)** connects the customer network to the provider network.

The PE can add the provider's outer S-Tag:

```text
Before PE:

[C-Tag VLAN 10]

After PE:

[S-Tag VLAN 100][C-Tag VLAN 10]
```

At the destination provider edge, the outer provider tag is removed before delivering the customer traffic.

---

## 5. Why QinQ Is Used

Without QinQ, a provider may have difficulty transporting many customers' VLANs while preserving their individual VLAN numbering.

For example:

```text
Customer A
VLAN 10
VLAN 20

Customer B
VLAN 10
VLAN 20

Customer C
VLAN 10
VLAN 20
```

The same customer VLAN IDs can exist independently because the provider can place each customer's traffic into a different S-VLAN/service context.

```text
Customer A
C-VLAN 10
      │
      ▼
S-VLAN 100

Customer B
C-VLAN 10
      │
      ▼
S-VLAN 200

Customer C
C-VLAN 10
      │
      ▼
S-VLAN 300
```

The customer's VLAN numbering can therefore be preserved across the provider network.

> **Important:** QinQ does not mean the provider has no VLAN limits. It provides an additional VLAN namespace/context by stacking tags.

---

## 6. QinQ Scaling Model

The key scalability idea is:

```text
C-VLAN
└── Customer's VLAN namespace

S-VLAN
└── Provider's service namespace
```

Conceptually:

```text
                 Provider Network
                       │
          ┌────────────┼────────────┐
          │            │            │
       S-VLAN 100   S-VLAN 200   S-VLAN 300
          │            │            │
       Customer A   Customer B   Customer C
          │            │            │
       C-VLAN 10   C-VLAN 10   C-VLAN 10
```

Each customer's C-VLAN 10 can remain distinct because the provider's S-VLAN/service context separates them.

## 7. Cisco QinQ / 802.1Q Tunnel

Cisco switches can provide QinQ-style tunneling using **802.1Q tunneling**, commonly configured with:

```cisco
switchport mode dot1q-tunnel
```

This is a **Cisco-specific implementation/configuration mechanism** for 802.1Q tunneling.

A typical provider-facing customer port can be configured as:

```cisco
interface GigabitEthernet0/1
 description CUSTOMER-A
 switchport access vlan 100
 switchport mode dot1q-tunnel
 switchport nonegotiate
```

Here:

```text
VLAN 100
└── Provider S-VLAN

dot1q-tunnel
└── Enables 802.1Q tunneling behavior

nonegotiate
└── Disables DTP negotiation
```

## 8. Cisco QinQ Frame Flow

Assume the customer sends:

```text
Customer VLAN = 10
Provider S-VLAN = 100
```

### Step 1 — Customer sends frame

```text
[Ethernet][C-Tag VLAN 10][Payload]
```

### Step 2 — Provider edge adds S-Tag

```text
[Ethernet][S-Tag VLAN 100][C-Tag VLAN 10][Payload]
```

### Step 3 — Provider transports the frame

```text
[S-Tag VLAN 100][C-Tag VLAN 10]
```

The provider's S-VLAN carries the customer-tagged frame across the provider network.

### Step 4 — Destination provider edge removes S-Tag

```text
[Ethernet][C-Tag VLAN 10][Payload]
```

### Step 5 — Customer receives its original VLAN

```text
Customer VLAN 10
```

The customer's original C-VLAN information has been preserved.

## 9. Provider Backbone

The provider's backbone must transport the S-VLAN.

Example:

```cisco
interface TenGigabitEthernet1/1
 description PROVIDER-BACKBONE
 switchport mode trunk
 switchport trunk allowed vlan 100
```

Conceptually:

```text
Customer
   │
   │ C-VLAN 10
   ▼
PE1
   │
   │ S-VLAN 100
   │
   ▼
Provider Backbone
   │
   │ S-VLAN 100
   ▼
PE2
   │
   │ C-VLAN 10
   ▼
Customer
```

The provider backbone does not need to understand the customer's VLAN numbering in the same way the customer's network does; the customer VLAN information is transported inside the provider service context.

## 11. QinQ vs Double-Tagging VLAN-Hopping Attack

These concepts are easy to confuse.

### Legitimate QinQ

```text
Customer
   │
   │ C-Tag
   ▼
Provider Edge
   │
   │ adds S-Tag
   ▼
[S-Tag][C-Tag]
   │
   ▼
Provider Network
```

This is a legitimate Layer 2 service.

### Double-Tagging Attack

A VLAN-hopping attack can exploit **double-tagged 802.1Q frames** and native-VLAN behavior.

The attacker intentionally constructs a frame with two VLAN tags.

```text
[Outer 802.1Q Tag][Inner 802.1Q Tag][Payload]
```

This is an **attack technique**, not the same thing as provider QinQ.

> **Exam Trap:**  
> **QinQ ≠ double-tagging VLAN-hopping attack.**  
> Both involve two VLAN tags, but their purpose and network context are different.

## 12. QinQ vs DTP vs 802.1Q

|Technology|Purpose|
|---|---|
|**DTP**|Negotiates whether a Cisco switch link becomes a trunk|
|**802.1Q**|VLAN tagging/encapsulation|
|**QinQ / 802.1ad**|Stacks VLAN tags to transport customer VLANs through a provider network|
|**VTP**|VLAN database distribution|
|**LLDP**|Neighbor/device discovery|

Mental model:

```text
DTP
└── Should this link be a trunk?

802.1Q
└── How is VLAN information tagged?

QinQ
└── How can a provider carry an already-tagged customer frame
    inside another provider VLAN context?
```

## 14. Important Limitations and Design Considerations

### MTU

QinQ adds another VLAN tag, increasing frame size.

```text
Customer frame
      +
S-Tag
      =
larger Ethernet frame
```

Every provider link carrying the QinQ frame must support the required frame size.

---

### VLAN ID Space

QinQ provides an additional VLAN namespace, but it does **not create unlimited VLANs**.

The actual number of usable S-VLANs and C-VLANs depends on:

- IEEE VLAN ID restrictions
    
- Reserved VLAN IDs
    
- Cisco platform capabilities
    
- Software version
    
- Provider design
    

---

### MAC Learning

QinQ remains a Layer 2 Ethernet service.

Do not reduce MAC learning to the oversimplified rule:

```text
"inner MAC on access, outer MAC on backbone"
```

Actual MAC learning and forwarding behavior depends on the specific provider-bridge/tunneling implementation and platform.

The important CCNP concept is:

```text
QinQ transports customer Layer 2 frames
inside a provider VLAN/service context.
```

## 15. Exam Traps

### Trap 1 — S-Tag vs C-Tag

```text
S-Tag
└── Outer/provider/service tag

C-Tag
└── Inner/customer tag
```

Common TPIDs:

```text
S-Tag → 0x88A8
C-Tag → 0x8100
```

---

### Trap 2 — QinQ adds 8 bytes

Two VLAN tags:

```text
4 + 4 = 8 bytes
```

Compared with an untagged Ethernet frame, QinQ introduces **8 bytes of VLAN-tag overhead**.

---

### Trap 3 — Customer VLAN is preserved

QinQ does not normally require the provider to renumber the customer's VLANs.

```text
Customer VLAN 10
       ↓
C-VLAN 10
       ↓
[S-VLAN 100][C-VLAN 10]
       ↓
C-VLAN 10
```

---

### Trap 4 — `dot1q-tunnel`

Cisco's:

```cisco
switchport mode dot1q-tunnel
```

is used for Cisco 802.1Q tunneling/QinQ-style service.

It is not simply another normal trunk mode such as:

```cisco
switchport mode trunk
```

---

### Trap 5 — QinQ is not VLAN hopping

```text
QinQ
└── Legitimate VLAN stacking/tunneling

Double-tagging attack
└── Malicious VLAN-hopping technique
```

---

### Trap 6 — MTU

Do not blindly memorize:

```text
"QinQ MTU = 1508"
```

The correct principle is:

```text
QinQ adds another 4-byte VLAN tag
to an already 802.1Q-tagged frame.
```

Therefore, the provider path must accommodate the resulting frame size.

## 16. CCNP Mental Model

```text
QinQ / 802.1ad
│
├── Customer Network
│     │
│     └── C-VLAN
│           └── Customer VLAN identity
│
├── Provider Edge
│     │
│     └── Adds S-Tag
│           └── Provider service identity
│
├── Provider Network
│     │
│     └── Carries:
│           [S-Tag][C-Tag][Payload]
│
└── Destination Provider Edge
      │
      └── Removes S-Tag
            │
            └── Customer receives original C-VLAN
```

### One-line memory aid

```text
C-Tag = Customer
S-Tag = Service Provider
QinQ   = Customer VLAN inside Provider VLAN
```
