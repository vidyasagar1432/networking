# Summarization (Route Aggregation)

> **Level 05 · IPv4** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

**Route summarization (aggregation)** combines multiple more-specific routes into a  
**single less-specific route**.

Example:

```text
10.1.0.0/24
10.1.1.0/24
10.1.2.0/24
10.1.3.0/24
        ↓
10.1.0.0/22
```

Summarization reduces routing-table size, limits routing updates, improves scalability,  
and helps contain route instability.

> **Core idea:** advertise one larger prefix instead of many smaller prefixes.

---

## 2. Core Concepts

### 2.1 How summarization works

A summary is determined by finding the **common leftmost bits** of the network  
addresses.

For four /24 networks:

```text
10.1.0.0/24 → 10.1.00000000
10.1.1.0/24 → 10.1.00000001
10.1.2.0/24 → 10.1.00000010
10.1.3.0/24 → 10.1.00000011
               └──────┘
               6 common bits
```

The first two octets provide:

```text
10.1 = 16 bits
```

The third octet provides:

```text
000000 = 6 common bits
```

Therefore:

```text
16 + 6 = /22
```

Summary:

```text
10.1.0.0/22
```

A `/22` contains four `/24` networks:

```text
10.1.0.0/24
10.1.1.0/24
10.1.2.0/24
10.1.3.0/24
```

---

### 2.2 Steps to calculate a summary

1. List all network addresses.
    
2. Convert the changing octet(s) to binary.
    
3. Find the **common leftmost bits**.
    
4. Count those common bits.
    
5. That count becomes the summary prefix length.
    
6. Set all remaining bits to `0`.
    
7. Verify that the resulting summary covers the intended networks.
    

---

## 3. Summary Alignment

A summary must begin on the correct **prefix boundary**.

For example, a `/22` has:

```text
32 - 22 = 10 host bits
```

When summarizing /24 networks, a `/22` groups:

```text
4 × /24
```

Therefore valid /22 boundaries in the third octet are:

```text
0
4
8
12
16
20
...
252
```

Valid examples:

```text
10.1.0.0/22
10.1.4.0/22
10.1.8.0/22
10.1.12.0/22
```

Invalid example:

```text
10.1.1.0/22
```

A `/22` beginning at `.1` cannot represent an exact four-/24 block because the  
prefix boundary is incorrect.

> **Exam rule:** the summary prefix must be aligned with its block size.

---

## 4. What a Summary Covers

A summary represents **every address inside its prefix**, not just the specific  
subnets that currently exist.

For example:

```text
10.1.0.0/22
```

covers:

```text
10.1.0.0 – 10.1.3.255
```

Therefore, if you summarize:

```text
10.1.0.0/24
10.1.1.0/24
10.1.3.0/24
```

as:

```text
10.1.0.0/22
```

the summary also covers:

```text
10.1.2.0/24
```

even if that subnet does not exist.

This can cause **black-hole routing** if traffic for an unused portion of the  
summary is sent toward the summarizing router.

> **Important:** an aggregate is a covering prefix. It does not mean that every  
> address inside it has a valid more-specific route.

---

## 5. Summarization vs. Supernetting

Both use the same **binary prefix-aggregation mathematics**, but the terms are  
used differently.

|Concept|Meaning|
|---|---|
|**Route summarization**|Combining multiple routes into one less-specific route|
|**Supernetting**|Combining contiguous address blocks into a larger prefix|
|**CIDR**|Classless addressing using arbitrary prefix lengths|

Example:

```text
192.168.0.0/24
192.168.1.0/24
192.168.2.0/24
192.168.3.0/24
        ↓
192.168.0.0/22
```

The same aggregation can be described as a **supernet** and as a **route summary**,  
depending on context.

---

## 6. Where Summarization Is Used

### 6.1 Distribution → Core

A distribution router may have:

```text
10.1.0.0/24
10.1.1.0/24
10.1.2.0/24
10.1.3.0/24
```

Instead of advertising four routes toward the core, it can advertise:

```text
10.1.0.0/22
```

This is a common hierarchical-network design practice.

---

### 6.2 OSPF

OSPF supports summarization at specific boundaries.

**ABR inter-area summarization:**

```text
router ospf 1
 area 1 range 10.1.0.0 255.255.252.0
```

This summarizes routes from an area toward other OSPF areas.

For external routes, summarization is performed on an ASBR using:

```text
summary-address
```

---

### 6.3 EIGRP

EIGRP supports manual route summarization on an outgoing interface:

```text
router eigrp 100
 network 10.0.0.0

interface GigabitEthernet0/1
 ip summary-address eigrp 100 10.1.0.0 255.255.252.0
```

The summary is advertised instead of the more-specific routes on that interface.

---

### 6.4 BGP

BGP supports aggregation with:

```text
router bgp 65001
 aggregate-address 10.1.0.0 255.255.252.0
```

`summary-only` suppresses the more-specific component routes from being advertised  
along with the aggregate:

```text
router bgp 65001
 aggregate-address 10.1.0.0 255.255.252.0 summary-only
```

---

## 7. Benefits

|Benefit|Explanation|
|---|---|
|**Smaller routing tables**|Fewer prefixes need to be stored|
|**Fewer updates**|Less routing information propagates through the network|
|**Better scalability**|Hierarchical networks can hide internal details|
|**Faster convergence**|Changes to individual subnets need not affect every router|
|**Flap containment**|Instability in a more-specific route can remain within a smaller part of the network|

---

## 8. Risks

### 8.1 Black-hole routing

If a router advertises:

```text
10.1.0.0/22
```

but only some of the component networks actually exist, traffic for an unused  
portion may still reach the summarizing router.

The router may then discard the traffic.

---

### 8.2 Overly broad summaries

A summary that is too large may include address space belonging to another  
network or routing domain.

Example:

```text
Intended:
10.1.0.0/24
10.1.1.0/24

Poor summary:
10.1.0.0/16
```

The `/16` covers far more address space than intended.

> **Exam rule:** summarize as tightly as possible while still achieving the desired  
> aggregation.

---

### 8.3 Loss of routing detail

A summary intentionally hides more-specific information.

This is normally desirable, but it can make troubleshooting or path selection  
less precise.

---

## 9. Longest Prefix Match

Summarization does **not automatically override more-specific routes**.

Routers use **longest prefix match**.

Example:

```text
10.1.0.0/22     → Router A
10.1.2.0/24     → Router B
```

Traffic destined for:

```text
10.1.2.10
```

matches both routes, but the `/24` is more specific than the `/22`.

Therefore:

```text
10.1.2.10 → Router B
```

> **Key relationship:** specific route wins over summary route.

---

## 10. Exam Traps

### Trap 1 — Three /24s do not automatically make a /22

A `/22` contains **four /24s**.

Therefore:

```text
10.1.0.0/24
10.1.1.0/24
10.1.2.0/24
10.1.3.0/24
```

can form:

```text
10.1.0.0/22
```

But three networks alone do not make an exact `/22`; the resulting summary would  
also cover the missing fourth `/24`.

---

### Trap 2 — Alignment matters

```text
10.1.0.0/22   ✓
10.1.4.0/22   ✓
10.1.1.0/22   ✗
```

The summary must start at the correct block boundary.

---

### Trap 3 — A summary can cover nonexistent space

A summary describes an entire address range.

It can therefore cover networks that are not actually assigned.

---

### Trap 4 — More-specific routes win

If both exist:

```text
10.1.0.0/22
10.1.2.0/24
```

the `/24` wins for destinations inside `10.1.2.0/24`.

---

### Trap 5 — OSPF `area range` is not for external routes

```text
area X range
```

is used for **inter-area route summarization** by an ABR.

External-route summarization uses:

```text
summary-address
```

on an ASBR.

---

### Trap 6 — EIGRP summary is interface-based

EIGRP manual summarization is configured on the **outgoing interface**:

```text
ip summary-address eigrp ...
```

## 11. Quick Review

|Item|Value|
|---|---|
|**Purpose**|Represent multiple routes with one less-specific route|
|**Method**|Find common leftmost bits|
|**Prefix**|Number of common bits|
|**Boundary**|Summary must be properly aligned|
|**Main design location**|Network hierarchy / aggregation boundaries|
|**OSPF**|`area range` for inter-area; `summary-address` for external routes|
|**EIGRP**|`ip summary-address eigrp`|
|**BGP**|`aggregate-address`|
|**Main benefit**|Smaller routing tables and reduced routing churn|
|**Main risk**|Overly broad summaries and black-hole routing|
|**Routing rule**|Longest prefix match wins|
|**Related concept**|Supernetting / CIDR aggregation|

## 12. One-Minute Exam Memory

```text
SUMMARIZATION
      ↓
Many specific routes
      ↓
Find common leftmost bits
      ↓
Create aligned less-specific prefix
      ↓
Advertise ONE summary
      ↓
Smaller routing table
      ↓
Less routing churn
```

Remember:

```text
Common bits → Summary prefix
Correct boundary → Valid summary
Summary → Covers entire prefix
More-specific route → Wins
Too-broad summary → Possible black hole
```
