# Route Aggregation

> **Level 05 · IPv4** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

**Route aggregation** is the composite term for summarizing **many routes into fewer**
(supernetting at the classful edge, summarization in IGP/BGP, and longest-prefix
checking). In practice, "aggregation" is what BGP does at ISP/enterprise boundaries and
what OSPF/EIGRP do at area/distribution points.

---

## 2. Core Concepts

### 2.1 Aggregation points in the routing ecosystem

| Layer/Protocol | Mechanism |
|----------------|-----------|
| IGP (OSPF/EIGRP) | `area X range`, `summary-address` at boundaries |
| BGP | `aggregate-address` / `summary-only`; suppress-maps for specifics |
| Static | route to `null0` for the aggregate + specifics via peers |
| RIB/CEF | longest-prefix-match picks specifics over aggregate |

### 2.2 The "aggregate + null0" pattern (classic design)
- Advertise the summary (e.g., `10.1.0.0/22` toward core).
- Add a **discard/null route** for the aggregate on the distributor so traffic that
  matches only the summary (and goes nowhere) is dropped instead of looped:
  ```
  ip route 10.1.0.0 255.255.252.0 null0
  ```
- Prevents looped forwarding for unallocated sub-prefixes.

### 2.3 Longest-prefix match interplay
- Even if a more specific (e.g., /24) is NOT advertised by the aggregator, the core
  has the /22 — a flow to the missing /24 routes via the /22; if no real path exists
  → matches null0 → drop (not black-hole into a ring).

### 2.4 BGP aggregation specifics

| Option | Behavior |
|--------|----------|
| `aggregate-address X Y` | creates the aggregate; keeps specifics (*suppress-map* to filter) |
| `aggregate-address X Y summary-only` | advertise only the aggregate |
| attribute inherit | MED/communities attach per rule |
- Aggregation in BGP is the chief reason the Internet table stays ~1M routes (Level 12).

### 2.5 Aggregation vs leaking (the exam nuance)
- Aggregating at the boundary hides specifics → a distant AS cannot prefer a better path
  to a covered prefix (nontransit design trade-off).
- Used with **forwarding/mitigation**: RIB "policy leak" can push specifics where needed.

## 3. Configuration / Commands

```text
# IGP example (EIGRP interface summarization)
router eigrp 100
interface Gi0/1
 ip summary-address eigrp 100 10.1.0.0 255.255.252.0

# BGP aggregate with summary-only
router bgp 65001
 neighbor 10.0.0.2 remote-as 65002
 aggregate-address 10.1.0.0 255.255.252.0
 aggregate-address 10.1.0.0 255.255.252.0 summary-only

# Null route to protect a gap
ip route 10.1.0.0 255.255.252.0 null0

# Verify
show ip route | include 10.1.0.0
```

## 4. Exam Traps

- **Longest-prefix** always wins over the aggregate — the "why does the specific route
  exist for host reachability" answer.
- **Summarize only contiguous** blocks — non-contiguous aggregation creates a wrong
  supernet.
- **Always consider null0** for an advertised aggregate (loop prevention).
- **In BGP: `summary-only` vs retaining specifics** — a classic two-option question.
- **Aggregation is a trade**: simple table but less path preference for covered prefixes.
