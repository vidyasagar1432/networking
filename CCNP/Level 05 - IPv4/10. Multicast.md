# Multicast (IPv4)

> **Level 05 · IPv4** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

**IPv4 multicast** delivers traffic to a **group of interested receivers**. Instead of sending a separate unicast copy to every receiver, the source sends to one multicast group and the network replicates traffic only where needed.

IPv4 multicast uses **Class D addresses (`224.0.0.0/4`)**.

Common uses include **IPTV, streaming, financial market feeds, and routing protocols** such as OSPF, EIGRP, and RIPv2.

Multicast models include:

- **One-to-many** — one source, many receivers.
    
- **Many-to-many** — multiple sources and receivers.
    
- **Source-specific multicast (SSM)** — receivers subscribe to a specific `(S,G)` source/group pair.
    

---

## 2. Core Concepts

### 2.1 IPv4 Multicast Address Range

The entire IPv4 multicast range is:

```text
224.0.0.0 – 239.255.255.255
224.0.0.0/4
```

Historically, this is called **Class D**.

Unlike unicast addresses, multicast addresses identify **groups**, not individual interfaces.

There is no host/network portion within a multicast address.

---

### 2.2 Important Multicast Ranges

|Range|Purpose|
|---|---|
|`224.0.0.0/24`|Link-local multicast|
|`224.0.1.0 – 238.255.255.255`|Globally scoped / administratively assignable multicast space|
|`239.0.0.0/8`|Administratively scoped multicast|

#### Link-local multicast: `224.0.0.0/24`

Traffic sent to `224.0.0.0/24` is **not forwarded by multicast routers** and remains on the local network segment.

Important examples:

|Address|Purpose|
|---|---|
|`224.0.0.1`|All IPv4 hosts on the local subnet|
|`224.0.0.2`|All IPv4 multicast routers on the local subnet|
|`224.0.0.5`|OSPF routers|
|`224.0.0.6`|OSPF DRs and BDRs|
|`224.0.0.9`|RIPv2 routers|
|`224.0.0.10`|EIGRP routers|
|`224.0.0.22`|IGMPv3|

**Exam point:** `224.0.0.0/24` is **link-local multicast**, and routers do not forward it.

---

### 2.3 Administratively Scoped Multicast

```text
239.0.0.0/8
```

`239.0.0.0/8` is intended for **private/organizational multicast domains**.

It is commonly used inside enterprises where multicast traffic should remain within an organization's administrative scope.

---

## 3. How Multicast Works

A simplified multicast flow:

```text
Source
   |
   | sends to multicast group
   v
Multicast Router
   |
   +------> Receiver A
   |
   +------> Receiver B
   |
   +------> Receiver C
```

### Step 1 — Receiver joins the group

A host uses **IGMP** to indicate that it wants to receive traffic for a multicast group.

Example:

```text
"I want to receive 239.1.1.1"
```

IGMP is used between **IPv4 hosts and their directly connected multicast routers**.

---

### Step 2 — Multicast routing builds the distribution tree

Routers use a multicast routing protocol such as **PIM** to determine where multicast traffic should be forwarded.

Common PIM models include:

- **PIM-DM** — Dense Mode
    
- **PIM-SM** — Sparse Mode
    
- **PIM-SSM** — Source-Specific Multicast
    

---

### Step 3 — Routers replicate traffic where necessary

The source sends **one IP multicast packet**.

Routers replicate the packet only onto outgoing interfaces that lead toward interested receivers.

This avoids sending separate copies across every network path.

---

## 4. Multicast at Layer 2

IPv4 multicast is mapped to an Ethernet multicast MAC address.

The Ethernet multicast MAC range is:

```text
01:00:5E:00:00:00
        through
01:00:5E:7F:FF:FF
```

General format:

```text
01:00:5E:0x:xx:xx
```

### 4.1 IPv4-to-Ethernet Mapping

An IPv4 multicast address contains:

```text
32 total bits
```

The multicast portion is:

```text
28 bits
```

Ethernet uses only:

```text
23 bits
```

of the IPv4 multicast address when creating the multicast MAC.

Therefore:

```text
28 IPv4 multicast bits
        ↓
23 bits mapped to Ethernet MAC
        ↓
5 bits are lost
```

This creates a **many-to-one mapping**.

### 4.2 The Collision Trap

Because 5 bits are discarded:

```text
2^5 = 32
```

different IPv4 multicast addresses can map to the **same Ethernet multicast MAC address**.

Therefore:

> **32 IPv4 multicast addresses can map to one Ethernet multicast MAC address.**

This is an important ENCOR exam concept.

The switch can distinguish the MAC address, but the MAC mapping itself cannot uniquely identify every IPv4 multicast group.

---

## 5. IGMP Snooping

Without effective **IGMP snooping**, a Layer-2 switch may flood multicast traffic throughout the VLAN because it does not know which ports have interested receivers.

With IGMP snooping:

```text
Multicast source
       |
       v
     Switch
    /      \
   /        \
Receiver   No receiver
   |          X
   v
Gets traffic
```

The switch listens to IGMP messages and builds a forwarding state for multicast groups.

Therefore:

> **IGMP snooping limits multicast flooding by forwarding multicast traffic only toward ports with interested receivers.**

IGMP snooping operates on the **Layer-2 switch**; IGMP itself is a **Layer-3 host/router protocol**.

---

## 6. Unicast vs Broadcast vs Multicast

|Feature|Unicast|Broadcast|Multicast|
|---|---|---|---|
|Destination|One host|All hosts in broadcast domain|Interested group members|
|Delivery|One-to-one|One-to-all|One-to-many / many-to-many|
|Efficiency|Separate traffic per recipient|Sends to everyone|Replicates only where needed|
|Normal routing|Yes|Normally not routed|Yes|
|Example|HTTP, SSH|ARP, DHCP Discover|IPTV, streaming, routing protocols|

### Key distinction

```text
Unicast   → one specific destination
Broadcast → everyone in the broadcast domain
Multicast → only members of a multicast group
```

---

## 7. PIM and Multicast Routing

**PIM (Protocol Independent Multicast)** is used by routers to build multicast forwarding paths.

Common modes:

### PIM-DM

**Dense Mode** assumes receivers are widely distributed.

It initially floods multicast traffic and then prunes branches that do not have receivers.

```text
Flood → Prune
```

---

### PIM-SM

**Sparse Mode** assumes receivers are relatively sparse.

It commonly uses a **Rendezvous Point (RP)** to help sources and receivers initially discover each other.

```text
Source
   |
   v
   RP
   |
   +---- Receiver A
   |
   +---- Receiver B
```

**Exam point:**

> The RP is associated with **PIM Sparse Mode**, not with SSM.

---

### PIM-SSM

**Source-Specific Multicast (SSM)** allows a receiver to specify both:

```text
Source + Group
```

This is represented as:

```text
(S,G)
```

Example:

```text
Source = 192.168.10.10
Group  = 232.1.1.1

(S,G) = (192.168.10.10, 232.1.1.1)
```

SSM uses the IPv4 range:

```text
232.0.0.0/8
```

A major advantage of SSM is that it **does not require an RP**.

---

## 8. TTL and Link-Local Multicast

IPv4 multicast packets contain a normal IPv4 **TTL field**.

Many local multicast control protocols use:

```text
TTL = 1
```

This prevents the packet from traveling beyond the local segment.

However, the more important rule for ENCOR is:

> **Traffic destined to `224.0.0.0/24` is link-local multicast and is not forwarded by multicast routers.**

For example, OSPF uses:

```text
224.0.0.5
224.0.0.6
```

so OSPF neighbor/control traffic remains local to the connected network.

## 10. Cisco IOS Configuration

### Enable IPv4 multicast routing

```cisco
conf t
ip multicast-routing
```

---

### Enable PIM on an interface

```cisco
interface GigabitEthernet0/1
 ip pim sparse-mode
```

PIM must be enabled on the relevant Layer-3 interfaces participating in multicast routing.

---

### Configure IGMP version

```cisco
interface GigabitEthernet0/1
 ip igmp version 3
```

IGMP version 3 supports **source-specific membership information**, which is important for SSM.

---

### Verify multicast routing

```cisco
show ip mroute
```

Displays the IPv4 multicast routing table.

---

### Verify IGMP groups

```cisco
show ip igmp groups
```

Displays multicast groups learned through IGMP.

## 11. Exam Traps

### Trap 1 — Multicast is not broadcast

```text
Broadcast → all hosts
Multicast → interested group members
```

Multicast is specifically designed for group-based delivery.

---

### Trap 2 — Class D has no host/network split

Do not subnet multicast addresses like normal unicast addresses.

```text
224.0.0.0/4
```

defines the multicast address space; multicast addresses identify **groups**.

---

### Trap 3 — 28 bits vs 23 bits

IPv4 multicast:

```text
28 group bits
```

Ethernet multicast mapping:

```text
23 bits
```

Therefore:

```text
28 - 23 = 5 bits lost
2^5 = 32 addresses
```

**32 IPv4 multicast addresses can map to the same Ethernet multicast MAC.**

---

### Trap 4 — IGMP does not route multicast

IGMP answers:

> **Which hosts want to receive this multicast group?**

PIM answers:

> **How should multicast traffic be routed between multicast routers?**

---

### Trap 5 — SSM does not need an RP

```text
PIM-SM  → commonly uses RP
PIM-SSM → no RP required
```

SSM uses `(S,G)` source-specific subscriptions.

---

### Trap 6 — 224.0.0.0/24 is link-local

Routers do not forward traffic destined for:

```text
224.0.0.0/24
```

This is why multicast control traffic such as OSPF hellos remains local.

---

### Trap 7 — IGMP snooping is a switch feature

```text
IGMP          → host/router membership protocol
IGMP Snooping → Layer-2 switch feature
PIM           → multicast routing protocol
```

---

### Trap 8 — Multicast MAC collisions are normal

The multicast IP-to-MAC mapping is **not one-to-one**.

```text
32 IPv4 multicast groups
             ↓
     same Ethernet MAC
```

This does not mean the IP multicast groups are identical; it is simply a limitation of the Layer-2 mapping.

### Exam takeaway

> **IPv4 multicast = group-based delivery using `224.0.0.0/4`. IGMP manages receiver membership, PIM routes multicast between routers, and IGMP snooping controls Layer-2 forwarding. Remember `224.0.0.0/24` is link-local, `232.0.0.0/8` is SSM, `239.0.0.0/8` is administratively scoped, and the 28-bit IPv4 multicast address maps to only 23 bits of the Ethernet multicast MAC, creating a 32-to-1 mapping collision.**
