# Object Tracking

> **Level 14 · First Hop Redundancy** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

**Object Tracking** allows Cisco IOS/IOS XE to monitor the state of an object—such as an interface, route, or IP SLA operation—and make another feature react to that object's state.

The basic model is:

```text
Tracked condition
      ↓
Object state: Up / Down
      ↓
Subscribed feature reacts
      ↓
Priority / weighting / route / next-hop changes
```

Object tracking is especially important with **FHRPs** because an FHRP router may have a healthy LAN interface while its **upstream path is broken**.

Without tracking:

```text
LAN interface = UP
       ↓
FHRP thinks router is healthy
       ↓
Router may remain preferred
       ↓
Traffic can be black-holed
```

With tracking:

```text
Upstream condition fails
       ↓
Tracked object = DOWN
       ↓
FHRP priority/weighting changes
       ↓
Another gateway can become preferred
```

### Key exam concept

> **Object tracking extends FHRP awareness beyond the local interface by allowing a router to react to tracked conditions such as upstream interfaces, routes, or IP SLA results.**

---

# 2. Object Tracking Architecture

Object tracking has two parts:

```text
1. Define what to monitor
2. Reference that object from a feature
```

Example:

```text
track 1 interface GigabitEthernet0/1 line-protocol
```

Then:

```text
interface GigabitEthernet0/0
 standby 10 track 1 decrement 20
```

The relationship is:

```text
Track Object 1
      |
      ↓
Gi0/1 line protocol
      |
      ↓
Up / Down
      |
      ↓
HSRP
      |
      ↓
Priority changes
```

### Important

> **Creating a tracking object alone does not necessarily change anything. The object must be consumed/referenced by another feature.**

---

# 3. Tracked Object Types

Common object-tracking types include:

|Object|What it monitors|Example|
|---|---|---|
|Interface line protocol|Interface operational state|`track 1 interface Gi0/1 line-protocol`|
|Interface IP routing|Whether IP routing is enabled/usable on an interface|`track 2 interface Gi0/1 ip routing`|
|IP route|Whether a route is present/reachable|`track 3 ip route 10.0.0.0 255.0.0.0 reachability`|
|IP SLA|Result of an IP SLA operation|`track 4 ip sla 10`|
|Track list|Combination of other tracking objects|`track 5 list boolean and`|

The exact available tracking types and syntax can vary by Cisco IOS/IOS XE release and platform.

---

# 4. Interface Tracking

Interface tracking monitors an interface condition.

Example:

```text
track 1 interface GigabitEthernet0/1 line-protocol
```

This tracks the **line protocol** state of the interface.

Conceptually:

```text
Gi0/1
  |
  +-- UP   → Track 1 = UP
  |
  +-- DOWN → Track 1 = DOWN
```

### Why line protocol?

An interface can have different physical and logical states.

For FHRP uplink tracking, the **line protocol** state is commonly used because it represents whether the interface is operational at Layer 2.

---

# 5. Interface IP-Routing Tracking

Example:

```text
track 2 interface GigabitEthernet0/1 ip routing
```

This tracks whether the interface is usable for IP routing according to the specified tracking criterion.

This is different from:

```text
line-protocol
```

because the two tracking modes examine different interface conditions.

### Exam distinction

```text
line-protocol
    ↓
Tracks line protocol state

ip routing
    ↓
Tracks IP-routing usability/state
```

---

# 6. IP Route Tracking

Object tracking can monitor whether a particular route exists in the routing table.

Example:

```text
track 3 ip route 10.0.0.0 255.0.0.0 reachability
```

Conceptually:

```text
Route exists
    ↓
Track = UP

Route disappears
    ↓
Track = DOWN
```

This is useful when you care about **routing reachability**, rather than merely whether a physical interface is up.

### Why this matters

An interface may remain up while the route through that interface disappears.

Therefore:

```text
Interface UP
      ≠
Destination reachable
```

Route tracking can detect that difference.

---

# 7. IP SLA Tracking

Object tracking can monitor the result of an **IP SLA operation**.

Example:

```text
track 4 ip sla 10
```

A typical design is:

```text
IP SLA operation
      ↓
Tests a destination
      ↓
Success / Failure
      ↓
Track object
      ↓
Up / Down
      ↓
FHRP or routing feature reacts
```

### Example

Suppose R1 should remain the preferred gateway only while it can reach an upstream router.

```text
R1
 |
 | IP SLA probe
 ↓
8.8.8.8
```

If the probe fails:

```text
IP SLA = failed
     ↓
Track 4 = DOWN
     ↓
HSRP priority decreases
     ↓
Another gateway can become Active
```

### Important

IP SLA tracking can provide reachability information beyond the local interface.

However:

> **IP SLA is only as end-to-end as the operation being performed.**

For example, an ICMP echo probe to a remote IP tests reachability to that destination; it does not automatically prove that every application or every path is healthy.

---

# 8. Track Lists

Multiple tracking objects can be combined into a **track list**.

Example:

```text
track 5 list boolean and
```

A track list can combine multiple objects using logical conditions.

Conceptually:

```text
Track 1
   +
Track 2
   +
Track 3
   ↓
Track List
   ↓
Final UP/DOWN state
```

Common logical concepts include:

- **AND**
    
- **OR**
    

Track lists are useful when a feature should react to a combination of conditions rather than one individual object.

---

# 9. Track States

A tracking object can report a state such as:

|State|Meaning|
|---|---|
|**Up**|Tracked condition is currently satisfied|
|**Down**|Tracked condition has failed|
|**Not present / Unknown**|Object or required information is not currently available|

The exact state wording can vary depending on the object type and IOS/IOS XE version.

### Verify state

```text
show track
```

This is the primary command for inspecting tracking state.

---

# 10. Object Tracking with HSRP

Object tracking is commonly used to change **HSRP priority**.

Example:

```text
track 1 interface GigabitEthernet0/1 line-protocol
```

Then:

```text
interface GigabitEthernet0/0
 standby 10 ip 10.0.0.1
 standby 10 priority 110
 standby 10 track 1 decrement 20
```

Normal state:

```text
Priority = 110
Track 1 = UP
```

If the tracked interface fails:

```text
Track 1 = DOWN
       ↓
Priority decrement = 20
       ↓
110 - 20 = 90
```

The router's HSRP priority becomes:

```text
90
```

If another HSRP router has a higher priority, it can become Active.

### Important

```text
HSRP
  ↓
Tracking changes PRIORITY
```

---

# 11. Multiple HSRP Tracking Objects

Multiple objects can be tracked.

Example:

```text
track 1 interface GigabitEthernet0/1 line-protocol
track 2 ip sla 10
```

HSRP:

```text
interface GigabitEthernet0/0
 standby 10 ip 10.0.0.1
 standby 10 priority 110
 standby 10 track 1 decrement 20
 standby 10 track 2 decrement 15
```

Normal:

```text
110
```

If Track 1 fails:

```text
110 - 20 = 90
```

If Track 2 also fails:

```text
110 - 20 - 15 = 75
```

Therefore:

```text
Both tracked objects UP
        ↓
Priority = 110

Track 1 DOWN
        ↓
Priority = 90

Track 1 + Track 2 DOWN
        ↓
Priority = 75
```

---

# 12. Object Tracking with VRRP

VRRP can also use object tracking to influence router priority where supported by the Cisco IOS/IOS XE platform and version.

Conceptually:

```text
Tracked object
      ↓
Object DOWN
      ↓
VRRP priority changes
      ↓
Another router can become Master
```

The exact VRRP tracking syntax and capabilities are **platform/release dependent**, so always verify the Cisco IOS/IOS XE documentation for the device being configured.

### Exam concept

The important distinction is:

```text
HSRP → tracking can decrement priority
VRRP → tracking can influence priority
GLBP → tracking decrements weighting
```

---

# 13. Object Tracking with GLBP

GLBP uses tracking differently.

For GLBP:

> **Tracking affects GLBP weighting, not GLBP priority.**

Example:

```text
track 1 interface GigabitEthernet0/1 line-protocol
```

Then:

```text
interface GigabitEthernet0/0
 glbp 10 ip 10.0.0.1
 glbp 10 weighting 110 lower 80 upper 100
 glbp 10 track 1 decrement 40
```

Normal:

```text
Weighting = 110
Track 1 = UP
```

If Track 1 fails:

```text
110 - 40 = 70
```

Because:

```text
70 < lower threshold 80
```

the AVF becomes inactive.

### Key distinction

```text
HSRP
Tracking → Priority

VRRP
Tracking → Priority

GLBP
Tracking → Weighting
```

---

# 14. GLBP Weighting Thresholds

GLBP can use:

```text
lower
upper
```

thresholds.

Example:

```text
glbp 10 weighting 110 lower 80 upper 100
```

Interpretation:

```text
Initial weighting = 110
Lower threshold   = 80
Upper threshold   = 100
```

Suppose:

```text
track 1 decrement 40
```

Then:

```text
110 - 40 = 70
```

Because:

```text
70 < 80
```

the AVF becomes inactive.

When the tracked condition recovers, the weighting returns to the configured calculated value.

The upper threshold controls when the forwarder can become active again.

### Important

Do not memorize:

```text
Weighting = 0 → always inactive
```

Instead memorize:

```text
Lower threshold
    ↓
AVF becomes inactive

Upper threshold
    ↓
AVF can become active again
```

# 15. Tracking and Upstream Failure

This is the main reason object tracking is used with FHRPs.

Consider:

```text
             Internet
                |
             R1 ISP
                |
              R1
                |
             Clients
```

If R1's client-facing interface remains up but the ISP connection fails:

```text
Client-facing interface = UP
ISP reachability = DOWN
```

Without tracking:

```text
HSRP may still see R1 as healthy
```

With IP SLA tracking:

```text
ISP reachability
      ↓
IP SLA fails
      ↓
Track object DOWN
      ↓
HSRP priority decreases
      ↓
Backup router becomes preferred
```

This is the **key practical advantage of object tracking**.

---

# 16. Object Tracking vs Interface State

Do not confuse these concepts.

### Without tracking

An FHRP may primarily know:

```text
My local interface is UP
```

### With interface tracking

The FHRP can know:

```text
My important uplink is DOWN
```

### With IP SLA tracking

The FHRP can know:

```text
The remote destination I care about is unreachable
```

### With route tracking

The FHRP can know:

```text
The required route is no longer present/reachable
```

Therefore:

```text
Local state
     ↓
Interface tracking
     ↓
Route state
     ↓
Remote reachability
```

Object tracking provides increasingly useful information depending on what is being monitored.

# 17. Object Tracking and Static Routes

Object tracking can control whether a static route remains installed.

Example:

```text
track 1 ip sla 10
```

Then:

```text
ip route 0.0.0.0 0.0.0.0 10.0.0.1 track 1
```

Conceptually:

```text
IP SLA succeeds
      ↓
Track 1 = UP
      ↓
Static route installed

IP SLA fails
      ↓
Track 1 = DOWN
      ↓
Tracked static route removed
```

This can allow a backup route to become preferred.

### Important

A tracked static route is different from simply configuring a static route.

The route is tied to the state of the tracking object.

---

# 18. Object Tracking and PBR

Object tracking can also be used with **Policy-Based Routing (PBR)**.

A common mechanism is:

```text
set ip next-hop verify-availability
```

This allows PBR to verify whether a configured next hop is available using tracking information.

Conceptually:

```text
PBR
 |
 +-- Next-hop 1
 |      |
 |      +-- Track object
 |
 +-- Next-hop 2
        |
        +-- Backup
```

If the preferred next hop becomes unavailable:

```text
Track = DOWN
     ↓
Preferred next hop rejected
     ↓
Backup next hop can be selected
```

### Important

`verify-availability` is the **PBR action/mechanism**.

The tracking object itself is separately defined.

# 19. Object Tracking and Other Features

Object tracking is not limited to FHRPs.

It can interact with features such as:

- HSRP
    
- VRRP
    
- GLBP
    
- Tracked static routes
    
- PBR next-hop verification
    
- Other Cisco IOS/IOS XE features that support tracking objects
    

The exact supported consumers vary by platform and software release.

### Core architecture

```text
                 Object Tracking
                       |
          +------------+------------+
          |            |            |
         HSRP         GLBP         Routing
          |            |            |
      Priority      Weighting    Route/Next-hop
```

# 20. Complete Configuration Example

## R1 — Primary Gateway

```text
track 1 interface GigabitEthernet0/1 line-protocol
track 2 ip sla 10

interface GigabitEthernet0/0
 ip address 10.0.0.2 255.255.255.0
 standby 10 ip 10.0.0.1
 standby 10 priority 110
 standby 10 preempt
 standby 10 track 1 decrement 20
 standby 10 track 2 decrement 15
```

IP SLA:

```text
ip sla 10
 icmp-echo 8.8.8.8
 frequency 5
ip sla schedule 10 life forever start-time now
```

Track the SLA:

```text
track 2 ip sla 10
```

Conceptually:

```text
Normal:
110

Uplink failure:
110 - 20 = 90

SLA failure:
110 - 15 = 95

Both fail:
110 - 20 - 15 = 75
```

If the backup router has a higher resulting priority, it can become HSRP Active.

# 22. Troubleshooting Workflow

When tracking does not produce the expected FHRP behavior, troubleshoot in this order:

```text
1. Is the tracking object configured?
             ↓
2. Is the object UP or DOWN?
             ↓
3. Is the object referenced by the feature?
             ↓
4. Is the decrement/weighting configured correctly?
             ↓
5. Did the FHRP priority/weight actually change?
             ↓
6. Is preemption configured if required?
             ↓
7. Is the backup router's resulting priority higher?
```

---

# 23. Common Failures

|Symptom|Likely Cause|Check|
|---|---|---|
|No priority change|Track object not referenced|FHRP tracking configuration|
|Track remains UP|Condition has not actually failed|`show track`|
|Track remains DOWN|Interface/SLA/route condition failed|`show track`|
|HSRP does not fail over|Decrement is too small|Compare resulting priorities|
|HSRP fails over unexpectedly|Decrement is too large|Review all tracked objects|
|GLBP AVF becomes inactive|Weight crossed lower threshold|`show glbp`|
|GLBP does not recover|Weight has not reached recovery condition|Weighting/threshold configuration|
|IP SLA track does not change|SLA operation itself is failing/misconfigured|`show ip sla statistics`|
|Tracked route disappears|Route condition failed|`show ip route`|
|Static route does not behave as expected|Track object or route syntax/configuration issue|`show track`, `show ip route`|
|PBR does not use backup next hop|Next-hop verification/tracking issue|PBR + tracking configuration|

# 24. Common Exam Traps

### Trap 1 — Creating a track object automatically changes HSRP

**False.**

The object must be **referenced by HSRP**.

```text
track 1 interface Gi0/1 line-protocol
```

alone does not automatically change HSRP priority.

You need something such as:

```text
standby 10 track 1 decrement 20
```

---

### Trap 2 — Object tracking only monitors interfaces

**False.**

It can monitor conditions such as:

```text
Interface
Route
IP SLA
Track lists
```

and other supported objects.

---

### Trap 3 — GLBP tracking changes priority

**False.**

GLBP tracking affects:

```text
Weighting
```

not AVG election priority.

---

### Trap 4 — IP SLA automatically means end-to-end application monitoring

**False.**

IP SLA tests whatever the configured operation tests.

For example:

```text
ICMP echo
```

tests ICMP reachability to the configured destination.

---

### Trap 5 — Interface UP means upstream connectivity is healthy

**False.**

An interface can remain UP while:

```text
ISP path fails
Routing fails
Remote destination becomes unreachable
```

This is why IP SLA and route tracking can be useful.

---

### Trap 6 — Weighting 0 is the universal GLBP failure condition

**False.**

GLBP uses configured:

```text
lower
upper
```

thresholds.

---

### Trap 7 — PBR `verify-availability` is itself the track object

**False.**

Think:

```text
Track object
     ↓
Provides state

PBR verify-availability
     ↓
Consumes that state
```

# 25. Practical Design Example

Consider two Internet gateways:

```text
                 Internet
                /        \
             ISP1        ISP2
              |           |
             R1           R2
              \           /
               \         /
                Clients
```

R1 is preferred.

If R1's local interface is still up but ISP1 is unreachable, simple interface status may not detect the failure.

Use:

```text
IP SLA
   ↓
Track
   ↓
HSRP priority decrement
```

Flow:

```text
R1 → IP SLA probe → ISP1/remote target
                    |
                    X Failure
                    |
                 Track DOWN
                    |
             HSRP priority drops
                    |
                 R2 becomes
                preferred
```

This is one of the most important real-world applications of object tracking.

# 29. Final Exam Memory

> **Object tracking connects network conditions to routing or FHRP behavior. It allows a router to react to failures that a simple local interface-state check may not detect.**

Remember:

```text
TRACK
  ↓
WATCH SOMETHING
  ↓
UP / DOWN
  ↓
FEATURE REACTS
```

And for FHRP:

```text
HSRP:
Track → Priority decrement

VRRP:
Track → Priority change

GLBP:
Track → Weighting decrement
```

The most important practical idea is:

> **Object tracking makes FHRP failover depend on actual network reachability or path health, not merely whether the local interface is physically up.**
