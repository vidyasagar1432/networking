# Policy-Based NAT

> **Level 15 · NAT** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

**Policy-Based NAT (Policy NAT)** applies NAT conditionally instead of translating all traffic that matches only a source address.

The NAT decision can be based on additional traffic characteristics such as:

- Source IP address
    
- Destination IP address
    
- Source/destination protocol and ports
    
- A route-map and its match conditions
    

This allows different traffic flows to use different NAT policies.

> **Core idea:** Policy NAT answers **“Which traffic should be translated, and how?”** rather than simply translating every matching inside source.

---

## 2. Regular NAT vs Policy NAT

### Regular source NAT

A typical source NAT rule matches only the inside source:

```cisco
access-list 1 permit 10.0.0.0 0.0.0.255

ip nat inside source list 1 interface GigabitEthernet0/1 overload
```

Conceptually:

```text
Source matches ACL
       │
       ▼
Translate
```

Every destination is treated the same unless additional NAT rules or mechanisms change the behavior.

---

### Policy NAT

Policy NAT adds additional conditions.

Conceptually:

```text
Source matches
      +
Destination / protocol / port matches
      │
      ▼
Apply selected NAT policy
```

Example use case:

```text
10.0.0.0/24 → ISP-A destinations → NAT using ISP-A address
10.0.0.0/24 → ISP-B destinations → NAT using ISP-B address
```

---

# 3. Why Policy NAT Is Used

Policy NAT is useful when different traffic flows require different translations.

Common scenarios include:

|Use Case|Purpose|
|---|---|
|Multi-ISP|Use different NAT policies for different traffic|
|Destination-specific NAT|Translate traffic only toward selected destinations|
|Service-specific NAT|Apply NAT based on TCP/UDP ports|
|Overlapping networks|Translate selected traffic between overlapping address spaces|
|VPN / special paths|Apply NAT selectively so specific traffic is translated or excluded|
|Multiple public address ranges|Assign different traffic classes to different pools|

---

# 4. ACL-Based Policy NAT

Policy NAT can use an extended ACL to match both source and destination information.

Example:

```cisco
access-list 101 permit ip 10.0.0.0 0.0.0.255 198.51.100.0 0.0.0.255

ip nat pool ISP-A 203.0.113.10 203.0.113.20 netmask 255.255.255.0

ip nat inside source list 101 pool ISP-A overload
```

The ACL matches:

```text
Source:
10.0.0.0/24

Destination:
198.51.100.0/24
```

Therefore, only traffic matching both conditions is eligible for this NAT rule.

---

## 4.1 Source + Destination Matching

Conceptually:

```text
             ┌─────────────────────┐
             │ Source = 10.0.0.0/24│
             └──────────┬──────────┘
                        │
                        ▼
             ┌─────────────────────┐
             │ Destination =       │
             │ 198.51.100.0/24     │
             └──────────┬──────────┘
                        │
                       YES
                        │
                        ▼
                 Apply NAT policy
```

Traffic from the same source to another destination may therefore use a different NAT rule or remain untranslated.

---

# 5. Policy NAT Using Ports

An extended ACL can also match protocol and Layer-4 ports.

Example:

```cisco
access-list 102 permit tcp 10.0.0.0 0.0.0.255 198.51.100.0 0.0.0.255 eq 443

ip nat pool HTTPS-PUBLIC 203.0.113.10 203.0.113.10 netmask 255.255.255.0

ip nat inside source list 102 pool HTTPS-PUBLIC overload
```

This policy matches:

```text
Source:
10.0.0.0/24

Destination:
198.51.100.0/24

Protocol:
TCP

Destination port:
443
```

This allows NAT behavior to be differentiated by application traffic.

> **Exam concept:** Extended ACLs give Policy NAT more granular matching than a standard source-only ACL.

---

# 6. Route-Map-Based NAT

Cisco IOS/IOS XE also supports NAT rules that reference a **route-map**.

The route-map determines whether the NAT rule applies based on its match conditions.

Example:

```cisco
route-map NAT-POLICY permit 10
 match ip address 101
```

The NAT rule can reference that route-map:

```cisco
ip nat inside source route-map NAT-POLICY interface GigabitEthernet0/1 overload
```

Conceptually:

```text
Packet
  │
  ▼
Route-map
  │
  ├── Match → YES → Apply NAT
  │
  └── No match → NAT rule does not apply
```

> **Important:** A route-map used for NAT is not simply a routing policy. In this context, it is being used to control NAT classification.

---

# 7. Route-Map Matching

A route-map can contain multiple match conditions.

For example:

```cisco
access-list 101 permit ip 10.0.0.0 0.0.0.255 198.51.100.0 0.0.0.255

route-map NAT-POLICY permit 10
 match ip address 101
```

The ACL defines the traffic that should match the route-map.

The NAT rule then references the route-map:

```cisco
ip nat inside source route-map NAT-POLICY interface GigabitEthernet0/1 overload
```

This provides a policy-driven way to decide which traffic is translated.

---

# 8. Multi-ISP Policy NAT

One important Policy NAT design is a router connected to multiple ISPs.

Example:

```text
                    ISP-A
                      │
                Gi0/1 │
                      │
                ┌─────┴─────┐
                │   Router  │
                └─────┬─────┘
                      │ Gi0/2
                      │
                    ISP-B
```

Inside network:

```text
10.0.0.0/24
```

Suppose traffic destined for one network should use ISP-A:

```text
10.0.0.0/24
      │
      ├── Destination A → NAT using ISP-A public address
      │
      └── Destination B → NAT using ISP-B public address
```

Separate NAT policies can classify the traffic.

Example:

```cisco
access-list 101 permit ip 10.0.0.0 0.0.0.255 198.51.100.0 0.0.0.255
access-list 102 permit ip 10.0.0.0 0.0.0.255 192.0.2.0 0.0.0.255
```

Then different NAT policies can be associated with the appropriate public addresses/interfaces.

> **Important:** NAT alone does not determine the complete forwarding path. Routing and NAT must be designed together. In multi-ISP designs, the return path must also be considered.

---

# 9. Policy NAT and Routing

Policy NAT should not be confused with policy-based routing (PBR).

|Feature|Policy NAT|PBR|
|---|---|---|
|Purpose|Control NAT translation|Control forwarding path|
|Main function|Change address/port information|Select next hop/interface|
|Uses|NAT rules, ACLs, route-maps|Route-maps|
|Changes packet addressing|Yes|Normally no|
|Changes routing decision|Not inherently|Yes|

A route-map can be involved in both technologies, but the purpose is different.

```text
Policy NAT:
"Should this packet be translated?"

PBR:
"Where should this packet be forwarded?"
```

---

# 10. Policy NAT and NAT Exemption

A common design requirement is:

```text
Internet traffic → NAT
VPN traffic → NO NAT
```

Policy NAT can be used to make NAT conditional.

For example:

```text
                 ┌── Internet → NAT
Inside hosts ────┤
                 └── VPN destination → No NAT
```

The exact configuration depends on the Cisco platform and NAT/VPN design.

> **Important:** Do not assume that every VPN requires Policy NAT. NAT exemption/identity NAT and platform-specific NAT behavior should be evaluated according to the actual VPN design.

---

# 11. Outside Source NAT

Policy NAT should be distinguished from **outside source NAT**.

Outside source NAT modifies the representation of an address belonging to the outside network.

Example:

```cisco
ip nat outside source static 203.0.113.99 198.51.100.99
```

Conceptually:

```text
Outside address
203.0.113.99
      │
      ▼
198.51.100.99
```

This is useful in designs involving:

- Overlapping address spaces
    
- Merging networks with duplicate addressing
    
- Certain VPN/partner connectivity designs
    

> **Important:** Outside source NAT is a NAT direction/type. It should not be treated as synonymous with Policy NAT.

---

# 12. Inside Source vs Outside Source NAT

|NAT Type|Address Being Translated|
|---|---|
|Inside source NAT|Inside host/source address|
|Outside source NAT|Outside host/source address|
|Static NAT|Fixed one-to-one mapping|
|Dynamic NAT|Dynamic address allocation|
|PAT|Uses Layer-4 identifiers to support overload|

Example:

```text
Inside Source NAT:

10.0.0.10
    ↓
203.0.113.10
```

Outside Source NAT:

```text
203.0.113.99
    ↓
198.51.100.99
```

# 13. Policy NAT vs Regular ACL NAT

|Aspect|Regular Source NAT|Policy NAT|
|---|---|---|
|Basic match|Source address|Source + additional conditions|
|Destination aware|No|Yes, when configured|
|Port aware|Limited by basic ACL|Yes, with extended matching|
|Selectivity|Lower|Higher|
|Multiple policies|Possible but less granular|Designed for conditional policies|
|Common use|General Internet NAT|Destination/application-specific NAT|

---

# 14. NAT Rule Selection

When multiple NAT rules could potentially match the same packet, the router must determine which applicable NAT rule should be used according to Cisco NAT processing rules.

Therefore, avoid creating overlapping NAT policies without understanding their interaction.

Example of a potentially problematic design:

```text
Rule 1:
10.0.0.0/24 → any destination → NAT

Rule 2:
10.0.0.0/24 → 198.51.100.0/24 → different NAT
```

The broad rule may interfere with the intended selective policy.

> **Best practice:** Make Policy NAT conditions sufficiently specific and verify the actual translation table and configuration.

# 15. NAT Direction Matters

For inside source NAT:

```text
ip nat inside source ...
```

For outside source NAT:

```text
ip nat outside source ...
```

These commands describe **which side's source address is being translated**, not simply where the packet physically enters the router.

Remember the terminology:

```text
Inside Local
Inside Global
Outside Local
Outside Global
```

Understanding these four addresses is essential for troubleshooting Policy NAT.

|Symptom|Possible Cause|Check|
|---|---|---|
|Traffic not translated|ACL does not match|`show access-lists`|
|Wrong public address|Incorrect NAT policy/pool|NAT configuration|
|Specific destination not translated|Destination ACL does not match|Extended ACL|
|Application traffic not translated|Protocol/port condition does not match|Extended ACL|

# 19. Common CCNP Exam Traps

### Trap 1 — Source-only ACL NAT is not the same as Policy NAT

```cisco
access-list 1 permit 10.0.0.0 0.0.0.255
```

This matches only the source address.

Policy NAT becomes useful when additional traffic characteristics are used to make the NAT decision.

---

### Trap 2 — Policy NAT is not the same as PBR

Both can use route-maps, but:

```text
Policy NAT → controls translation
PBR        → controls forwarding
```

---

### Trap 3 — Outside source NAT is not synonymous with Policy NAT

```cisco
ip nat outside source ...
```

defines the NAT direction/type.

It is commonly relevant to overlapping address designs, but it is conceptually separate from Policy NAT.

---

### Trap 4 — NAT does not automatically fix asymmetric routing

Policy NAT can help implement a multi-ISP design, but routing must still provide a valid and predictable return path.

```text
NAT policy ≠ routing policy
```

---

### Trap 5 — A broad NAT rule can interfere with selective policies

If a general NAT policy matches traffic before the intended selective behavior, the result may not be what you expect.

Always inspect the actual configuration and translations.

---

### Trap 6 — `match-in-vrf` is not the definition of Policy NAT

`match-in-vrf` is associated with specific NAT/VRF behavior. It should not be used as a generic explanation of Policy NAT.

```cisco

```

The policy applies only to traffic matching:

```text
Source:
10.0.0.0/24

Destination:
198.51.100.0/24
```

access-list 101 permit ip 10.0.0.0 0.0.0.255 198.51.100.0 0.0.0.255

# 23. One-Minute Summary

> **Policy NAT = conditional NAT.**

```text
Regular NAT:

Source matches
     │
     ▼
Translate


Policy NAT:

Source matches
     +
Destination / protocol / port matches
     │
     ▼
Translate according to policy
```

Remember:

- **Standard source NAT** can match primarily on the source address.
    
- **Policy NAT** makes NAT conditional on additional traffic characteristics.
    
- **Extended ACLs** can match source, destination, protocol, and ports.
    
- **Route-map-based NAT** can use route-map matching to control NAT.
    
- **Policy NAT is not the same as PBR.**
    
- **Outside source NAT is a separate NAT type**, often useful with overlapping address spaces.
    
- **NAT does not replace routing**; multi-ISP designs require correct forwarding and return paths.
    
- Always verify the actual result with:
    

```cisco
show ip nat translations
show ip nat statistics
show access-lists
show route-map
```
