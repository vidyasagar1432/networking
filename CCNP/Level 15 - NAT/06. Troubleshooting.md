# NAT Troubleshooting

> **Level 15 · NAT** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

NAT troubleshooting should follow a structured path:

**Interface classification → Rule matching → Translation creation → Forwarding → Return traffic**

Most NAT failures fall into these areas:

- Incorrect `ip nat inside` / `ip nat outside` interface assignment
    
- NAT rule or ACL does not match the traffic
    
- Dynamic pool exhaustion or incorrect pool configuration
    
- Translation is missing, expired, or not being created
    
- Routing or return-path problems
    
- Application/protocol-specific NAT behavior
    

> **CCNP Tip:** Do not assume that a NAT problem is an ALG problem just because ping works while an application fails. Verify NAT state, routing, ports, and protocol behavior first.

---

## 2. Core Troubleshooting Flow

### 2.1 Troubleshooting sequence

|Step|What to verify|Primary command|
|---|---|---|
|1|NAT inside/outside interfaces|`show ip nat statistics`|
|2|NAT rule/ACL matching traffic|`show access-lists`|
|3|Translation created|`show ip nat translations`|
|4|Routing and forwarding|`show ip route`|
|5|Return traffic|Ping/test from outside|
|6|Live NAT processing|`debug ip nat`|
|7|Application-specific behavior|Protocol/application testing|

A useful mental model is:

```text
Inside packet
     ↓
Is the ingress interface NAT inside?
     ↓
Does the NAT rule match?
     ↓
Can a translation be created?
     ↓
Is the packet routed toward the outside?
     ↓
Does return traffic reach the NAT device?
     ↓
Is the return packet reverse-translated?
```

## 3. Interface Classification Failures

NAT depends on identifying the interfaces involved in the translation.

```cisco
interface GigabitEthernet0/0
 ip nat inside

interface GigabitEthernet0/1
 ip nat outside
```

### Common problems

|Symptom|Possible cause|
|---|---|
|No translations|Interface not marked `ip nat inside` / `ip nat outside`|
|Some traffic is not translated|Traffic enters/exits through an incorrectly classified interface|
|Unexpected NAT behavior|Inside/outside roles are reversed or applied to the wrong interfaces|

Verify with:

```cisco
show ip nat statistics
```

> **CCNP Tip:** NAT is **direction-aware**. The inside/outside classification determines how IOS interprets the addresses involved in translation.

---

## 4. NAT Rule / ACL Matching Failures

For dynamic NAT and PAT, an ACL commonly identifies the inside local addresses eligible for translation.

Example:

```cisco
access-list 10 permit 192.168.10.0 0.0.0.255

ip nat inside source list 10 interface GigabitEthernet0/1 overload
```

### Common symptoms

|Symptom|Possible cause|
|---|---|
|No hosts translated|ACL does not match the source traffic|
|Some hosts translated|ACL scope is too narrow|
|Unexpected hosts translated|ACL permits addresses that should not be NATed|
|NAT rule appears correct but no translation|Wrong ACL, interface, direction, or routing|

Check ACL matches:

```cisco
show access-lists
```

Check the NAT configuration:

```cisco
show running-config | include ip nat
```

> **Important:** An ACL match does **not** by itself guarantee that NAT will occur. Interface classification, NAT rule configuration, pool availability, and forwarding must also be correct.

---

## 5. Dynamic NAT and Pool Exhaustion

Dynamic NAT allocates addresses from a configured pool.

Example:

```cisco
ip nat pool PUBLIC 203.0.113.10 203.0.113.20 netmask 255.255.255.0
ip nat inside source list 10 pool PUBLIC
```

Without overload, each inside host generally requires a separate translated address.

If the pool is exhausted:

```text
New inside hosts cannot obtain a translation.
```

### Dynamic NAT vs PAT

|Feature|Dynamic NAT|PAT / Overload|
|---|---|---|
|Translated address|Pool address|Usually one/few addresses|
|Port translation|No|Yes|
|Multiple hosts per public IP|Generally no|Yes|
|Pool exhaustion|Possible|Much less likely, but ports/resources can be exhausted|

Check pool utilization:

```cisco
show ip nat statistics
```

> **CCNP Tip:** Do not describe PAT as completely immune to exhaustion. PAT has a finite number of available translation resources, including ports and platform resources.

## 6. Translation Table and State

Use the translation table to determine whether NAT is actually creating state.

```cisco
show ip nat translations
```

Example:

```text
Pro Inside global      Inside local       Outside local      Outside global
--- 203.0.113.10:1025  192.168.10.10:1025 198.51.100.10:443 198.51.100.10:443
```

### What to look for

- Expected inside local address
    
- Expected inside global address
    
- Correct outside destination
    
- Correct protocol
    
- Correct TCP/UDP ports for PAT
    
- Whether the translation exists while the session is active
    

### Common problems

|Symptom|Possible cause|
|---|---|
|No translation|NAT rule/interface/routing problem|
|Translation disappears|NAT timeout or session termination|
|Unexpected translation|Incorrect NAT rule or traffic classification|
|Old translation remains|Session has not yet expired|

Clear translations when appropriate:

```cisco
clear ip nat translation *
```

> **Warning:** Clearing translations can terminate or disrupt active NAT sessions. Use it deliberately, especially on production devices.

## 7. ICMP and NAT

ICMP does not use TCP/UDP ports, but IOS NAT can still maintain translation state for ICMP.

For ICMP, the **ICMP identifier** can be used to distinguish sessions.

Therefore:

```text
"No ICMP translation because ICMP cannot be translated"
```

is incorrect.

Instead, if ICMP is not being translated, investigate:

- NAT interface classification
    
- NAT rule/ACL matching
    
- Routing
    
- Existing translation state
    
- ICMP filtering
    
- Platform/software behavior
    

Useful commands:

```cisco
show ip nat translations
show ip nat statistics
```

## 8. Return-Path and Routing Problems

A successful outbound translation does not guarantee successful end-to-end communication.

Example:

```text
Inside Host
192.168.10.10
     |
     | NAT
     ↓
203.0.113.10
     |
     ↓
Internet
     |
     ↓
Return traffic
     |
     ↓
NAT Router
     |
     ↓
192.168.10.10
```

The return traffic must be able to reach the NAT device.

Check routing:

```cisco
show ip route
```

Check the NAT translation:

```cisco
show ip nat translations
```

### Common return-path problems

|Symptom|Possible cause|
|---|---|
|Outbound request leaves but no reply|Missing/incorrect return route|
|Translation exists but session fails|Return traffic bypasses NAT device|
|Intermittent connectivity|Asymmetric routing|
|Inbound connection fails|Missing static NAT/PAT or filtering|

> **CCNP Tip:** NAT does not replace routing. Both the forward and return paths must be correct.

## 9. Inbound Connections

Distinguish between **return traffic for an existing outbound session** and an **unsolicited inbound connection**.

### Existing outbound session

If an inside host initiates the connection:

```text
Inside host → NAT → Outside server
Outside server → NAT → Inside host
```

The return traffic can use the existing dynamic NAT/PAT state.

A separate static NAT rule is not required merely because the return packet is inbound.

### Unsolicited inbound connection

If an external host initiates a connection toward an inside server, the inside server normally requires a static NAT or static PAT mapping.

Example:

```cisco
ip nat inside source static tcp 192.168.10.100 443 203.0.113.100 443
```

This allows an outside client to reach the inside server through the mapped address/port, assuming routing and security policy also permit it.

## 10. Static NAT / Static PAT Troubleshooting

For inbound services, verify:

```cisco
show ip nat translations
show running-config | include ip nat
```

Check:

- Correct inside local address
    
- Correct inside global address
    
- Correct protocol
    
- Correct TCP/UDP port
    
- Correct inside/outside interface classification
    
- Return routing
    
- ACL/firewall policy
    

> **Important:** NAT translation alone does not guarantee that a connection will succeed. Security policies, routing, and the server/application must also permit the traffic.

## 11. Application and Protocol Problems

If basic IP connectivity works but an application fails, investigate protocol-specific behavior.

Examples include:

- FTP
    
- SIP
    
- Certain embedded-address protocols
    
- Applications that dynamically negotiate additional connections
    
- Protocols affected by NAT traversal
    

### FTP

FTP can establish additional data connections depending on the FTP mode and protocol behavior.

If FTP fails while basic connectivity works, investigate:

- Active vs passive FTP
    
- NAT behavior
    
- Firewall/inspection policy
    
- Control/data connection handling
    

### SIP / RTP

SIP signaling and RTP media can be affected by:

- NAT
    
- Firewall policies
    
- SIP inspection/ALG behavior
    
- NAT traversal mechanisms
    
- Incorrect advertised addresses
    
- Asymmetric paths
    

> **CCNP Tip:** Do not memorize “SIP/RTP requires ALG.” NAT behavior depends on the platform, software version, application, and network design.

## 12. Debugging NAT

### Basic NAT debug

```cisco
debug ip nat
```

This provides real-time information about NAT processing.

Use it carefully on production devices because debugging can consume CPU and generate large amounts of output.

Stop debugging with:

```cisco
undebug all
```

or:

```cisco
no debug all
```

> **Exam Tip:** `debug ip nat` is useful for observing whether packets are actually being translated. Availability and syntax of more detailed debug options can vary by IOS/IOS XE release and platform.

## 14. Recommended Troubleshooting Procedure

### Scenario: Inside host cannot access an external server

#### Step 1 — Verify interfaces

```cisco
show ip nat statistics
```

Confirm the correct interfaces are identified as:

```text
Inside
Outside
```

#### Step 2 — Verify NAT configuration

```cisco
show running-config | include ip nat
```

Check:

- Static NAT
    
- Dynamic NAT
    
- PAT
    
- NAT pool
    
- ACL reference
    
- Correct interfaces
    

#### Step 3 — Verify ACL matching

```cisco
show access-lists
```

Confirm the inside source address is permitted.

#### Step 4 — Generate traffic

From the inside host:

```text
ping <outside-address>
```

Or test the actual application.

#### Step 5 — Check translations

```cisco
show ip nat translations
```

If no translation appears, investigate the NAT rule, ACL, interface classification, and routing.

#### Step 6 — Check NAT statistics

```cisco
show ip nat statistics
```

Look for:

- Active translations
    
- Hits
    
- Misses
    
- Pool utilization
    
- Inside/outside interfaces
    

#### Step 7 — Verify routing

```cisco
show ip route
```

Confirm the NAT router can reach the destination and that return traffic can reach the NAT router.

#### Step 8 — Use debug if necessary

```cisco
debug ip nat
```

Generate a small amount of test traffic and observe the result.

Then disable debugging:

```cisco
undebug all
```

## 15. Symptom → Cause → Verification

|Symptom|Likely cause|Verify with|
|---|---|---|
|Nothing translates|Incorrect interface classification|`show ip nat statistics`|
|Nothing translates|NAT ACL/rule does not match|`show access-lists`|
|Some hosts fail|ACL scope or NAT policy|`show access-lists`|
|Dynamic NAT fails for new hosts|Pool exhaustion|`show ip nat statistics`|
|PAT sessions fail under heavy load|Translation/port/resource exhaustion|NAT statistics/translations|
|Translation exists but application fails|Routing, filtering, ports, or application behavior|NAT table + routing + application test|
|Outbound works, return fails|Return-path/routing problem|`show ip route`|
|Unsolicited inbound connection fails|Missing static NAT/PAT or filtering|NAT config + ACL/firewall|
|Old translation remains|Session/timeout behavior|`show ip nat translations`|
|ICMP fails to translate|NAT matching/state/routing issue|NAT table + statistics|
|Ping works but application fails|Protocol/port/application-specific issue|Application test + NAT state|
|NAT behavior is intermittent|Asymmetric routing or state changes|Routing + NAT translations|
|NAT debug shows no translation|Packet does not match NAT conditions|`debug ip nat`|

## 16. Exam Traps

- **Check interface classification first.**
    
- NAT is **direction-aware** through inside/outside interface roles.
    
- A NAT ACL identifies traffic eligible for translation; an ACL hit alone does not prove successful NAT.
    
- **Dynamic NAT without overload can exhaust its address pool.**
    
- PAT can also exhaust available translation resources.
    
- **Return traffic for an existing outbound dynamic NAT/PAT session does not require a separate static mapping.**
    
- **Unsolicited inbound connections** normally require static NAT or static PAT.
    
- NAT does not replace routing; the return path must reach the NAT device.
    
- ICMP can be translated; it does not use TCP/UDP ports.
    
- `show ip nat translations` shows actual translation state.
    
- `show ip nat statistics` provides NAT counters, interfaces, and resource information.
    
- `show access-lists` helps determine whether the NAT ACL is matching traffic.
    
- `debug ip nat` provides live NAT processing information.
    
- Clear translations carefully because active sessions may be disrupted.
    
- Do not assume every application failure is caused by an ALG.
    
- Protocol-specific NAT behavior can depend on IOS/IOS XE version, platform, and application.

## 18. CCNP Troubleshooting Mindset

When troubleshooting NAT, ask these questions **in order**:

```text
1. Did the packet enter through the correct NAT inside interface?
2. Does the NAT rule match the packet?
3. Can IOS allocate/create the required translation?
4. Was the packet forwarded toward the correct destination?
5. Did the return packet reach the NAT device?
6. Did NAT reverse-translate the return traffic?
7. If IP connectivity works, is the application/protocol itself compatible with the NAT path?
```

> **Core idea:**  
> **NAT troubleshooting is not just “look for a translation.”**  
> Determine where the packet stops: **classification → matching → translation → forwarding → return traffic → application behavior**.
