# NAT64

> **Level 15 · NAT** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

**NAT64** enables **IPv6-only clients to communicate with IPv4-only servers** by translating traffic between IPv6 and IPv4.

A common NAT64 deployment combines:

- **IPv6-only clients**
    
- **DNS64**
    
- **Stateful NAT64 translator**
    
- **IPv4-only servers**
    

The basic flow is:

```text
IPv6 Client
    │
    │ IPv6
    ▼
 DNS64
    │
    │ Synthesizes AAAA
    ▼
NAT64 Translator
    │
    │ IPv4
    ▼
IPv4 Server
```

> **Key idea:** DNS64 creates an IPv6 destination that represents the IPv4 server, while NAT64 translates the resulting IPv6 traffic into IPv4.

---

# 2. Why NAT64 Is Needed

Consider an IPv6-only client:

```text
Client:
2001:db8:10::10
```

The client wants to reach an IPv4-only server:

```text
Server:
192.0.2.10
```

The client cannot directly send IPv6 traffic to an IPv4-only destination.

NAT64 provides the translation boundary:

```text
IPv6-only network
        │
        │ IPv6
        ▼
     NAT64
        │
        │ IPv4
        ▼
IPv4-only network
```

This allows IPv6-only networks to access legacy IPv4 services without requiring the client to have an IPv4 address.

---

# 3. NAT64 + DNS64

## 3.1 Why DNS64 Is Usually Needed

A normal IPv4-only DNS record may contain:

```text
A 192.0.2.10
```

An IPv6-only client normally requests an `AAAA` record.

If no native AAAA record exists, a **DNS64 resolver** can synthesize one.

For example:

```text
Original A record:

192.0.2.10
```

DNS64 can synthesize:

```text
64:ff9b::192.0.2.10
```

The exact textual representation can also appear as:

```text
64:ff9b::c000:020a
```

because:

```text
192.0.2.10
   │
   ▼
C0 00 02 0A
   │
   ▼
64:ff9b::c000:020a
```

The client therefore believes it is communicating with an IPv6 destination.

---

# 4. NAT64 Well-Known Prefix

The standardized **NAT64 Well-Known Prefix (WKP)** is:

```text
64:ff9b::/96
```

An IPv4 address is embedded in the final 32 bits.

Example:

```text
IPv4:

192.0.2.10
```

Binary/hex representation:

```text
192.0.2.10
C0 00 02 0A
```

NAT64 representation:

```text
64:ff9b::c000:20a
```

Conceptually:

```text
64:ff9b::/96
        +
    IPv4 address
```

> **Exam point:** `64:ff9b::/96` is the standard NAT64 Well-Known Prefix.

---

# 5. Stateful NAT64

**Stateful NAT64** maintains a translation state table.

Example:

```text
IPv6 client:

2001:db8:10::10:50000
          │
          │ NAT64
          ▼
IPv4 translator:

192.0.2.100:40000
          │
          ▼
IPv4 server:

198.51.100.10:443
```

The translator maintains state so that return traffic can be mapped back to the IPv6 client.

Conceptually:

```text
IPv6 flow
    │
    ▼
NAT64 state table
    │
    ▼
IPv4 flow
```

Stateful NAT64 can therefore support many IPv6 clients sharing a smaller IPv4 address pool.

---

# 6. Stateful NAT64 vs Stateless NAT64

|Feature|Stateful NAT64|Stateless NAT64|
|---|---|---|
|Translation state|Yes|No per-flow state|
|Address mapping|Many-to-few possible|Algorithmic/address-based|
|IPv4 address sharing|Yes|Generally no|
|Port translation|Common/required for address sharing|No stateful port multiplexing|
|Scalability|High|Depends on address mapping|
|Typical use|IPv6-only clients accessing IPv4 Internet|Controlled IPv6/IPv4 address mapping|

### Stateful

```text
Many IPv6 clients
       │
       ▼
NAT64 state
       │
       ▼
Smaller IPv4 pool
```

### Stateless

```text
IPv6 address
     │
     │ deterministic mapping
     ▼
IPv4 address
```

> **Important:** Stateless NAT64 is not simply “stateful NAT64 without a state table.” It uses algorithmic mappings and has different addressing requirements.

---

# 7. Stateful NAT64 Translation Example

Suppose:

```text
IPv6 Client:
2001:db8:10::10

IPv4 Server:
198.51.100.10
```

DNS64 synthesizes:

```text
64:ff9b::c633:640a
```

The client sends:

```text
2001:db8:10::10
        ↓
64:ff9b::c633:640a
```

The NAT64 translator recognizes the NAT64 prefix and extracts:

```text
198.51.100.10
```

It then creates an IPv4-side translation.

Conceptually:

```text
IPv6:

2001:db8:10::10
        │
        │ IPv6
        ▼
64:ff9b::c633:640a
        │
        │ NAT64
        ▼
198.51.100.10
        │
        │ IPv4
        ▼
IPv4 Server
```

Return traffic follows the state created by the translator.

---

# 8. DNS64 vs NAT64

These technologies perform different jobs.

|Technology|Function|
|---|---|
|DNS64|Synthesizes IPv6 AAAA records from IPv4 A records|
|NAT64|Translates IPv6 packets into IPv4 packets and vice versa|

Think:

```text
DNS64:
"Which IPv6 address should the client use?"

NAT64:
"How do I translate that IPv6 traffic into IPv4?"
```

Therefore:

```text
DNS64 ≠ NAT64
```

They are complementary technologies.

# 10. NAT64 Does Not Require DNS64

DNS64 is commonly deployed with NAT64, but the two are not technically identical.

If an application already knows a suitable synthesized IPv6 destination, NAT64 can perform the translation without DNS64.

However, for normal hostname-based applications on an IPv6-only client, DNS64 is commonly used to make IPv4-only destinations reachable.

---

# 11. NAT64 and IPv4 Address Pools

Stateful NAT64 may use an IPv4 pool for translated IPv4 source addresses.

Conceptually:

```text
IPv6 clients
     │
     ├── 2001:db8:10::10
     ├── 2001:db8:10::11
     └── 2001:db8:10::12
             │
             ▼
        NAT64 Translator
             │
             ▼
       IPv4 Pool
       192.0.2.100
       192.0.2.101
       192.0.2.102
```

The translator maintains state mapping IPv6 flows to IPv4 flows.

---

# 12. NAT64 vs NAT-PT

NAT64 is the modern IPv6/IPv4 translation architecture.

**NAT-PT (Network Address Translation - Protocol Translation)** was an earlier IPv4/IPv6 transition mechanism and was deprecated because of architectural and operational issues.

For CCNP-level learning:

```text
NAT-PT → historical/deprecated
NAT64  → modern IPv6/IPv4 translation
```

Do not treat NAT-PT and NAT64 as interchangeable technologies.

---

# 13. NAT64 and 464XLAT

**464XLAT** is a deployment architecture that uses two translation components:

```text
IPv6-only Client
       │
       │ CLAT
       ▼
IPv4-embedded IPv6
       │
       │ IPv6 network
       ▼
      PLAT
       │
       │ NAT64
       ▼
IPv4 Internet
```

The two major components are:

|Component|Function|
|---|---|
|CLAT|Customer-side IPv4-to-IPv6 translation|
|PLAT|Provider-side NAT64 translation|

464XLAT is particularly important in mobile networks where IPv6-only access networks still need to support IPv4 applications.

---

# 14. Inbound IPv4 → IPv6 Considerations

The primary NAT64 use case is:

```text
IPv6 client → IPv4 server
```

For unsolicited connections initiated from an IPv4 network toward an IPv6-only host, a normal stateful NAT64 deployment does not automatically provide a permanent inbound mapping.

A separate mechanism or explicit mapping/design is required if IPv4-initiated access to IPv6 services is needed.

> **Exam point:** Do not describe NAT64 as a general-purpose bidirectional replacement for dual-stack. Its classic use case is IPv6-only clients accessing IPv4 resources.

---

# 15. Application Considerations

NAT64 can affect applications that embed IP addresses or depend on protocol-specific behavior.

Potential concerns include:

- Applications embedding IPv4 literals
    
- Protocols that carry IP addresses inside payloads
    
- Some FTP modes
    
- Some SIP deployments
    
- Protocols that do not work correctly through address translation
    
- Applications that require IPv4-specific behavior
    

Modern applications should generally prefer DNS names and IPv6/IPv4-independent addressing rather than embedding literal addresses.

---

# 16. Fragmentation and MTU

IPv6 and IPv4 have different fragmentation behavior.

NAT64 translators must correctly handle differences between IPv6 and IPv4 packet processing.

Important considerations include:

- Path MTU
    
- ICMPv6 Packet Too Big
    
- IPv4 fragmentation
    
- Reassembly
    
- Transport-layer behavior
    

A NAT64 deployment should therefore have appropriate MTU and ICMP handling.

---

# 17. Routing Requirements

NAT64 requires correct routing on both sides.

The IPv6 network needs a route toward the NAT64 prefix:

```text
64:ff9b::/96
        │
        ▼
    NAT64 router
```

The NAT64 device needs IPv4 reachability toward the translated IPv4 destinations.

Conceptually:

```text
IPv6 routing:
64:ff9b::/96 → NAT64

IPv4 routing:
IPv4 destinations → IPv4 network
```

A correct NAT64 configuration alone does not guarantee connectivity.

# 18. Cisco Configuration

> **Platform and IOS XE release matter.** NAT64 commands are not identical across Cisco platforms/releases. Always verify the exact syntax against the platform documentation being used.

A conceptual stateful NAT64 configuration can involve:

```cisco
! IPv6 client-facing interface
interface GigabitEthernet0/0
 ipv6 address 2001:db8:10::1/64
 ipv6 enable
 nat64 enable

! IPv4 server-facing interface
interface GigabitEthernet0/1
 ip address 192.0.2.1 255.255.255.0
 nat64 enable

! NAT64 prefix
nat64 prefix stateful 64:ff9b::/96

! IPv4 translation pool
nat64 v4 pool NAT64-POOL 192.0.2.100 192.0.2.120
```

> **Important:** Treat this as a conceptual Cisco IOS XE example, not a universal configuration template. NAT64 feature syntax and support vary by IOS XE release and hardware/platform.

# 20. Troubleshooting Workflow

### Step 1 — Verify IPv6 connectivity

```cisco
show ipv6 interface brief
show ipv6 route
```

The client must be able to reach the NAT64 translator.

---

### Step 2 — Verify the NAT64 prefix

Confirm that the IPv6 route to:

```text
64:ff9b::/96
```

points toward the NAT64 translator.

---

### Step 3 — Verify DNS64

Check whether the client receives a synthesized AAAA record.

Example:

```text
AAAA:
64:ff9b::c633:640a
```

If the DNS response contains only an A record and no usable synthesized AAAA record, the IPv6-only client may not know how to reach the IPv4-only server.

---

### Step 4 — Verify IPv4 reachability

On the NAT64 side:

```cisco
show ip route
```

The translator must have a valid path to the IPv4 destination.

---

### Step 5 — Verify NAT64 translations

```cisco
show nat64 translations
```

Look for a translation corresponding to the IPv6 client and IPv4 destination.

---

### Step 6 — Verify statistics

```cisco
show nat64 statistics
```

Look for:

- Active translations
    
- Packets translated
    
- Errors
    
- Resource exhaustion
    

---

### Step 7 — Check MTU and ICMP

If small packets work but larger traffic fails, investigate:

```text
Path MTU
ICMPv6 Packet Too Big
IPv4 fragmentation
```

# 21. Troubleshooting Common Failures

|Symptom|Likely Cause|Check|
|---|---|---|
|IPv6 client cannot reach IPv4 server|NAT64 not functioning|NAT64 translations/statistics|
|No synthesized AAAA|DNS64 problem|DNS response|
|Client cannot reach synthetic IPv6 address|Missing route to NAT64 prefix|`show ipv6 route`|
|NAT64 translation exists but server unreachable|IPv4 routing problem|`show ip route`|
|Return traffic fails|State/routing issue|NAT64 state and routing|
|Large packets fail|MTU/fragmentation issue|PMTUD/ICMP|
|Application fails but ping works|Application/protocol compatibility|Application behavior|
|NAT64 resources exhausted|Too many active sessions|NAT64 statistics|
|IPv4 server cannot initiate connection|No appropriate inbound mapping/design|NAT64 architecture|

# 22. Common CCNP Exam Traps

### Trap 1 — DNS64 is not NAT64

```text
DNS64 → synthesizes AAAA records

NAT64 → translates IPv6/IPv4 packets
```

They commonly work together.

---

### Trap 2 — `64:ff9b::/96` is the NAT64 Well-Known Prefix

Remember:

```text
64:ff9b::/96
```

The IPv4 address is encoded in the final 32 bits.

---

### Trap 3 — NAT64 is not the same as PAT

Stateful NAT64 can use port translation to allow address sharing, but NAT64 translates between **IPv6 and IPv4 protocol/address families**.

PAT is an IPv4 NAT mechanism that uses Layer-4 identifiers to multiplex translations.

```text
PAT:
IPv4 → IPv4

NAT64:
IPv6 → IPv4
```

---

### Trap 4 — Stateful and stateless NAT64 are different

```text
Stateful:
Translation state is maintained.

Stateless:
Mapping is algorithmic and does not maintain per-flow state.
```

---

### Trap 5 — NAT64 does not automatically make IPv4-only clients reach IPv6 servers

Classic NAT64 is primarily:

```text
IPv6 → IPv4
```

If the requirement is:

```text
IPv4-only client → IPv6-only server
```

a different translation mechanism/design may be required.

---

### Trap 6 — DNS64 does not translate packets

DNS64 only changes the DNS answer.

```text
DNS64:
A → synthesized AAAA

NAT64:
IPv6 packet ↔ IPv4 packet
```

---

### Trap 7 — Routing is still required

You need:

```text
IPv6 route → NAT64 prefix
IPv4 route → IPv4 destination
```

NAT64 does not replace normal routing.

|Feature|Dual-Stack|NAT64|

> **NAT64 is primarily used to let IPv6-only clients reach IPv4-only resources.**  
> **Routing, DNS, MTU, and application compatibility still matter.**
