# iBGP

> **Level 12 · BGP** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

**iBGP** (Internal BGP) runs **between routers in the same AS** to carry BGP routes from
edge to edge without re-advertising them to the IGP. Because iBGP **does not change
next-hop** and applies a **split-horizon** rule, it needs special handling: a **full mesh**
of sessions, **next-hop-self** at eBGP boundaries, and either **route reflectors** or
**confederations** (notes 08–09) to scale beyond a handful of routers.

---

## 2. Core Concepts

### 2.1 Why iBGP exists

- eBGP routes at the edge would flood the IGP and lose attributes (local-pref, AS_PATH,
  MED) — the IGP can't carry BGP attributes.
- iBGP carries those attributes **within** the AS, keeping the IGP small.

### 2.2 The two iBGP rules (exam-critical)

| Rule | Consequence | Fix |
|------|-------------|-----|
| Next-hop is NOT changed | iBGP peers may not have a route to the next hop | `next-hop-self` at the eBGP boundary |
| iBGP-learned routes NOT re-advertised to iBGP | routes stop at the receiving router | full mesh / route reflector / confederation |

- Without `next-hop-self`, the next hop may be the eBGP neighbor's address — not reachable
  unless the IGP knows it.

### 2.3 Full mesh requirement

- Every iBGP speaker must peer with **every other** iBGP speaker (n(n-1)/2 sessions).
- A route received from one iBGP peer can then reach all others.
- At scale this explodes → **route reflectors (note 08)** and **confederations (note 09)**.

### 2.4 Basic iBGP configuration

```text
router bgp 65001
 neighbor 10.0.0.2 remote-as 65001      ! same AS = iBGP
 neighbor 10.0.0.2 next-hop-self        ! fix next hop at eBGP edge
```

- **remote-as identical** → iBGP session. No TTL=1 constraint; loopbacks are typical.
- `next-hop-self` is placed where eBGP routes enter the iBGP mesh.

### 2.5 Loop prevention

- **Within** the AS: a router does not re-advertise an iBGP-learned route to another iBGP
  peer (split horizon) — no routing loop inside the AS.
- **Out of the AS**: when advertising an iBGP-learned route to eBGP, the AS_PATH is
  prepended, so it can't loop back (note 04).

### 2.6 The synchronization rule (legacy, disabled by default)

- Old rule: don't advertise an iBGP route until the IGP carries it too.
- Disabled by default in modern IOS — the exam expects **synchronization off**.

## 3. Configuration / Commands

```text
show ip bgp summary
show ip bgp neighbors 10.0.0.2 advertised-routes
show ip bgp neighbors 10.0.0.2 received-routes
show ip bgp                          ! next hops visible
show ip bgp next-hop-resolution      ! recursion into IGP
```

## 4. Troubleshooting & common failures

| Symptom | Likely cause | Check |
|---------|--------------|-------|
| iBGP route not installed | next hop not in RIB | `show ip bgp` next-hop, `next-hop-self` |
| Route missing transit | split horizon (no full mesh) | session count |
| iBGP session flapping | update-source / identifier mismatch | `show ip bgp neighbors` |
| Recursion failure | IGP doesn't carry next hop | `show ip cef` / IGP table |
| eBGP route lost inbound | no next-hop-self on boundary | add it |

---

## 5. Exam Traps

- iBGP **AD = 200** (eBGP is 20).
- iBGP does **not** change the next-hop → `next-hop-self` required at the edge.
- **Split horizon:** iBGP-learned routes are not sent to other iBGP peers → full mesh or
  reflectors.
- **Synchronization is off** by default — don't expect it on.
- iBGP session = same `remote-as`; loopbacks + `update-source` typical.
