# EIGRP RTP (Reliable Transport Protocol)

> **Level 11 · EIGRP** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

**RTP (Reliable Transport Protocol)** is EIGRP's **own transport mechanism** for  
delivering EIGRP packets between neighbors.

Despite its name, RTP is **not TCP or UDP**. EIGRP uses RTP directly over IP and  
provides reliable delivery for selected EIGRP packet types through **sequence  
numbers, acknowledgments, and retransmissions**.

EIGRP is carried directly in IPv4 using:

```text
IP Protocol = 88
```

EIGRP commonly uses:

```text
224.0.0.10
```

for IPv4 multicast communication with EIGRP routers on the local network.

There are **no TCP or UDP ports** because EIGRP does not use TCP or UDP.

---

## 2. EIGRP Packet Types

EIGRP uses five major packet types:

|Packet|Reliable?|Primary Purpose|
|---|---|---|
|**Hello**|No|Neighbor discovery and keepalive|
|**Update**|Yes|Advertise routing/topology information|
|**Query**|Yes|Ask neighbors for a route during DUAL computation|
|**Reply**|Yes|Respond to an EIGRP query|
|**ACK**|No|Acknowledge receipt of a reliable packet|

### Easy Memory

```text
HELLO = unreliable
ACK   = unreliable

UPDATE = reliable
QUERY  = reliable
REPLY  = reliable
```

---

## 3. Reliable vs Unreliable Delivery

### 3.1 Reliable Packets

The following EIGRP packets require reliable delivery:

```text
Update
Query
Reply
```

EIGRP uses RTP mechanisms such as:

- Sequence numbers
    
- Acknowledgments
    
- Retransmissions
    
- Retransmission Timeout (RTO)
    
- SRTT (Smooth Round-Trip Time)
    

If a reliable packet is not acknowledged within the appropriate retransmission  
period, EIGRP can retransmit it to the affected neighbor.

---

### 3.2 Unreliable Packets

Hello packets do not use RTP reliable delivery.

This is intentional.

If a hello is lost, the next hello can arrive shortly afterward. There is no need  
to retransmit every hello.

ACK packets are also not themselves reliably acknowledged. An ACK confirms receipt  
of a reliable EIGRP packet.

---

## 4. Sequence Numbers and Acknowledgments

Reliable EIGRP packets use **sequence numbers** to track delivery.

Simplified process:

```text
Router A
   |
   | Update (Sequence Number)
   v
Router B
   |
   | ACK
   v
Router A
```

If Router A does not receive the expected acknowledgment:

```text
Reliable packet sent
       ↓
No ACK received
       ↓
RTO expires
       ↓
Packet retransmitted
```

This allows EIGRP to provide reliable delivery without using TCP.

---

## 5. RTP Is Not TCP

This is an important exam distinction.

```text
TCP
 └── Transport-layer protocol
     └── Uses TCP ports

EIGRP RTP
 └── EIGRP-specific transport mechanism
     └── Runs with EIGRP
     └── Uses IP protocol 88
     └── No TCP/UDP ports
```

Therefore:

> **EIGRP does not run over TCP or UDP.**

RTP is part of EIGRP's own packet-delivery mechanism.

---

## 6. Multicast and Unicast

EIGRP commonly uses IPv4 multicast:

```text
224.0.0.10
```

This address represents:

```text
All EIGRP Routers
```

### General behavior

```text
Neighbor discovery
        ↓
EIGRP Hello
        ↓
224.0.0.10 multicast
```

Reliable packets can initially be sent using multicast when appropriate.

However, when a reliable multicast packet is not acknowledged by a particular  
neighbor, EIGRP can **retransmit the packet individually to that neighbor**.

Therefore, do not memorize:

```text
Reliable = always unicast
```

or:

```text
Reliable = always multicast
```

Instead remember:

> EIGRP uses multicast when appropriate and can use unicast for neighbor-specific  
> delivery and retransmissions.

## 8. Hello and Hold Timers

EIGRP uses Hello packets to discover and maintain neighbors.

Common default values are:

|Interface/Network Type|Hello|Hold|
|---|--:|--:|
|Broadcast / many P2P interfaces|5 seconds|15 seconds|
|NBMA|60 seconds|180 seconds|

These are common defaults; exact behavior can vary by platform/interface type and  
configuration.

### Relationship

The hold timer is commonly:

```text
Hold = 3 × Hello
```

For example:

```text
5-second Hello
3 × 5 = 15-second Hold
```

and:

```text
60-second Hello
3 × 60 = 180-second Hold
```

---

## 9. EIGRP Timer Matching

Unlike OSPF, EIGRP neighbors do **not** require matching Hello intervals.

For example:

```text
Router A:
Hello = 5 sec
Hold  = 15 sec

Router B:
Hello = 10 sec
Hold  = 30 sec
```

An adjacency can still form if the other required EIGRP parameters match.

The important concept is:

> Each router advertises a hold time, and the receiving router uses that hold time  
> to determine how long it can go without hearing from the neighbor.

### Exam Trap

```text
OSPF:
Hello/Dead timers must match.

EIGRP:
Hello intervals do not have to match.
```

---

## 10. EIGRP K-Values

EIGRP neighbors must agree on the **K-values** used to calculate the metric.

If K-values do not match:

```text
K-values mismatch
      ↓
EIGRP adjacency does not form
```

Default classic EIGRP K-values are:

```text
K1 = 1
K2 = 0
K3 = 1
K4 = 0
K5 = 0
```

Therefore, by default, EIGRP's metric uses:

```text
Bandwidth
Delay
```

### Exam Comparison

```text
Hello timer mismatch
→ EIGRP adjacency can still form

K-value mismatch
→ EIGRP adjacency does NOT form
```

## 11. RTP and DUAL

RTP is closely connected to **DUAL**.

When DUAL needs a diffusing computation:

```text
Successor fails
      ↓
No Feasible Successor
      ↓
Route becomes Active
      ↓
DUAL sends Query
      ↓
RTP reliably delivers Query
      ↓
Neighbor processes Query
      ↓
Neighbor sends Reply
      ↓
RTP reliably delivers Reply
      ↓
DUAL completes computation
```

Therefore:

> **DUAL decides what routing information is needed; RTP provides the reliable  
> delivery mechanism for the EIGRP packets used to exchange that information.**

---

## 12. Passive vs Active

EIGRP route states are closely related to DUAL.

### Passive

```text
Passive
   ↓
Route is stable
```

A passive route is not currently undergoing a DUAL diffusing computation.

### Active

```text
Active
   ↓
DUAL is performing a diffusing computation
   ↓
Queries have been sent
   ↓
Replies are being awaited
```

RTP provides reliable delivery for the relevant Query and Reply packets.

---

## 13. SRTT and RTO

EIGRP maintains timing information for reliable communication with neighbors.

### SRTT

**SRTT (Smooth Round-Trip Time)** represents a smoothed estimate of the time  
required for communication with a neighbor.

### RTO

**RTO (Retransmission Timeout)** determines how long EIGRP waits before  
retransmitting a reliable packet when the expected acknowledgment has not arrived.

Conceptually:

```text
Packet sent
    ↓
Measure response time
    ↓
Maintain SRTT
    ↓
Calculate/use RTO
    ↓
Retransmit if required
```

Useful neighbor information can be viewed with:

```text
show ip eigrp neighbors
```

which can display values such as:

```text
SRTT
RTO
```

---

## 14. Neighbor Adjacency and RTP

A simplified EIGRP neighbor process is:

```text
Hello
  ↓
Neighbor discovered
  ↓
EIGRP parameters checked
  ↓
Adjacency established
  ↓
Routing information exchanged
  ↓
Reliable Update packets as required
  ↓
DUAL maintains routes
```

The neighbor relationship depends on more than just receiving Hellos.

Important parameters include:

- EIGRP AS/process relationship
    
- K-values
    
- Network/interface compatibility
    
- Authentication, when configured
    
- Primary addressing/network configuration
    
- EIGRP packet communication

## 15. Troubleshooting

### 15.1 Neighbor Flapping

Possible causes:

- Packet loss
    
- Interface instability
    
- Physical problems
    
- Congestion
    
- Hold timer expiration
    
- Incorrect network/interface configuration
    

Check:

```text
show ip eigrp neighbors
show ip eigrp interfaces
```

---

### 15.2 Reliable Packet Retransmissions

Possible causes:

- Packet loss
    
- Congestion
    
- One-way communication
    
- Neighbor instability
    
- Interface problems
    

Check:

```text
show ip eigrp neighbors
show ip eigrp traffic
```

Pay attention to:

```text
SRTT
RTO
retransmission activity
```

Do not assume that changing RTO manually is the normal fix; EIGRP uses its  
measured timing information to determine retransmission behavior.

---

### 15.3 No EIGRP Neighbors

Possible causes include:

- Incorrect EIGRP configuration
    
- K-value mismatch
    
- Incorrect AS/process configuration
    
- Authentication mismatch
    
- Interface/network problems
    
- EIGRP packets being filtered
    
- Multicast communication problems
    
- Protocol 88 being blocked
    

Useful commands:

```text
show ip eigrp neighbors
show ip eigrp interfaces
show ip protocols
```

---

### 15.4 SIA

**Stuck-in-Active (SIA)** occurs when an EIGRP route remains Active because required  
query processing/replies do not complete within the expected time.

Possible causes include:

- Unreachable neighbors
    
- Excessive query propagation
    
- Network instability
    
- Congested/overloaded routers
    
- Problems preventing Query/Reply communication
    

Useful commands:

```text
show ip eigrp topology active
show ip eigrp neighbors
show ip eigrp traffic
```

Important:

> SIA is primarily a **DUAL query/reply problem**. Do not describe it simply as  
> an “RTP failure.”

## 18. Exam Traps

### Trap 1 — Protocol 88 vs Port

EIGRP uses:

```text
IP Protocol 88
```

It does **not** use:

```text
TCP port 88
UDP port 88
```

---

### Trap 2 — RTP Is Not TCP

RTP provides EIGRP-specific reliable delivery.

```text
EIGRP → IP protocol 88 → RTP mechanisms
```

It does not mean:

```text
EIGRP → TCP
```

---

### Trap 3 — Reliable Packet Types

Remember:

```text
Reliable:
    Update
    Query
    Reply

Unreliable:
    Hello
    ACK
```

---

### Trap 4 — ACK Is Unreliable

The ACK itself does not require an ACK.

```text
Update
   ↓
ACK
```

The ACK confirms receipt of the reliable packet.

---

### Trap 5 — EIGRP Hello Timers Do Not Have to Match

Unlike OSPF:

```text
EIGRP Hello timers do not need to match.
```

The receiving router uses the hold time advertised by its neighbor.

---

### Trap 6 — K-Values Must Match

```text
K-value mismatch
      ↓
No EIGRP adjacency
```

Do not confuse this with Hello timer behavior.

---

### Trap 7 — 224.0.0.10

The common IPv4 EIGRP multicast address is:

```text
224.0.0.10
```

It represents the EIGRP router multicast group on the local network.

Do not assume every EIGRP packet is always multicast.

---

### Trap 8 — SIA Is Not Simply “RTP Failed”

```text
SIA
 ↓
DUAL query/reply process does not complete
```

RTP provides reliable delivery mechanisms for EIGRP packets, but SIA is fundamentally  
a DUAL/query-domain convergence problem.

---

## 19. RTP vs DUAL

These two concepts are easy to confuse.

|Feature|RTP|DUAL|
|---|---|---|
|Full name|Reliable Transport Protocol|Diffusing Update Algorithm|
|Main purpose|EIGRP packet delivery|Route calculation/convergence|
|Reliability|Provides reliable delivery|Uses routing information|
|Sequence numbers|Yes|Uses topology/route state|
|ACKs|Yes|Not its primary function|
|Retransmission|Yes|No|
|Queries|Carries/delivers them reliably|Generates/processes them|
|Replies|Carries/delivers them reliably|Generates/processes them|
|Loop-free path selection|No|Yes|
|Feasible successor|No|Yes|
|Active/Passive|Supports packet exchange involved|Determines route state|

### Memory Trick

```text
DUAL = Decides
RTP  = Delivers
```

Or:

```text
DUAL → What path should I use?
RTP  → Did my EIGRP packet get there?
```
