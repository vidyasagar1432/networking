# EIGRP Variance (Unequal-Cost Load Balancing)

> **Level 11 · EIGRP** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

**`variance`** allows EIGRP to install multiple **unequal-metric paths** to the same destination, providing **unequal-cost load balancing**.

Unlike protocols such as traditional OSPF path selection, EIGRP can use multiple paths even when their metrics are different, provided the candidate paths satisfy EIGRP's loop-free and installation requirements.

The two key requirements are:

1. The candidate path must satisfy the **feasibility condition**.
    
2. The candidate path's metric must fall within the configured **variance** relative to the successor.
    

The default is:

```text
variance 1
```

which permits normal equal-cost multipath behavior.

---

# 2. Core Concepts

## 2.1 Successor and Feasible Successor

Before understanding variance, distinguish:

### Successor

The **successor** is the best loop-free path to the destination.

Its metric becomes the route's **Feasible Distance (FD)**.

### Feasible Successor

A **feasible successor** is a backup path that satisfies EIGRP's feasibility condition:

```text
RD < FD
```

Where:

- **RD** = Reported Distance from the neighbor
    
- **FD** = local Feasible Distance
    

This condition guarantees that the neighbor is closer to the destination than the local router's current feasible distance and provides the loop-free property.

---

## 2.2 Variance Rule

For a candidate path to participate in unequal-cost load balancing, its metric must satisfy:

```text
metric(candidate) <= variance × metric(successor)
```

and it must satisfy the feasibility condition:

```text
RD(candidate) < FD(successor)
```

Therefore:

```text
Candidate eligible
    =
Feasibility condition satisfied
    AND
Variance metric bound satisfied
```

### Example

Suppose:

```text
Successor FD = 100
```

and:

```text
variance 2
```

Then the maximum candidate metric allowed by variance is:

```text
2 × 100 = 200
```

A candidate with metric:

```text
150
```

can potentially be installed if:

```text
RD < 100
```

A candidate with metric:

```text
250
```

fails the variance requirement because:

```text
250 > 200
```

---

# 3. Worked Example

Consider:

```text
Successor A:
    FD = 100

Candidate B:
    metric = 150
    RD = 60

Candidate C:
    metric = 300
    RD = 120
```

Configure:

```text
variance 2
```

The variance limit is:

```text
2 × 100 = 200
```

### Candidate B

Variance:

```text
150 <= 200
```

Feasibility:

```text
60 < 100
```

Therefore:

```text
B → eligible
```

### Candidate C

Variance:

```text
300 > 200
```

Therefore:

```text
C → not eligible
```

It also fails the feasibility condition:

```text
120 > 100
```

So:

```text
Successor A → installed
Candidate B  → installed
Candidate C  → excluded
```

---

# 4. Variance Values

## `variance 1`

```text
variance 1
```

This is the default.

It does not provide unequal-cost load balancing.

Only paths with the same metric as the successor can qualify through the variance calculation.

Therefore:

```text
variance 1
    ↓
equal-cost multipath
```

---

## `variance 2`

```text
variance 2
```

A candidate path can have a metric up to:

```text
2 × successor metric
```

provided it also satisfies the feasibility condition.

Example:

```text
Successor = 100
Variance  = 2

Maximum candidate metric = 200
```

---

## `variance 3`

```text
variance 3
```

Maximum candidate metric:

```text
3 × successor metric
```

Again, the feasibility condition must still be satisfied.

---

# 5. Variance Does Not Override Loop Prevention

This is one of the most important ENCOR exam points.

Increasing variance does **not** make an unsafe path usable.

For example:

```text
Successor FD = 100
Candidate metric = 150
Candidate RD = 120
variance = 2
```

Variance check:

```text
150 <= 200
```

Passes.

But feasibility check:

```text
120 < 100
```

Fails.

Therefore:

```text
Candidate → NOT eligible
```

Even though its metric falls within the variance range.

### Core rule

> **Variance controls the acceptable metric range; the feasibility condition preserves loop freedom.**

---

# 6. Variance and Feasible Successors

A candidate path can be considered for unequal-cost installation only if it satisfies EIGRP's feasibility requirements.

Think of the process as:

```text
              Candidate Path
                    │
                    ↓
          Feasibility Condition
              RD < FD ?
             /        \
           No          Yes
           │            │
           ↓            ↓
        Reject      Variance Check
                         │
                  Metric <=
                  Variance × FD ?
                    /       \
                  No         Yes
                  │           │
                  ↓           ↓
               Reject      Eligible
```

This is the cleanest way to remember the relationship.

---

# 7. `maximum-paths`

Variance determines **which unequal-cost paths may qualify**.

`maximum-paths` determines **how many paths can be installed**.

Example:

```text
topology base
 variance 3
 maximum-paths 4
```

Conceptually:

```text
variance
   ↓
Which candidate paths qualify?

maximum-paths
   ↓
How many qualifying paths may be installed?
```

Therefore, increasing variance does not necessarily mean that every qualifying route will appear in the routing table.

The maximum-path limit still applies.

---

# 8. Example with `maximum-paths`

Suppose EIGRP finds:

```text
Successor      = 100
Candidate B    = 120
Candidate C    = 140
Candidate D    = 180
Candidate E    = 190
Candidate F    = 200
```

Configure:

```text
variance 2
maximum-paths 4
```

Variance limit:

```text
2 × 100 = 200
```

All listed candidates fall within the metric limit.

However:

```text
maximum-paths 4
```

limits the number of paths installed according to the platform's EIGRP path-selection rules.

Therefore:

> **Variance controls eligibility; maximum-paths controls the number of installed paths.**

---

# 9. Traffic Distribution

When EIGRP installs unequal-cost paths, forwarding can use multiple next hops.

Do **not** memorize that EIGRP always distributes traffic using a strict inverse-metric mathematical ratio.

Actual traffic distribution depends on the router's forwarding implementation and CEF/load-sharing behavior.

The important ENCOR concept is:

```text
Equal-cost paths
    → equal-cost multipath behavior

Unequal-cost EIGRP paths
    → unequal-cost load balancing
```

The actual packet distribution may not exactly match the theoretical inverse-metric ratio.

# 10. Configuration

In named EIGRP, `variance` is configured under:

```text
address-family
    ↓
topology base
```

Example:

```text
router eigrp CAMPUS
 address-family ipv4 unicast autonomous-system 100
  topology base
   variance 2
   maximum-paths 4
  exit-af-topology
 exit-address-family
```

For IPv6:

```text
router eigrp CAMPUS
 address-family ipv6 unicast autonomous-system 100
  topology base
   variance 2
   maximum-paths 4
  exit-af-topology
 exit-address-family
```

The same fundamental variance concept applies to both IPv4 and IPv6 EIGRP.

---

# 11. Classic EIGRP Configuration

In classic EIGRP, the command is configured under the EIGRP routing process:

```text
router eigrp 100
 variance 2
 maximum-paths 4
```

Named mode moves these settings into the appropriate:

```text
topology base
```

configuration.

---

# 12. Relationship with the Routing Table

When qualifying paths are installed, the routing table can contain multiple next hops for the same destination.

Example conceptually:

```text
D    10.10.10.0/24
     [90/100] via 10.1.1.2
            via 10.1.2.2
```

The exact output depends on the platform and routing configuration.

The important concept is:

```text
One destination
      ↓
Multiple qualifying EIGRP paths
      ↓
Multiple next hops
```

---

# 13. Relationship with the Topology Table

The topology table is important when troubleshooting variance.

Use:

```text
show ip eigrp topology
```

or named-mode address-family commands where supported.

Look for:

- Successor
    
- Feasible Distance
    
- Reported Distance
    
- Candidate paths
    
- Feasible successors
    

A candidate may exist in the topology table but still not be installed because:

- It fails the feasibility condition
    
- Its metric is outside the variance range
    
- `maximum-paths` limits installation
    
- Another route-selection condition prevents installation

# 14. Troubleshooting

|Symptom|Likely Cause|Check|
|---|---|---|
|Unequal path not installed|Candidate fails feasibility|Check RD vs FD|
|Unequal path not installed|Variance too low|Check `variance`|
|Too few paths installed|`maximum-paths` limit|Check `maximum-paths`|
|Candidate metric too high|Outside variance range|Compare metric with variance × successor FD|
|Candidate looks good but is rejected|Not feasible|Verify `RD < FD`|
|Expected ECMP not present|Different metrics|Check EIGRP metrics|
|Load sharing seems uneven|Forwarding/load-sharing behavior|Check CEF and forwarding behavior|
|Paths change after metric modification|Topology recalculation|Check EIGRP topology|

# 17. Exam Traps

### Trap 1 — Variance does not replace feasibility

Wrong:

```text
variance 10
```

therefore every path up to 10× the successor is usable.

Correct:

```text
Feasibility condition
        +
Variance condition
        +
Maximum-paths
```

all determine whether a path can be installed.

---

### Trap 2 — Use RD, not Administrative Distance

Do not confuse:

```text
RD = Reported Distance
```

with:

```text
AD = Administrative Distance
```

The EIGRP feasibility condition is:

```text
RD < FD
```

Administrative Distance is a separate route-source preference mechanism.

---

### Trap 3 — `variance 1`

```text
variance 1
```

is the default and does not enable unequal-cost load balancing.

It permits normal equal-cost multipath behavior.

---

### Trap 4 — Variance does not determine the number of paths

Remember:

```text
variance
    ↓
qualifying metric range

maximum-paths
    ↓
maximum number of installed paths
```

---

### Trap 5 — Higher variance does not guarantee more paths

A higher variance only expands the metric range.

A candidate can still fail because:

```text
RD >= FD
```

or because:

```text
maximum-paths
```

limits installation.

---

### Trap 6 — EIGRP does not guarantee a simple inverse-metric traffic ratio

Do not memorize:

```text
Metric 100 vs 200
→ exactly 2:1 traffic
```

as a universal forwarding rule.

The exact traffic distribution depends on the forwarding implementation.

---

### Trap 7 — Variance is an EIGRP feature

EIGRP is well known for supporting **unequal-cost load balancing**.

This is one of its major distinctions from protocols that normally install only equal-cost paths.

# 19. One-Minute Mental Model

Think of EIGRP variance as a **two-stage filter**:

```text
                     Candidate Path
                           │
                           ↓
                  ┌─────────────────┐
                  │ Feasibility     │
                  │    RD < FD      │
                  └────────┬────────┘
                           │
                    Pass   │   Fail
                     │     │
                     ↓     └────────→ Reject
              ┌─────────────────┐
              │ Variance Check  │
              │ Metric <=       │
              │ Variance × FD   │
              └────────┬────────┘
                       │
                Pass   │   Fail
                 │     │
                 ↓     └──────────→ Reject
          Candidate eligible
                 │
                 ↓
          maximum-paths
                 │
                 ↓
        Installed next hops
```

### Core ENCOR formula

> **EIGRP Variance = Feasibility (`RD < FD`) + Metric Bound (`metric ≤ variance × successor FD`) + `maximum-paths`**

### Key commands

```text
router eigrp CAMPUS
 address-family ipv4 unicast autonomous-system 100
  topology base
   variance 2
   maximum-paths 4
  exit-af-topology
 exit-address-family
```

Remember:

```text
variance
   ↓
How far from the successor metric can a candidate be?

maximum-paths
   ↓
How many qualifying paths can be installed?
```
