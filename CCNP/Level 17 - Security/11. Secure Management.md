# Secure Management

> **Level 17 · Security** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

**Secure management** protects the interfaces and protocols used to administer network  
devices. The goal is to ensure management traffic is:

- **Encrypted**
    
- **Authenticated**
    
- **Authorized**
    
- **Restricted to trusted sources**
    
- **Audited/logged**
    
- **Separated from normal user traffic where appropriate**
    

For ENCOR, know the relationship between the **management plane**, secure management  
protocols, **AAA**, management ACLs, and management-network isolation.

The preferred management choices are:

> **SSH instead of Telnet · HTTPS instead of HTTP · SNMPv3 instead of SNMPv1/v2c ·  
> SCP instead of TFTP/FTP**

---

# 2. Management Plane

A network device can be viewed as having three logical planes:

|Plane|Purpose|Typical Protection|
|---|---|---|
|**Data plane**|Forwards user traffic|ACLs, infrastructure security|
|**Control plane**|Processes routing/control protocols|CoPP|
|**Management plane**|Device administration and monitoring|SSH, HTTPS, AAA, ACLs, SNMPv3|

### Management-plane traffic includes

- SSH
    
- HTTPS
    
- SNMP
    
- Syslog
    
- NTP
    
- SCP
    
- Other device-management protocols
    

> **Key distinction:** CoPP protects the **control plane** from excessive traffic destined  
> for the device CPU. Secure management protects **administrative access** to the device.

---

# 3. Secure Management Protocols

## 3.1 CLI Management

|Protocol|Port|Security|Recommendation|
|---|--:|---|---|
|Telnet|23|Unencrypted|Avoid|
|**SSH**|**22**|**Encrypted**|**Preferred**|

SSH encrypts the management session and protects credentials and commands from  
being transmitted in clear text.

Use:

```cisco
ip ssh version 2
```

Restrict VTY lines:

```cisco
line vty 0 15
 transport input ssh
```

---

## 3.2 Web Management

|Protocol|Port|Security|Recommendation|
|---|--:|---|---|
|HTTP|80|Unencrypted|Avoid|
|**HTTPS**|**443**|**TLS encrypted**|Preferred when web management is required|

Enable HTTPS:

```cisco
ip http secure-server
```

If HTTP is not required:

```cisco
no ip http server
```

If HTTPS management is also unnecessary:

```cisco
no ip http secure-server
```

### Important

`ip http secure-server` enables HTTPS. It does **not** automatically mean that the  
plain HTTP server is disabled.

---

# 4. SNMP Security

SNMP is commonly used for monitoring and management.

|Version|Security|
|---|---|
|SNMPv1|Community string; no encryption|
|SNMPv2c|Community string; no encryption|
|**SNMPv3**|Authentication and optional privacy/encryption|

Prefer **SNMPv3** for secure management.

SNMPv3 security levels include:

|Level|Authentication|Encryption|
|---|---|---|
|`noAuthNoPriv`|No|No|
|`authNoPriv`|Yes|No|
|`authPriv`|Yes|**Yes**|

> **Exam point:** `authPriv` provides both authentication and privacy/encryption.

Do not expose SNMP management unnecessarily to untrusted networks.

---

# 5. Secure File Transfer

|Protocol|Security|Use|
|---|---|---|
|TFTP|Unencrypted|Legacy/simple transfer|
|FTP|Unencrypted credentials/data|Avoid for sensitive management|
|**SCP**|**SSH-based encrypted transfer**|Preferred Cisco file transfer|
|SFTP|SSH-based secure transfer|Platform-dependent|

For ENCOR, remember:

> **SCP is preferred over TFTP/FTP when secure file transfer is required.**

SCP is commonly used for transferring:

- IOS/IOS XE images
    
- Configuration files
    
- Other device files

# 6. Restricting VTY Access

A secure VTY configuration should restrict both the **protocol** and the **source  
addresses**.

Example:

```cisco
access-list 99 permit 10.10.10.0 0.0.0.255
!
line vty 0 15
 transport input ssh
 access-class 99 in
 login local
 exec-timeout 5 0
```

This provides several protections:

|Configuration|Purpose|
|---|---|
|`transport input ssh`|Prevents Telnet access|
|`access-class 99 in`|Restricts source addresses|
|`login local`|Uses local username database|
|`exec-timeout 5 0`|Disconnects idle sessions|

### Important distinction

`access-class` on a VTY line controls **who can access the management line**.

It is different from an interface ACL used to filter normal transit traffic.

# 7. AAA for Secure Management

AAA provides:

- **Authentication** — Who are you?
    
- **Authorization** — What are you allowed to do?
    
- **Accounting** — What management activity was recorded?
    

Enable AAA:

```cisco
aaa new-model
```

Example authentication method list:

```cisco
aaa authentication login DEFAULT group tacacs+ local
```

Apply it to VTY lines:

```cisco
line vty 0 15
 login authentication DEFAULT
 transport input ssh
```

### Authorization

Command authorization can be configured separately:

```cisco
aaa authorization commands 15 DEFAULT group tacacs+ local
```

This controls authorization for privilege-level 15 commands through the configured  
AAA method list.

### Accounting

EXEC accounting:

```cisco
aaa accounting exec DEFAULT start-stop group tacacs+
```

Command accounting can also be configured when command-level auditing is required.

> **Exam point:** Authentication, authorization, and accounting are separate AAA  
> functions. Configuring authentication alone does not automatically provide command  
> accounting.

---

# 8. Local Fallback Authentication

Centralized AAA servers may become unavailable, so a local fallback account can be  
configured.

Example:

```cisco
username admin privilege 15 secret StrongAdminPassword
!
aaa authentication login DEFAULT group tacacs+ local
```

The method list attempts TACACS+ first and then uses the local database if the  
configured AAA method permits fallback.

> **Important:** AAA fallback behavior depends on the method list and the response  
> from the AAA server. Do not assume every AAA failure automatically behaves identically.

---

# 9. Restrict HTTPS Management

The IOS HTTP/HTTPS server can be restricted to trusted management sources.

Example:

```cisco
access-list 99 permit 10.10.10.0 0.0.0.255
!
ip http access-class 99 in
ip http secure-server
no ip http server
```

This provides:

1. **HTTPS encryption**
    
2. **Source-address restriction**
    
3. **No plain HTTP access**
    

Verify:

```cisco
show ip http server status
```

# 10. Management VLAN

A dedicated **management VLAN** separates device-management traffic from normal  
user VLANs.

Example design:

```text
             Management Network
                    |
              +-----+-----+
              |  Switch   |
              +-----+-----+
                    |
          +---------+---------+
          |                   |
        Router              Switch
       Management           Management
          IP                   IP
```

Benefits:

- Reduces exposure to user networks
    
- Simplifies management ACLs
    
- Provides centralized management policy
    
- Makes monitoring and troubleshooting easier
    

A management VLAN is **logical isolation**, not complete physical isolation.

---

# 11. Out-of-Band Management

**Out-of-band (OOB) management** uses a separate management network from the  
production/data network.

Conceptually:

```text
Production Network
       |
   Data Ports
       |
   +---+---+
   |Device |
   +---+---+
       |
 Management Port
       |
 Separate OOB Network
```

Advantages:

- Management remains reachable even when the production network has problems.
    
- Management traffic is separated from normal user/data traffic.
    
- Provides stronger isolation than simply placing management interfaces in a  
    production VLAN.
    

> **Exam concept:** OOB management is a form of **separate management-path isolation**.

---

# 12. Management ACLs

Management ACLs should allow only trusted administrative networks.

Example:

```cisco
ip access-list standard MGMT
 permit 10.10.10.0 0.0.0.255
 deny any
```

Apply to VTY:

```cisco
line vty 0 15
 access-class MGMT in
 transport input ssh
```

Apply to HTTP/HTTPS management when appropriate:

```cisco
ip http access-class MGMT in
```

### Security principle

> **Allow management access from trusted sources; deny unnecessary management access  
> from everywhere else.**

# 13. Secure SSH Baseline

A simplified SSH configuration:

```cisco
hostname R1
ip domain-name example.local
!
username admin privilege 15 secret StrongAdminPassword
!
crypto key generate rsa modulus 2048
ip ssh version 2
!
line vty 0 15
 login local
 transport input ssh
 exec-timeout 5 0
```

With a management ACL:

```cisco
ip access-list standard MGMT
 permit 10.10.10.0 0.0.0.255
 deny any
!
line vty 0 15
 access-class MGMT in
 login local
 transport input ssh
 exec-timeout 5 0
```

Verify:

```cisco
show ip ssh
show line
```

# 14. Secure Management and Device Hardening

Secure management overlaps heavily with **Device Hardening**, but the focus is  
different.

|Device Hardening|Secure Management|
|---|---|
|Reduce overall attack surface|Protect administrative access|
|Disable unnecessary services|Use secure management protocols|
|Secure console/AUX|SSH/HTTPS/SNMPv3|
|Login protection|AAA|
|Password protection|Management ACLs|
|Shut unused interfaces|Management VLAN/OOB|
|Security baseline|Secure management architecture|

Think of it this way:

> **Device hardening = secure the device.**  
> **Secure management = secure how administrators manage the device.**

# 16. Troubleshooting

|Symptom|Likely Cause|Check|
|---|---|---|
|SSH connection refused|SSH not configured or VTY does not permit SSH|`show ip ssh`, VTY configuration|
|Telnet still works|VTY permits Telnet|`transport input ssh`|
|SSH source rejected|VTY `access-class` blocks source|Check management ACL|
|Local login fails|Local user/AAA method problem|Check `username` and AAA|
|TACACS+ unavailable|AAA server/connectivity issue|Check AAA server and local fallback|
|HTTPS unavailable|HTTPS server disabled|`show ip http server status`|
|HTTP still available|HTTP server still enabled|`no ip http server`|
|SNMP exposed|Broad SNMP access|Restrict SNMP sources|
|SNMP credentials visible|SNMPv1/v2c community strings|Use SNMPv3|
|Management VLAN unreachable|VLAN/routing/ACL problem|Check VLAN, gateway, ACL|
|OOB unavailable|Separate management-path failure|Check OOB network|
|Idle session remains|No/long `exec-timeout`|Configure timeout|

# 17. Common Exam Traps

### Trap 1 — Telnet vs SSH

```text
Telnet → insecure
SSH    → secure
```

For secure CLI management, choose **SSH**.

---

### Trap 2 — HTTP vs HTTPS

```text
HTTP  → unencrypted
HTTPS → TLS encrypted
```

If web management is required, prefer **HTTPS**.

---

### Trap 3 — SNMPv2c vs SNMPv3

```text
SNMPv1/v2c → community strings, no encryption
SNMPv3     → authentication/privacy options
```

For secure monitoring, choose **SNMPv3**.

---

### Trap 4 — SNMPv3 Security Level

```text
noAuthNoPriv → no authentication, no encryption
authNoPriv   → authentication, no encryption
authPriv     → authentication + encryption
```

**`authPriv` is the strongest of the three SNMPv3 security levels.**

---

### Trap 5 — `access-class`

```cisco
line vty 0 15
 access-class MGMT in
```

`access-class` controls **source access to the VTY line**.

It does not replace an interface ACL for normal data-plane traffic.

---

### Trap 6 — HTTPS Does Not Automatically Disable HTTP

```cisco
ip http secure-server
```

enables HTTPS.

If HTTP is not required, explicitly use:

```cisco
no ip http server
```

---

### Trap 7 — AAA Functions Are Separate

Remember:

```text
Authentication  → Who are you?
Authorization   → What can you do?
Accounting      → What was recorded?
```

Authentication alone does not automatically provide command accounting.

---

### Trap 8 — Management VLAN vs OOB

A management VLAN provides **logical separation**.

OOB management provides a **separate management path/network**.

OOB generally provides stronger isolation and can remain available when the production  
network is unavailable.

---

### Trap 9 — SCP vs TFTP

```text
TFTP → unencrypted
SCP  → SSH-based encrypted transfer
```

For secure file transfer, prefer **SCP**.
