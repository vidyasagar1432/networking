# Infrastructure Security

> **Level 17 · Security** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

**Infrastructure security** protects the network infrastructure itself — routers, switches,  
routing protocols, control-plane resources, Layer-2 infrastructure, and management  
interfaces.

The objective is to prevent:

- Source-address spoofing
    
- ARP/DHCP attacks
    
- Rogue routing updates
    
- Unauthorized routing sessions
    
- MAC-address abuse
    
- STP attacks
    
- Control-plane exhaustion
    
- Management-plane abuse
    
- IPv6 infrastructure attacks
    

For ENCOR, understand **which security mechanism protects which part of the  
infrastructure**.

---

# 2. Infrastructure Security Model

|Infrastructure Target|Threat|Primary Defense|
|---|---|---|
|Edge router|IP source spoofing|uRPF / ACLs|
|WAN edge|Bogon/private-source traffic|Anti-spoofing ACLs|
|Routing protocols|Unauthorized peers/updates|Protocol authentication|
|BGP sessions|Spoofed TCP packets|TCP MD5 / TTL Security|
|Access switches|Rogue DHCP|DHCP Snooping|
|Access switches|ARP spoofing|DAI|
|Access switches|IP spoofing|IP Source Guard|
|Access ports|Unauthorized MACs|Port Security|
|Switch links|Broadcast/multicast/unicast floods|Storm Control|
|STP infrastructure|Rogue BPDUs|BPDU Guard / Root Guard|
|Device CPU|Control-plane floods|CoPP|
|Management plane|Unauthorized administration|AAA / SSH / ACLs|
|IPv6 access layer|Rogue RA/DHCPv6|RA Guard / DHCPv6 Guard|

# 3. Anti-Spoofing with uRPF

**Unicast Reverse Path Forwarding (uRPF)** validates the source address of an incoming  
packet against the routing information available on the device.

The basic idea:

> **Can the device reach the packet's source address through an acceptable path?**

---

## 3.1 Strict uRPF

Example:

```cisco
interface GigabitEthernet0/0
 ip verify unicast source reachable-via rx
```

Strict mode requires the best reverse path to the source address to point out the  
**same interface on which the packet arrived**.

### Best suited for

- Symmetric routing
    
- Customer/edge environments where the expected return path is known
    

### Problem

Strict uRPF can drop legitimate traffic when routing is **asymmetric**.

---

## 3.2 Loose uRPF

Conceptually:

```cisco
interface GigabitEthernet0/0
 ip verify unicast source reachable-via any
```

Loose mode only requires that the source address be reachable through **some interface**  
according to the routing table.

It does not require the reverse path to use the incoming interface.

### Best suited for

- Networks with asymmetric routing
    
- Multihomed environments
    
- Situations where strict reverse-path validation would incorrectly drop legitimate  
    traffic
    

---

## 3.3 Strict vs Loose

|Mode|Requirement|Main Concern|
|---|---|---|
|**Strict (`rx`)**|Reverse path uses incoming interface|Breaks asymmetric routing|
|**Loose (`any`)**|Source is reachable through any interface|Less restrictive|

### Exam trap

> **Asymmetric routing → strict uRPF can cause legitimate traffic drops.**

---

## 3.4 uRPF Verification

```cisco
show ip verify source
show ip interface | include verify
```

The exact output and verification commands can vary by IOS/IOS XE platform.

# 4. Anti-Spoofing ACLs

ACLs can block packets with invalid or unacceptable source addresses at the network  
edge.

Typical Internet-edge filtering includes:

- RFC1918 private source addresses
    
- Bogon/unallocated ranges where appropriate
    
- The organization's own prefixes appearing as Internet source addresses
    
- Other source addresses that should never legitimately arrive from that interface
    

Example concept:

```cisco
ip access-list extended WAN-IN
 deny ip 10.0.0.0 0.255.255.255 any
 deny ip 172.16.0.0 0.15.255.255 any
 deny ip 192.168.0.0 0.0.255.255 any
 permit ip any any
!
interface GigabitEthernet0/0
 ip access-group WAN-IN in
```

> This is only a simplified example. Production anti-spoofing ACLs must account for  
> the actual topology, legitimate traffic, IPv6, and provider/customer requirements.

### Important

Anti-spoofing filters are normally applied **inbound** on an interface where traffic  
from an untrusted network enters.

---

# 5. Directed Broadcast Protection

Routers should not normally forward directed broadcasts.

Modern Cisco IOS/IOS XE platforms generally disable IP directed broadcasts by default,  
but explicit hardening may be seen:

```cisco
interface GigabitEthernet0/0
 no ip directed-broadcast
```

Directed broadcasts can be abused in amplification attacks.

---

# 6. Routing-Protocol Security

Routing protocols must be protected against unauthorized peers and forged routing  
messages.

Common mechanisms include:

|Protocol|Security Mechanisms|
|---|---|
|OSPF|Authentication|
|EIGRP|Authentication|
|BGP|TCP MD5, TTL Security|
|IS-IS|Authentication|

Authentication helps ensure that routing messages originate from an authorized peer.

---

# 7. OSPF Authentication

OSPF can authenticate routing protocol packets.

Example concept:

```cisco
interface GigabitEthernet0/0
 ip ospf authentication message-digest
 ip ospf message-digest-key 1 md5 OSPFSecret
```

This enables OSPF message-digest authentication on the interface.

The exact OSPF authentication syntax can vary depending on the OSPF version and  
platform.

### Exam point

OSPF authentication protects against unauthorized or forged OSPF routing messages.

---

# 8. EIGRP Authentication

EIGRP supports authentication using key chains.

Example concept:

```cisco
key chain EIGRP-KEYS
 key 1
  key-string EIGRPSecret
!
interface GigabitEthernet0/0
 ip authentication key-chain eigrp 100 EIGRP-KEYS
```

Depending on IOS/IOS XE and EIGRP mode, authentication mechanisms can include  
MD5 or HMAC-SHA-256.

### Exam point

Know the relationship:

```text
Key chain
   ↓
Authentication key
   ↓
EIGRP neighbor authentication
```

---

# 9. BGP Security

BGP sessions can be protected using:

1. **TCP MD5 authentication**
    
2. **TTL Security (GTSM)**
    

---

## 9.1 BGP TCP MD5

Example:

```cisco
router bgp 65001
 neighbor 192.0.2.2 remote-as 65002
 neighbor 192.0.2.2 password BgpSecret
```

The password enables TCP MD5 authentication for the BGP TCP session.

### What it protects

TCP MD5 helps prevent unauthorized parties from successfully injecting TCP segments  
into the authenticated BGP session.

> It should not be described as independently "encrypting BGP." TCP MD5 provides  
> authentication/integrity protection, not confidentiality.

---

## 9.2 BGP TTL Security / GTSM

Example:

```cisco
router bgp 65001
 neighbor 192.0.2.2 ttl-security hops 1
```

**Generalized TTL Security Mechanism (GTSM)** uses the IP TTL value to help ensure that  
BGP packets originate within the expected hop distance.

It is particularly useful for protecting directly connected eBGP sessions from  
spoofed packets arriving from farther away.

### Important distinction

|Mechanism|Purpose|
|---|---|
|TCP MD5|Authenticates/protects TCP session segments|
|TTL Security|Restricts acceptable hop distance|

> **TTL Security is not an authentication mechanism.**

# 10. Layer-2 Infrastructure Security

The access layer is vulnerable to attacks involving:

- DHCP
    
- ARP
    
- IP source addresses
    
- MAC addresses
    
- STP
    
- Broadcast/multicast/unicast floods
    

Cisco provides several complementary controls.

---

# 11. DHCP Snooping

**DHCP Snooping** builds a binding database by inspecting DHCP traffic.

The binding information can contain:

```text
MAC address
IP address
VLAN
Interface
Lease information
```

Example:

```cisco
ip dhcp snooping
ip dhcp snooping vlan 10
!
interface GigabitEthernet0/1
 ip dhcp snooping trust
```

Typically:

- **Trusted ports** → DHCP server/uplink path
    
- **Untrusted ports** → Client-facing access ports
    

DHCP Snooping helps prevent rogue DHCP servers and provides bindings used by other  
security features.

---

# 12. Dynamic ARP Inspection (DAI)

**DAI** protects against ARP spoofing and ARP poisoning.

It validates ARP packets against trusted information, commonly the DHCP Snooping  
binding database.

Example:

```cisco
ip dhcp snooping
ip dhcp snooping vlan 10
ip arp inspection vlan 10
!
interface GigabitEthernet0/1
 ip dhcp snooping trust
 ip arp inspection trust
```

### Main purpose

> **DAI → protects against ARP spoofing.**

---

# 13. IP Source Guard (IPSG)

**IP Source Guard** restricts the source IP/MAC information that an access port can use.

It commonly relies on DHCP Snooping bindings.

Example:

```cisco
interface GigabitEthernet0/10
 ip verify source
```

### Main purpose

> **IPSG → helps prevent IP source-address spoofing at the access layer.**

---

# 14. Relationship Between DHCP Snooping, DAI, and IPSG

```text
                 DHCP Snooping
                       |
              Binding Database
                /             \
               /               \
             DAI               IPSG
              |                 |
        ARP validation      IP validation
```

|Feature|Primary Protection|
|---|---|
|DHCP Snooping|Rogue DHCP|
|DAI|ARP spoofing|
|IPSG|IP source spoofing|

### Exam trap

Not every access-layer security feature depends on DHCP Snooping.

For example:

- Port Security does not depend on DHCP Snooping.
    
- Storm Control does not depend on DHCP Snooping.
    
- BPDU Guard does not depend on DHCP Snooping.
    

---

# 15. Port Security

Port Security limits which source MAC addresses can use a switch port.

Example:

```cisco
interface GigabitEthernet0/10
 switchport mode access
 switchport port-security
 switchport port-security maximum 2
```

Possible violation modes include:

```text
protect
restrict
shutdown
```

### Main purpose

> **Port Security → controls unauthorized MAC addresses on an access port.**

It is more accurate to describe it as **MAC-address access control** rather than simply  
"MAC-flood protection."

---

# 16. Storm Control

Storm Control limits excessive Layer-2 traffic such as:

- Broadcast
    
- Multicast
    
- Unknown unicast
    

Example:

```cisco
interface GigabitEthernet0/10
 storm-control broadcast level 10.00
```

### Main purpose

> **Storm Control → limits Layer-2 traffic storms and protects switch resources.**

---

# 17. STP Infrastructure Protection

Spanning Tree can also be attacked or accidentally disrupted.

Important mechanisms include:

|Feature|Purpose|
|---|---|
|BPDU Guard|Protects edge/PortFast ports from unexpected BPDUs|
|Root Guard|Prevents a port from becoming an unexpected STP root path|
|PortFast|Quickly transitions an edge port to forwarding|
|Loop Guard|Helps prevent certain STP loops caused by unidirectional failures|

### BPDU Guard

Typically used on edge/access ports.

If an unexpected BPDU is received, the port can be placed into an error-disabled  
state.

### Root Guard

Prevents an interface from accepting superior BPDUs that could cause an unexpected  
device to become the STP root.

---

# 18. Control Plane Protection with CoPP

**Control Plane Policing (CoPP)** protects the device CPU/control plane from excessive  
traffic.

CoPP can police traffic destined for the control plane, such as:

- Routing protocols
    
- Management traffic
    
- ICMP
    
- Other traffic requiring CPU processing
    

Conceptually:

```text
Incoming traffic
       |
       v
   Classification
       |
       v
   CoPP Policy
    /      \
 allow     police/drop
       |
       v
    CPU / Control Plane
```

Example structure:

```cisco
class-map match-any ROUTING-PROTOCOLS
 match protocol ospf
!
policy-map COPP-POLICY
 class ROUTING-PROTOCOLS
  police 1000000 conform-action transmit exceed-action drop
!
control-plane
 service-policy input COPP-POLICY
```

Exact CoPP syntax and supported match criteria vary by IOS/IOS XE platform.

Verify:

```cisco
show policy-map control-plane
show control-plane
```

### Main purpose

> **CoPP → protects the device CPU/control plane from excessive traffic.**

---

# 19. CoPP vs Infrastructure ACLs vs uRPF

These controls solve different problems.

|Control|Main Question|
|---|---|
|Edge ACL|Should this traffic/source be allowed?|
|uRPF|Is this source reachable through an acceptable path?|
|CoPP|How much traffic should reach the control plane/CPU?|
|DAI|Is this ARP information valid?|
|IPSG|Is this source IP/MAC permitted on this access port?|
|DHCP Snooping|Is this DHCP behavior legitimate?|

# 20. Management-Plane Protection

Infrastructure security also includes protecting device administration.

Use:

- AAA
    
- SSH
    
- HTTPS
    
- SNMPv3
    
- Management ACLs
    
- Dedicated management VLANs
    
- OOB management
    
- Secure logging/NTP
    

Example:

```cisco
line vty 0 15
 transport input ssh
 access-class MGMT in
```

Management security is covered in greater detail under **Secure Management** and  
**Device Hardening**.

# 21. IPv6 Infrastructure Security

IPv6 introduces additional infrastructure-security concerns.

Important controls include:

|Threat|Defense|
|---|---|
|Rogue Router Advertisements|RA Guard|
|Rogue DHCPv6 server|DHCPv6 Guard|
|IPv6 source spoofing|IPv6 ACL/source validation|
|Neighbor Discovery attacks|IPv6 security mechanisms / inspection features|
|IPv6 routing attacks|Routing-protocol authentication|

### Exam point

Do not assume IPv4-only security mechanisms automatically protect IPv6.

IPv6 has its own Neighbor Discovery and Router Advertisement security considerations.

# 23. Troubleshooting

|Symptom|Likely Cause|Check|
|---|---|---|
|Legitimate packets dropped|Strict uRPF with asymmetric routing|Check routing/reverse path|
|Spoofed source accepted|Missing uRPF/edge ACL|Check inbound filtering|
|BGP session fails|MD5/password mismatch|Check neighbor password|
|BGP packets rejected|TTL Security mismatch|Check `ttl-security` / hop count|
|OSPF neighbors fail|Authentication mismatch|Check OSPF authentication|
|Rogue DHCP server works|DHCP Snooping missing/misconfigured|Check trusted ports|
|ARP spoofing succeeds|DAI missing/misconfigured|Check DAI|
|Client spoofs IP|IPSG missing/misconfigured|Check source guard|
|Unauthorized MAC works|Port Security absent/misconfigured|Check port-security|
|Broadcast storm affects switch|Storm Control absent/threshold too high|Check storm-control|
|Rogue switch becomes root|Root Guard absent|Check STP protection|
|Unexpected BPDU on access port|BPDU Guard absent|Check edge-port protection|
|CPU becomes overloaded|Missing/incorrect CoPP|Check control-plane policy|
|Routing protocol packets dropped|CoPP policing too aggressive|Check policy counters|
|IPv6 rogue RA succeeds|RA Guard absent|Check IPv6 access-layer security|

# 24. Common Exam Traps

### Trap 1 — Strict vs Loose uRPF

```text
Strict → reverse path must use incoming interface
Loose  → source must be reachable through any interface
```

Asymmetric routing is the classic **strict uRPF trap**.

---

### Trap 2 — BGP MD5 vs TTL Security

```text
TCP MD5     → authenticates/protects TCP session
TTL Security→ restricts packet hop distance
```

Neither should be described as general-purpose encryption of BGP traffic.

---

### Trap 3 — DHCP Snooping Dependency

DAI and IPSG commonly use DHCP Snooping bindings.

But:

```text
Port Security ≠ DHCP Snooping
Storm Control ≠ DHCP Snooping
BPDU Guard   ≠ DHCP Snooping
Root Guard   ≠ DHCP Snooping
```

---

### Trap 4 — DAI vs IPSG

```text
DAI  → ARP security
IPSG → IP source security
```

---

### Trap 5 — CoPP vs ACL

An ACL can filter traffic based on configured match criteria.

CoPP specifically protects the **control plane/CPU** by policing traffic destined  
for that plane.

---

### Trap 6 — Port Security

Port Security is primarily about **MAC-address control on switch ports**.

Do not define it only as "MAC flood protection."

---

### Trap 7 — Management Plane vs Control Plane

```text
Management plane → SSH, HTTPS, SNMP, administration
Control plane    → routing protocols / CPU processing
```

CoPP protects the control plane; secure management protects administrative access.

---

### Trap 8 — IPv4 vs IPv6

IPv6 introduces security considerations such as:

```text
RA Guard
DHCPv6 Guard
IPv6 ACLs
Neighbor Discovery protection
```

Do not assume an IPv4-only security configuration automatically secures IPv6.
