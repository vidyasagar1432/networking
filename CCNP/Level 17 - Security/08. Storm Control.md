# Storm Control

> **Level 17 · Security** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

**Storm Control** is a Layer 2 switchport protection feature that monitors and limits excessive **broadcast, multicast, and unknown-unicast** traffic.

It helps prevent a traffic storm from consuming switch and LAN resources when excessive flooded traffic is caused by:

- Layer 2 loops
    
- Network misconfigurations
    
- Faulty devices
    
- Excessive broadcast/multicast traffic
    
- Certain types of malicious traffic
    

Storm Control operates at the **interface level**.

> **Important:** Storm Control limits the effects of excessive flooded traffic; it does **not** eliminate the underlying Layer 2 loop. STP is responsible for preventing Layer 2 loops.

---

# 2. The Traffic Storm Problem

Normally, a switch floods certain frames when it does not know the appropriate destination port.

Examples include:

```text
Broadcast
     ↓
Flood within VLAN
     ↓
Multiple switchports
```

A Layer 2 loop can cause this traffic to circulate repeatedly:

```text
          +---------+
          | Switch1 |
          +----+----+
             ↙   ↘
           ↙       ↘
     +------+       +------+
     | SW2  |───────| SW3  |
     +------+       +------+
```

The result can be:

```text
Broadcast/Multicast/Unknown Unicast
                ↓
             Flooding
                ↓
          More flooding
                ↓
        Resource exhaustion
```

Storm Control limits the amount of these traffic classes that can pass through a switchport.

---

# 3. What Storm Control Monitors

Storm Control can protect against excessive:

|Traffic Type|Meaning|Typical Risk|
|---|---|---|
|**Broadcast**|Frames sent to `FF:FF:FF:FF:FF:FF`|Broadcast storms|
|**Multicast**|Multicast frames|Multicast flooding|
|**Unknown unicast**|Unicast destination not in the MAC table|Unknown-unicast flooding|

### Important

Storm Control does **not** normally limit known unicast traffic.

For example:

```text
Known Unicast
     ↓
MAC table knows destination
     ↓
Forward to specific port
```

This is different from:

```text
Unknown Unicast
     ↓
Destination MAC unknown
     ↓
Flood within VLAN
```

---

# 4. Broadcast Storm

A broadcast frame is intended for all devices in the local broadcast domain.

Example:

```text
PC1
 │
 │ Broadcast
 ▼
Switch
 ├── PC2
 ├── PC3
 ├── PC4
 └── PC5
```

If a loop causes broadcast traffic to circulate repeatedly, the amount of traffic can grow rapidly.

Storm Control can limit broadcast traffic entering/leaving a protected interface.

---

# 5. Multicast Storm

Multicast traffic can also be flooded when the switch does not have the appropriate multicast forwarding information.

Excessive multicast traffic can consume:

- Interface bandwidth
    
- Switch forwarding resources
    
- Host resources
    

Storm Control can limit multicast traffic according to the configured threshold.

---

# 6. Unknown-Unicast Storm

Unknown-unicast traffic occurs when a switch receives a frame for a destination MAC address that is **not currently known in the MAC address table**.

The switch may flood the frame within the VLAN.

Example:

```text
Destination MAC:
aaaa.bbbb.9999

MAC table:
No entry

        ↓

Unknown Unicast
        ↓
Flood within VLAN
```

Excessive unknown-unicast traffic can therefore contribute to a traffic storm.

---

# 7. Storm Control Thresholds

Storm Control can use different measurement methods depending on the Cisco platform and IOS release.

Common concepts include:

```text
Percentage of interface bandwidth
Packets per second (pps)
Bits per second (bps)
```

### Percentage

Example concept:

```text
storm-control broadcast level 50
```

The threshold represents a percentage of the interface's bandwidth, where supported by the platform.

### Packets Per Second

Example concept:

```text
storm-control multicast level pps 500
```

The threshold is based on the number of packets received per second.

### Bits Per Second

Example concept:

```text
storm-control unicast level bps 20m
```

The threshold is based on traffic rate in bits per second.

> **Platform note:** Exact threshold syntax and supported measurement methods vary between Cisco IOS/IOS XE platforms. Use `?` on the target switch to verify the available syntax.

---

# 8. Rising and Falling Thresholds

Storm Control can support two thresholds:

```text
Rising threshold
Falling threshold
```

This provides **hysteresis**.

Example:

```text
Rising threshold  → 50%
Falling threshold → 30%
```

Conceptually:

```text
Traffic
  │
50% ─────────────── Rising threshold
  │       ↓
  │   Suppression
  │
30% ─────────────── Falling threshold
  │       ↓
  │   Normal behavior
  │
  └──────────────────────── Time
```

This prevents the switch from repeatedly enabling and disabling suppression when traffic fluctuates around a single threshold.

---

# 9. Basic Configuration

Example:

```text
interface GigabitEthernet0/1
 storm-control broadcast level 50
 storm-control multicast level 50
 storm-control unicast level 50
```

This configures storm-control thresholds for:

```text
Broadcast
Multicast
Unknown unicast
```

A rising/falling threshold can be specified where supported:

```text
interface GigabitEthernet0/1
 storm-control broadcast level 50 30
```

Conceptually:

```text
50% → begin suppression
30% → stop suppression
```

> Always verify the exact syntax supported by the switch platform and IOS/IOS XE release.

---

# 10. Storm Control Actions

Storm Control can have different actions depending on platform and configuration.

Common actions include:

```text
shutdown
trap
```

### Default Suppression Behavior

The normal storm-control mechanism **suppresses traffic exceeding the configured threshold** while leaving the interface operational.

Conceptually:

```text
Traffic below threshold
        ↓
Forward normally

Traffic above threshold
        ↓
Suppress excessive traffic
        ↓
Interface remains operational
```

---

# 11. `action trap`

Example:

```text
interface Gi0/1
 storm-control action trap
```

This generates an **SNMP notification/trap** when storm-control conditions are detected, where supported.

The important distinction is:

```text
trap
 ↓
Notification to management system
```

It does **not** mean the port is shut down.

Storm-control suppression can continue according to the configured behavior.

---

# 12. `action shutdown`

Example:

```text
interface Gi0/1
 storm-control action shutdown
```

When the configured storm-control condition triggers the shutdown action, the interface can be placed into an **err-disabled** state.

Conceptually:

```text
Storm detected
     ↓
Threshold exceeded
     ↓
Shutdown action
     ↓
Interface err-disabled
```

The interface may require manual or configured automatic recovery.

---

# 13. Combining Actions

On platforms that support it, actions can be combined:

```text
storm-control action shutdown trap
```

This can provide:

```text
Shutdown
   +
SNMP notification
```

> Command availability varies by Cisco platform/IOS release.

---

# 14. Suppression vs Shutdown

This is an important exam distinction.

|Behavior|Result|
|---|---|
|**Normal suppression**|Excess traffic is dropped/suppressed; port remains up|
|**Trap**|Management notification is generated|
|**Shutdown**|Port can become err-disabled|

Remember:

```text
Suppress → control traffic
Trap     → notify management
Shutdown → disable interface
```

---

# 15. Storm Control and STP

Storm Control and STP solve different problems.

### STP

STP prevents Layer 2 loops by blocking redundant paths.

```text
Redundant link
      ↓
STP
      ↓
Blocking
      ↓
Loop prevented
```

### Storm Control

Storm Control limits excessive flooded traffic.

```text
Excessive flood traffic
        ↓
Storm Control
        ↓
Traffic suppressed
```

### Important

Storm Control does **not** replace STP.

If a loop exists:

```text
STP → prevents the loop
Storm Control → limits the resulting flood traffic
```

They can therefore complement each other.

---

# 16. Storm Control vs DAI vs IPSG vs Port Security

These security features have different purposes.

|Feature|Main Protection|
|---|---|
|**Port Security**|Source MAC restrictions|
|**DHCP Snooping**|DHCP protection + trusted bindings|
|**DAI**|ARP spoofing protection|
|**IPSG**|Source IP/MAC validation|
|**Storm Control**|Excessive flooded traffic|

Think:

```text
Port Security
      ↓
Who can use this port?

DHCP Snooping
      ↓
Which IP/MAC bindings are trusted?

DAI
      ↓
Is this ARP information legitimate?

IPSG
      ↓
Is this source IP/MAC authorized?

Storm Control
      ↓
Is excessive flood traffic occurring?
```

---

# 17. Storm Control vs CoPP

Storm Control and **Control Plane Policing (CoPP)** protect different areas.

|Feature|Scope|Main Purpose|
|---|---|---|
|**Storm Control**|Interface/data-plane traffic|Limit excessive flooded traffic|
|**CoPP**|Control plane|Protect the switch/router CPU|

Example:

```text
Broadcast storm
      ↓
Storm Control
```

versus:

```text
Excessive traffic destined to CPU
      ↓
CoPP
```

Do not confuse the two.

---

# 18. Storm Control and Layer 2 Loops

A common scenario:

```text
          Switch A
          /      \
         /        \
      Switch B──Switch C
```

If STP fails to prevent the loop, broadcast/multicast/unknown-unicast traffic can circulate.

Storm Control can reduce the impact:

```text
Layer 2 loop
     ↓
Flood traffic
     ↓
Storm Control
     ↓
Excess traffic suppressed
```

However:

> **Storm Control is a mitigation mechanism, not a loop-prevention mechanism.**

The root cause should still be investigated and corrected using STP/L2 troubleshooting.

# 20. Troubleshooting

|Symptom|Likely Cause|Check|
|---|---|---|
|Broadcast traffic is being dropped|Broadcast threshold exceeded|`show storm-control`|
|Multicast traffic is being dropped|Multicast threshold exceeded|Storm-control status|
|Unknown unicast is being dropped|Unknown-unicast threshold exceeded|Storm-control status|
|Port becomes err-disabled|Shutdown action triggered|`show interfaces status err-disabled`|
|SNMP alerts generated|Trap action configured|Storm-control configuration|
|No protection for multicast|Multicast storm control not configured|Interface configuration|
|No protection for unknown unicast|Unknown-unicast control not configured|Interface configuration|
|Traffic repeatedly suppressed|Threshold too low|Review rising/falling levels|
|Loop still exists|STP problem|Check STP topology|
|Legitimate traffic affected|Threshold too aggressive|Increase threshold carefully|

# 21. Troubleshooting Workflow

### Step 1 — Check Storm Control

```text
show storm-control
```

Determine:

```text
Traffic type
Configured threshold
Current status
```

### Step 2 — Check Interface Configuration

```text
show running-config interface Gi0/1
```

Look for:

```text
storm-control broadcast
storm-control multicast
storm-control unicast
storm-control action
```

### Step 3 — Check Interface State

```text
show interfaces Gi0/1
show interfaces status
```

### Step 4 — Check for Err-Disabled State

```text
show interfaces status err-disabled
```

### Step 5 — Check STP

If a storm appears to be caused by a loop:

```text
show spanning-tree
```

Check for:

- Unexpected topology
    
- Incorrect port roles
    
- STP state changes
    
- Missing/incorrect edge configuration
    
- Redundant links that are not being blocked appropriately
    

### Step 6 — Review Thresholds

If legitimate traffic is being suppressed, carefully review:

```text
Rising threshold
Falling threshold
Traffic class
Rate measurement
```

# 25. Automatic Recovery

If storm-control shutdown causes an err-disabled interface, automatic recovery can be configured using the appropriate supported errdisable recovery mechanism.

Example:

```text
errdisable recovery interval 60
```

The exact recovery cause supported for storm-control can vary by Cisco platform/IOS release.

Verify available causes:

```text
errdisable recovery cause ?
```

Then configure the appropriate cause if supported.

> Automatic recovery should be used carefully. If the storm condition remains, the interface can become err-disabled again.

# 26. Threshold Design

Storm-control thresholds should not be chosen blindly.

Too low:

```text
Legitimate traffic
       ↓
Threshold exceeded
       ↓
Unnecessary suppression
```

Too high:

```text
Real storm
    ↓
Threshold not reached quickly enough
    ↓
Greater impact
```

A practical design should consider:

- Interface speed
    
- Expected broadcast traffic
    
- Expected multicast traffic
    
- Expected unknown-unicast traffic
    
- Normal traffic patterns
    
- Rising/falling thresholds
    
- Business requirements

# 27. Important Terminology

### Broadcast

Traffic destined to:

```text
FF:FF:FF:FF:FF:FF
```

### Multicast

Traffic destined to a multicast MAC address.

### Unknown Unicast

A unicast destination MAC that is not currently present in the switch's MAC address table, causing flooding within the VLAN.

### Storm

An excessive amount of flooded traffic that can consume network resources.

### Suppression

Dropping/excluding traffic above the configured storm-control threshold according to the platform's implementation.

### Hysteresis

Using separate rising and falling thresholds to avoid repeated state changes around a single threshold.

# 28. Exam Traps

- Storm Control monitors **broadcast, multicast, and unknown-unicast** traffic.
    
- Unknown unicast is **not the same as all unicast traffic**.
    
- Storm Control operates at the **switchport/interface level**.
    
- Storm Control is a **flood-control mechanism**, not a replacement for STP.
    
- STP prevents Layer 2 loops; Storm Control limits the impact of excessive flooded traffic.
    
- Storm Control can use **percentage, pps, or bps**, depending on platform/IOS support.
    
- A rising/falling threshold provides **hysteresis**.
    
- Normal storm-control behavior **suppresses excessive traffic** rather than automatically shutting the port down.
    
- `action trap` provides a management notification; it does not mean the interface is shut down.
    
- `action shutdown` can place the interface into **err-disabled** state.
    
- Storm Control does not normally control **known unicast** traffic.
    
- Thresholds that are too low can suppress legitimate traffic.
    
- Thresholds that are too high may provide insufficient protection.
    
- Storm Control does **not identify or fix the root cause** of a Layer 2 loop.
    
- CoPP and Storm Control operate at different scopes: **CoPP protects the control plane; Storm Control protects against excessive flooded traffic at an interface**.
    
- Exact command syntax and supported threshold/action options can vary by Cisco platform and IOS/IOS XE release.

# 31. One-Minute Exam Summary

**Storm Control = limit excessive flooded traffic on a switchport.**

Remember:

```text
Broadcast ─────────┐
                   │
Multicast ─────────┼──→ Storm Control
                   │
Unknown Unicast ───┘
                         │
                         ▼
                  Threshold exceeded
                         │
                         ▼
                  Traffic suppressed
```

Core concepts:

```text
Storm Control → Flood-control mechanism
Broadcast     → Protected
Multicast     → Protected
Unknown UC    → Protected
Known UC      → Normally not controlled
Threshold     → %, pps, or bps depending on platform
Rising/Falling → Hysteresis
Suppress      → Normal protection behavior
Trap          → Notify NMS
Shutdown      → Err-disable interface
STP           → Prevents loops
CoPP          → Protects control plane
```

Most important commands:

```text
show storm-control
show running-config interface Gi0/1
show interfaces status err-disabled
show spanning-tree
```

**STP prevents the loop → Storm Control limits the flood → CoPP protects the CPU.**
