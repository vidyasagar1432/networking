# CoPP (Control Plane Policing)

> **Level 17 · Security** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

**CoPP (Control Plane Policing)** protects the device CPU by **rate-limiting traffic  
destined for the control plane**. This includes traffic such as routing protocols,  
management protocols, and other packets that the device itself must process.

Without CoPP, a high-rate flood directed at the device can consume CPU resources and  
interfere with routing, management, and other control-plane functions.

**Key idea:**

> **CoPP protects the CPU by classifying and policing traffic before it reaches the  
> control plane.**

---

## 2. Core Concepts

### 2.1 The Network Planes

|Plane|Purpose|Examples|
|---|---|---|
|**Data plane**|Forwards transit traffic|CEF-switched packets|
|**Control plane**|Runs protocols and processes traffic destined to the device|OSPF, BGP, EIGRP, STP, ICMP|
|**Management plane**|Device management and administration|SSH, SNMP, HTTPS, Syslog|

CoPP is applied to the **control plane** and can protect CPU-bound traffic, including  
management traffic that must be processed by the device.

---

### 2.2 How CoPP Works

```text
Incoming packet
      ↓
Control-plane classification
      ↓
ACL / class-map matching
      ↓
Policy-map
      ↓
Policing
   ↙      ↘
Transmit   Drop
      ↓
Device CPU
```

CoPP uses the Cisco QoS framework:

|Component|Purpose|
|---|---|
|**ACL**|Identifies interesting traffic|
|**Class-map**|Groups matching traffic|
|**Policy-map**|Defines policing actions|
|**control-plane**|Applies the policy to CPU-bound traffic|

---

## 3. CoPP Configuration Structure

A typical CoPP policy follows this structure:

```text
ip access-list extended COPP-MGMT
 permit tcp any host 192.0.2.1 eq 22
!
class-map match-any COPP-MGMT-CLASS
 match access-group name COPP-MGMT
!
policy-map COPP-POLICY
 class COPP-MGMT-CLASS
  police 512000 conform-action transmit exceed-action drop
 class class-default
  police 8000 conform-action transmit exceed-action drop
!
control-plane
 service-policy input COPP-POLICY
```

### Important

The ACL should classify traffic **destined to the device's own control plane**.

For example:

- SSH → device
    
- SNMP → device
    
- BGP → device
    
- OSPF → device
    
- ICMP → device
    

The exact ACLs and policing rates depend on the device, topology, protocol requirements,  
and expected traffic volume.

---

## 4. Policing Actions

A typical policing statement contains:

```text
police <rate> conform-action transmit exceed-action drop
```

|Action|Meaning|
|---|---|
|**conform-action transmit**|Traffic within the allowed rate is forwarded|
|**exceed-action drop**|Traffic above the allowed rate is discarded|

The goal is to allow legitimate control-plane traffic while limiting excessive traffic  
that could overwhelm the CPU.

---

## 5. Designing a CoPP Policy

### 5.1 Protect Critical Control Traffic

Routing and management protocols must receive enough bandwidth to function normally.

Typical traffic to consider:

- BGP
    
- OSPF
    
- EIGRP
    
- IS-IS
    
- HSRP/VRRP
    
- SSH
    
- SNMP
    
- ICMP
    
- Network-management traffic
    

Do **not** blindly apply extremely restrictive policing rates.

---

### 5.2 Use Separate Traffic Classes

A good CoPP design normally separates important traffic into logical classes.

Example:

```text
                    CoPP
                     │
        ┌────────────┼────────────┐
        ↓            ↓            ↓
     Routing       Management    Other
     protocols       SSH/SNMP    CPU traffic
        │            │            │
      Police       Police       Police
```

This prevents one type of traffic from consuming the entire control-plane allowance.

---

### 5.3 Class-Default

The `class-default` class catches traffic that does not match another class.

Example:

```text
class class-default
 police 8000 conform-action transmit exceed-action drop
```

A restrictive default policy can protect the CPU from unexpected traffic, but the rate  
must be high enough for legitimate unmatched control-plane traffic.

---

## 6. CoPP vs Other Protection Mechanisms

|Feature|Protects / Controls|Mechanism|
|---|---|---|
|**ACL**|Traffic entering/leaving an interface|Permit/deny|
|**Storm Control**|L2 broadcast/multicast/unknown-unicast storms|Rate limiting at switchport|
|**CoPP**|**Device control plane / CPU**|QoS policing|
|**Infrastructure ACL (iACL)**|Infrastructure addresses and services|ACL filtering|
|**uRPF**|Spoofed source addresses|Source-address validation|

### Key distinction

> **CoPP protects the device CPU.**

An interface ACL can block unwanted traffic before it reaches the device's processing  
path, while CoPP specifically controls traffic that is destined for and must be handled  
by the control plane.

---

## 7. CoPP Placement

CoPP is **not configured on individual interfaces**.

It is attached globally to the control plane:

```text
control-plane
 service-policy input COPP-POLICY
```

Therefore, do **not** think of CoPP as an "edge-interface protection feature."

Traffic can arrive through multiple interfaces and still be subject to the control-plane  
policy when it is destined for the device.

---

## 8. Verification

### Display the Control-Plane Policy

```text
show policy-map control-plane
```

This is the most important CoPP verification command.

Look for:

- Policy name
    
- Class names
    
- Packet counters
    
- Byte counters
    
- Conform counts
    
- Exceed/drop counts
    

Example:

```text
Router# show policy-map control-plane
```

### Other Useful Commands

```text
show control-plane
show class-map
show policy-map
```

The exact available commands can vary by Cisco platform and IOS XE release.

## 9. Troubleshooting

|Symptom|Possible Cause|What to Check|
|---|---|---|
|**CPU remains high**|CoPP absent or too permissive|Policy and class counters|
|**BGP/OSPF problems**|Routing traffic policed too aggressively|Routing class rate and drops|
|**SSH/SNMP fails**|Management traffic being dropped|Management class|
|**Unexpected CPU drops**|Class-default too restrictive|Default-class counters|
|**Legitimate traffic dropped**|Incorrect ACL/classification|ACL and class-map|
|**Flood still impacts CPU**|Rate limits too high or important traffic unclassified|Policy counters|
|**Management lockout**|SSH/HTTPS/SNMP not permitted or sufficiently policed|Management class|

### Troubleshooting Process

```text
1. Check the CoPP policy
        ↓
2. Check class counters
        ↓
3. Identify which class is dropping traffic
        ↓
4. Verify the ACL/classification
        ↓
5. Verify the policing rate
        ↓
6. Adjust the policy
        ↓
7. Recheck counters and CPU utilization
```

## 10. Common Configuration Mistakes

### Mistake 1 — Forgetting Management Traffic

If SSH is not properly classified and the default class is restrictive, legitimate  
management traffic can be dropped.

**Result:** possible management lockout.

---

### Mistake 2 — Policing Routing Protocols Too Aggressively

Routing protocols require sufficient control-plane bandwidth.

If BGP, OSPF, or another routing protocol is excessively policed, adjacency or routing  
stability can be affected.

---

### Mistake 3 — Treating CoPP Like an Interface ACL

CoPP is not configured like this:

```text
interface GigabitEthernet0/0
 ip access-group ...
```

Instead, the policy is attached to the control plane:

```text
control-plane
 service-policy input COPP-POLICY
```

---

### Mistake 4 — Making the Default Class Too Restrictive

A very low `class-default` rate can unintentionally drop legitimate CPU-bound traffic.

Always verify the traffic that will fall into the default class.

---

### Mistake 5 — Incorrect Classification

An ACL used by CoPP must accurately identify the traffic you intend to police.

Incorrect source/destination/protocol/port matching can result in:

- Important traffic being dropped
    
- Attack traffic being allowed
    
- Traffic falling into the wrong class
    

---

## 11. Exam-Critical Concepts

### Remember These

- **CoPP = Control Plane Policing**
    
- Protects the **device CPU/control plane**
    
- Uses the **QoS framework**
    
- Uses **ACL → class-map → policy-map**
    
- Policy is attached under **`control-plane`**
    
- Uses **policing/rate limiting**
    
- Excess traffic can be **dropped**
    
- Routing and management traffic must receive appropriate rates
    
- `class-default` handles unmatched traffic
    
- Verify with **`show policy-map control-plane`**
    
- CoPP is **not an interface ACL**
    
- Incorrect policing can disrupt routing or management
